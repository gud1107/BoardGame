# 보드게임 허브

1~10명이 폰이나 데스크톱으로 함께 즐기는 보드게임 대시보드 + 내기(순위 상금/벌금) 정산 시스템.

- **호스팅**: [Vercel](https://vercel.com/)
- **주 데이터베이스**: 브라우저 내장 **IndexedDB** (완전 오프라인 동작, 서버 없이도 전체 기능 사용 가능)
- **클라우드 DB (선택)**: [Supabase](https://supabase.com/) — 기기 간 플레이어 식별 매칭 + 내기 기록 백업용. 설정하지 않아도 앱의 나머지 기능은 정상 동작합니다. 단, **하나미코지·뱅!·그리드 포커·아발론·노땡스의 온라인 대전은 Supabase Realtime이 반드시 필요합니다** (기기들을 실시간으로 이어줄 다른 서버가 없기 때문) — 자세한 내용은 아래 "온라인 대전" 섹션 참고.

## 스택

Next.js 16 (App Router, Turbopack) · TypeScript · Tailwind CSS v4 · Zustand · idb (IndexedDB) · Supabase JS (선택)

## 시작하기

```bash
npm install
npm run dev
```

http://localhost:3000 접속. Supabase 없이도 모든 기능(게임 플레이, 내기 시스템, 기록)이 브라우저에만 저장되어 동작합니다.

Supabase를 연동하려면 `.env.example`을 `.env.local`로 복사해 값을 채우고, `supabase/schema.sql`을 Supabase SQL Editor에서 실행하세요.

```bash
npm run build   # 프로덕션 빌드
npm run lint    # ESLint
npm run test    # Vitest 단위 테스트 (게임 엔진 로직)
```

## 아키텍처 — 게임 20~100종으로 확장하기

게임 카탈로그는 순수 데이터입니다. `src/games/registry.ts`의 `GAME_REGISTRY` 배열에 항목 하나를 추가하면 대시보드에 즉시 카드가 나타납니다 (`playable: false`면 "준비중" 배지가 붙은 미리보기 카드로 표시).

실제로 플레이 가능한 게임을 추가하려면:

1. `src/games/<game-id>/` 아래에 순수 로직 엔진(`engine.ts`)과 React 컴포넌트를 작성합니다. 컴포넌트는 `PlayableGameProps`(`participants`, `onComplete`)를 구현해야 합니다 (`src/games/types.ts`).
2. `src/games/playableGames.tsx`의 `PLAYABLE_GAME_COMPONENTS`에 동적 import로 등록합니다 (대시보드 번들에 영향 없음).
3. `registry.ts`의 해당 항목을 `playable: true`로 바꿉니다.

`supportsAutoRanking`이 true인 게임은 `onComplete`에서 순위를 직접 계산해 넘겨줘야 하며(예: 하나미코지의 승/패), 그렇지 않은 게임은 플레이 후 순위를 수동으로 입력하는 화면(`RoundResultEntry`)이 자동으로 뜹니다.

**게임 로직과 내기 로직의 분리**: 각 게임의 실제 규칙/보드 UI(예: `HanamikojiBoard.tsx`)는 내기 시스템을 전혀 알지 못합니다. 승자만 `onGameEnd(winnerId)`로 보고하면, 그 게임의 최상위 컴포넌트(`HanamikojiGame.tsx`, `PlayableGameProps`를 구현)가 이를 `GameCompletionResult`(등수 배열)로 변환해 내기 정산으로 넘깁니다. 새 게임을 추가할 때도 이 패턴(순수 보드 컴포넌트 + 얇은 어댑터)을 따르면 됩니다.

## 1번째 게임: 하나미코지 (온라인 대전)

공식 규칙을 최대한 충실히 구현했습니다.

- 21장의 아이템 카드(게이샤 호감도 2,2,2,3,3,4,5장에 대응), 라운드 시작 시 1장 비공개 제외 후 각 6장 배분.
- 매 턴 1장 드로우 후 **비밀 / 거래 / 선물 / 경쟁** 4가지 액션을 라운드당 한 번씩 사용.
- 라운드 종료 시 게이샤별 카드 수를 비교해 다수를 가져간 쪽이 게이샤를 획득 — **게이샤 소유권은 다음 라운드에도 유지**됩니다.
- 누적 게이샤 4개 이상 또는 호감도 11점 이상을 먼저 달성하면 즉시 매치 승리.
- 화면 상단의 **"📖 룰북"** 버튼으로 4가지 액션과 승리 조건 요약을 언제든 다시 볼 수 있고, 카드/게이샤 칩을 호버(데스크톱)하거나 탭(모바일)하면 짧은 설명 툴팁이 뜹니다.

### 온라인 대전 (Supabase Realtime)

더 이상 한 기기를 주고받는 패스 앤 플레이가 아니라, **두 사람이 각자 자기 기기로 접속하는 실시간 온라인 대전**입니다.

1. **방 생성/참여**: 게임 카드를 누르면 바로 "🎲 방 만들기" / "🔑 초대 코드로 참여" 화면이 뜹니다 (기존의 "참가자 선택" 단계는 온라인 게임에서는 건너뜁니다 — `GameMeta.onlineMultiplayer`가 true인 게임은 방 자체가 참가자 식별 수단이 됩니다). 방을 만들면 4자리 코드가 생성되고 URL이 `?room=XXXX`로 바뀌어 그 링크를 그대로 공유하면 상대는 "참여"만 누르면 됩니다.
2. **대기실 → 자동 시작**: 두 사람이 같은 방 코드로 접속하면(Supabase Realtime **Presence**로 감지) 대기실이 자동으로 게임 화면으로 전환됩니다.
3. **실시간 동기화**: 카드를 뽑거나 액션을 선택하면 Supabase Realtime **Broadcast**로 상대 기기에 즉시(통상 1초 이내) 전달됩니다. 두 클라이언트는 서버에 상태를 저장하지 않고, **같은 시드로 같은 패를 배분**한 뒤 **같은 액션 로그를 같은 순서로 재생**해서 독립적으로 동일한 상태에 수렴합니다(락스텝 방식). 이 게임은 항상 "지금 차례인 사람"만 액션을 보낼 수 있는 구조라 두 기기가 동시에 쓰기 충돌을 일으킬 일이 없어서, 별도의 서버 권위(authoritative server) 로직 없이도 안전합니다.
4. **시점 분리 (카드 프라이버시)**: 접속한 기기가 p1/p2 중 어느 역할인지 판별해서, 화면 하단엔 **본인 손패만** 카드 앞면으로, 상대 손패는 **장수만 뒷면 아이콘**으로 보여줍니다.
5. **한계(문서화)**: 두 클라이언트가 같은 상태를 각자 계산하는 구조라, 기술적으로 자기 브라우저의 앱 상태를 직접 들여다보면 상대 손패 데이터 자체는 (렌더링되지 않을 뿐) 메모리에 존재합니다. 완전한 부정행위 방지를 하려면 서버가 각자에게 필요한 정보만 골라 보내주는 서버 권위 엔진(예: Supabase Edge Function)이 필요한데, 이번 범위에서는 과한 엔지니어링이라 판단해 제외했습니다 — 친구들끼리 하는 캐주얼한 온라인 대전 기준으로는 충분한 트레이드오프입니다.

**Supabase 설정 필요**: `.env.local`에 `NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_ANON_KEY`가 없으면 온라인 대전은 "설정이 필요합니다" 화면으로 안전하게 막힙니다(크래시하지 않음). Realtime Broadcast/Presence는 **별도 테이블/스키마가 필요 없습니다** — 프로젝트의 Realtime이 기본 상태(Authorization 미적용)라면 바로 동작합니다. 최신 프로젝트에서 Broadcast/Presence에 RLS 인가를 요구하도록 켜뒀다면 `realtime.messages`에 대한 정책을 추가해야 합니다.

## 2번째 게임: 뱅! (온라인 대전, 4~7인)

서부극 정체 은폐 카드 게임의 표준 베이스 게임판을 구현했습니다. **정식 룰의 개별 캐릭터 고유 능력(윌리 더 키드, 바트 카시디 등 16종)은 이번 범위에서 제외**했고, 그 외(80장 전체 카드, 보안관/부보안관/무법자/배신자 4역할, 두 가지 승리 조건 엣지 케이스, 무기 사거리·쌍안경/무스탕 거리 보정, 다이너마이트/감옥 메커니즘, 무법자 처치 보상, 보안관의 부보안관 오사 페널티)는 실제 규칙대로 구현했습니다.

- **역할**: 보안관(공개)은 부보안관과 함께 무법자·배신자를 전멸시키면 승리, 무법자는 보안관을 제거하면 승리, 배신자는 혼자 살아남아야만 승리(다른 조건보다 항상 우선). 제거되면 즉시 정체가 공개됩니다.
- **거리(Range)**: 자리는 원탁으로 고정되고, 죽은 자리는 계산에서 제외되어 원이 좁혀집니다. 장착한 무기가 정하는 사거리 이내의 상대만 뱅!으로 조준할 수 있고, 쌍안경/무스탕이 그 거리를 보정합니다.
- 화면 상단의 **"📖 뱅! 룰북"** 버튼으로 역할·거리·턴 순서·카드 22종 설명을 언제든 다시 볼 수 있습니다.
- **온라인 대전 아키텍처는 하나미코지와 완전히 동일한 패턴**입니다 — 방 생성(호스트가 4~7인 인원수를 정함) → 초대 코드 공유 → Realtime Presence로 좌석 채우기 → 시드 하나를 브로드캐스트해 각 클라이언트가 독립적으로 동일한 역할 배정·카드 셔플을 계산 → 이후 모든 카드 플레이는 `EngineAction`으로 브로드캐스트되어 같은 순수 리듀서(`applyAction`)로 재생. 뱅!의 "비밀 역할"은 하나미코지의 "비밀 손패"보다 훨씬 더 치명적인 정보라는 점(라운드 내내 유지되는 핵심 비밀 vs. 순간적인 카드 한 장) — 그럼에도 **같은 락스텝/전체 상태 공유 트레이드오프를 그대로 채택**했습니다: 이번 범위에서 새로운 서버 권위 인프라(Edge Function 등)를 두지 않기로 결정했기 때문입니다. 즉 기술적으로 자기 브라우저의 앱 상태를 들여다보면 다른 모든 플레이어의 역할과 손패를 알아낼 수 있습니다 — 친구들끼리 하는 캐주얼한 대전 기준의 트레이드오프이며, 진짜 부정행위 방지가 필요하면 역할만이라도 서버에서 배정해 각자에게 자기 역할만 전달하는 서버 권위 로직이 추가로 필요합니다.

## 3번째 게임: 그리드 포커 (온라인 대전, 2~6인)

넷플릭스 데스게임(오징어 게임 2화)의 룰을 참고해, 10면체 주사위 대신 표준 트럼프 카드로 재구성한 변형 규칙입니다.

- **덱**: 2~10·J·Q·K·A(13종 × 4문양 = 52장) + 조커 2장 = 54장. 공통 카드는 뽑을 때마다 즉시 되돌아가는 **복원 추출**이라, 매 순간 어떤 카드가 나올 확률이 항상 1/54로 동일하고 같은 카드가 여러 번 나올 수 있습니다. 조커는 숫자·문양을 가리지 않는 완전 와일드 카드입니다 (`evaluateHand`가 와일드 랭크를 전수 탐색해 최고의 족보를 계산).
- **배치**: 각자 5×5(25칸) 보드판에, 공개되는 공통 카드를 매 라운드 동시에 원하는 빈 칸에 배치합니다 (25라운드). 내가 가장 처음 놓은 칸만 상대에게 공개되고, 나머지 내 보드판 전체는 나만 볼 수 있습니다.
- **족보 제출**: 보드가 다 차면 가로 5 + 세로 5 + 대각선 2 = 12개 라인이 생기고, 매 라운드 각자 자신의 라인 중 하나를 골라 동시에 제출·비교해 승점을 겨룹니다(정통 포커 족보 서열 그대로, 동일 족보는 주 숫자 → 키커 → 마지막으로 문양(♠>◆>♥>♣) 순으로 승부). 2인전은 12개 중 10개 라인만 써서 6승 선취 시 즉시 승리(2개는 전략적으로 버릴 수 있음), 3인 이상은 12개 라인을 모두 써서 12라운드 종료 후 승점이 가장 높은 사람이 승리(7승 선취 시 즉시 확정)합니다.
- 화면 상단의 **"📖 족보 · 룰북"** 버튼으로 규칙 요약과 포커 족보 10종 예시 카드를 언제든 다시 볼 수 있습니다.
- **온라인 대전 아키텍처는 하나미코지·뱅!과 동일한 락스텝 패턴**입니다. 다만 카드 플레이가 "지금 차례인 사람"의 턴이 아니라 매 라운드 전원이 동시에 참여하는 구조라, 공통 카드를 뽑는 `draw-common` 액션만은 호스트(0번 좌석)가 `phase === "placing" && currentCard === null`을 감지해 자동으로 브로드캐스트합니다. 그 외(배치, 라인 제출)는 각자 자기 몫만 브로드캐스트합니다. 다른 두 게임과 같은 트레이드오프로, 모든 클라이언트가 전체 보드 상태를 메모리에 갖고 있고 UI가 시점 필터링만 담당합니다(`visibleOpponentBoard`).

## 4번째 게임: 아발론 (온라인 대전, 5~10인)

레지스탕스: 아발론(The Resistance: Avalon)의 표준 5~10인 룰을 구현했습니다. 정체 은폐 + 팀 투표 + 원정 성공/실패를 반복하는 파티 게임입니다.

- **역할**: 선한 세력(메를린/퍼시벌/충신)과 악한 세력(모르가나/모드레드/오베론/암살자)으로 나뉩니다. 인원별 구성은 공식 룰표 그대로(5인 3선 2악 ~ 10인 6선 4악)이며, 7인의 "오베론 또는 모드레드" 표기 애매함은 항상 모드레드를 우선하는 규칙으로 확정했습니다. 메를린은 모드레드를 제외한 모든 악(오베론 포함)을 보고, 퍼시벌은 메를린·모르가나 두 좌석을 알지만 둘 중 누가 진짜인지는 구분할 수 없고, 오베론을 제외한 악한 세력은 서로를 압니다.
- **원정 진행**: 리더가 라운드별 인원표에 맞춰 원정대를 지목하고 전원이 찬반 투표(과반 찬성만 통과, 동수는 부결) → 부결되면 리더가 다음 좌석으로 넘어가 재지목(한 라운드에서 연속 5회 부결 시 즉시 악 승리) → 승인되면 원정대만 비공개로 성공/실패 카드를 제출(선한 세력은 항상 성공만 제출 가능)합니다. 7인 이상의 4라운드는 실패 카드가 2장 이상이어야 실패 처리되는 예외가 있습니다.
- **승리 조건**: 원정 3회 실패 또는 연속 5회 부결이면 악이 즉시 승리, 원정 3회 성공 시에는 곧바로 끝나지 않고 암살자가 메를린으로 의심되는 좌석을 지목하는 암살 단계로 넘어가 — 정확히 맞히면 악의 역전승, 빗나가면 선의 승리로 확정됩니다.
- 화면 상단의 **"🎭 내 역할 다시 보기"** 버튼으로 언제든 자신의 비밀 정보(역할 + 그 역할이 아는 좌석)를 다시 확인할 수 있고, **"📖 아발론 룰북"** 버튼으로 역할·인원별 구성·원정 인원표를 다시 볼 수 있습니다.
- **온라인 대전 아키텍처는 하나미코지·뱅!·그리드 포커와 완전히 동일한 락스텝 패턴**입니다 — 방 생성(호스트가 5~10인 인원수를 정함) → 초대 코드 공유 → Realtime Presence로 좌석 채우기 → 시드 하나를 브로드캐스트해 각 클라이언트가 독립적으로 동일한 역할 배정을 계산 → 이후 모든 투표/원정 카드/암살 지목은 `EngineAction`으로 브로드캐스트되어 같은 순수 리듀서(`applyAction`)로 재생됩니다. 아발론의 "비밀 역할"은 뱅!보다도 더 치명적인 정보입니다 — 뱅!은 역할이 죽으면 공개라도 되지만, 아발론은 게임이 끝날 때까지 아무도 공개되지 않는 핵심 비밀이 그대로 유지되기 때문입니다. 그럼에도 **같은 락스텝/전체 상태 공유 트레이드오프를 그대로 채택**했습니다: 이번 범위에서 새로운 서버 권위 인프라(Edge Function 등)를 두지 않기로 결정했기 때문입니다. 즉 기술적으로 자기 브라우저의 앱 상태를 들여다보면 다른 모든 플레이어의 역할을 처음부터 끝까지 알아낼 수 있습니다 — 친구들끼리 하는 캐주얼한 대전 기준의 트레이드오프이며, 진짜 부정행위 방지가 필요하면 역할만이라도 서버에서 배정해 각자에게 자기 역할만 전달하는 서버 권위 로직이 추가로 필요합니다.

## 5번째 게임: 노땡스 (온라인 대전, 3~7인)

숫자 카드(3~35, 33장)를 놓고 벌이는 마이너스 경매(No Thanks!) 게임을 공식 규칙 그대로 구현했습니다.

- **준비**: 33장 중 무작위 9장을 아무도 보지 못하게 완전히 제외하고 남은 24장으로 진행합니다(`removedCards`는 엔진 상태에 남아 있지만 UI에는 절대 노출하지 않습니다). 시작 칩은 인원수별로 3~5인 11개, 6인 9개, 7인 7개입니다.
- **턴**: 중앙에 카드 1장이 공개되어 있고, 자기 차례엔 **칩 1개를 내고 넘기기(No Thanks!)** 또는 **카드+누적된 칩을 전부 가져오기** 중 하나를 고릅니다. 카드를 가져오면 즉시 다음 카드가 공개되고 **같은 사람이 턴을 이어갑니다**. 칩이 0개면 "넘기기"를 선택할 수 없고 무조건 가져와야 합니다 — 엔진이 이 조건을 어긴 `pass` 액션을 no-op으로 거부합니다.
- **점수 계산(핵심 규칙)**: 보유한 카드 숫자는 전부 벌점이지만, **연속된 숫자를 여러 장 가지고 있으면 그중 가장 작은 숫자 1장만** 벌점으로 계산합니다(`computeGroups`가 정렬 후 연속 구간을 묶습니다 — 처음에 무작위로 9장이 빠지기 때문에 중간 숫자가 없어 연속이 끊기는 경우가 흔합니다). 최종 점수 = (그룹별 최소 숫자의 합) − (남은 칩 개수)이며, 낮을수록 좋습니다. 동점이면 남은 칩이 더 많은 쪽이 우선이고, 그마저 같으면 진짜 공동 순위로 처리합니다(`computeRankings`, 표준 competition ranking: 1, 2, 2, 4 ...).
- **게임 모드(칩 공개 여부, 룰북 §2)**: 방장이 방 만들기 화면에서 **🔒 비밀 모드**(공식 룰 — 각자 자기 칩만 숫자로 보이고 남은 상대는 "?")와 **👁️ 공개 모드**(커스텀 룰 — 모든 플레이어의 칩이 항상 숫자로 공개)를 고릅니다. 선택값은 `game-start` 브로드캐스트에 실려 `startGame(playerCount, seed, chipVisibility)`로 전달되므로 **모든 클라이언트에 동일하게 적용되는 진짜 게임 규칙**이며, 대기실에도 현재 선택된 모드가 표시됩니다. 획득한 카드는 규칙상 항상 공개이므로 어느 모드든 상대 카드는 그룹화된 채로 그대로 보여줍니다.
- **로컬 연습 토글**: 비밀 모드에서도 화면 상단의 **"🙈 상대 칩 비공개"** 토글을 누르면 연습/디버그 목적으로 상대 칩을 나에게만 숫자로 표시할 수 있습니다(다른 사람 화면엔 영향 없는 로컬 전용 설정, `localStorage`에 저장 — 공개 모드에서는 이미 전원 공개이므로 이 버튼 자체가 숨겨집니다). **게임 종료 결과 화면에서는 모드·토글과 무관하게 전원의 칩이 항상 즉시 공개**됩니다.
- 화면 상단의 **"📖 노땡스 룰북"** 버튼으로 규칙 요약을 언제든 다시 볼 수 있고, 게임이 끝나면 전원의 카드 목록·연속 그룹화 내역·남은 칩·최종 점수를 표로 정리해서 보여줍니다.
- **연출**: "노 땡스!"를 선택하면 그 좌석에서 중앙 카드로 코인 하나가 토스되어 날아가고, "가져오기"를 선택하면 중앙의 카드+누적된 칩이 그 플레이어의 줄로 빨려 들어가듯 이동합니다(`AuctionEffects.tsx`). 두 효과 모두 새 라이브러리 없이 순수 CSS(`left`/`top` 트랜지션 + `@keyframes` — `globals.css`의 `coin-toss-arc`/`card-collect-fade`)로 구현했고, `NoThanksBoard`가 연속된 두 상태 스냅샷을 비교해(`detectAuctionEvent`) "방금 무슨 일이 일어났는지"를 추론하는 구조라 브로드캐스트로 상태를 받는 모든 클라이언트(행동을 한 사람뿐 아니라 지켜보는 사람까지)에서 동일하게 재생됩니다.
- **온라인 대전 아키텍처는 다른 4개 게임과 완전히 동일한 락스텝 패턴**입니다 — 방 생성(호스트가 3~7인 인원수를 정함) → 초대 코드 공유 → Realtime Presence로 좌석 채우기 → 시드 하나를 브로드캐스트해 각 클라이언트가 독립적으로 동일한 덱 셔플·9장 제외를 계산 → 이후 모든 pass/take 액션은 `EngineAction`으로 브로드캐스트되어 같은 순수 리듀서(`applyAction`)로 재생됩니다. 노땡스는 다른 게임들(비밀 역할, 비밀 손패)보다 비밀 정보가 적습니다 — 숨겨야 할 건 각자의 칩 개수뿐이라, 같은 락스텝/전체 상태 공유 트레이드오프를 채택해도 실질적인 노출 범위는 더 작습니다.

## 내기(정산) 시스템

화면 우측 하단의 **🎲 플로팅 버튼**으로 언제든 열고 닫을 수 있는 **내기 관리 사이드바**(`src/components/betting/BettingSidebar.tsx`)에서 모든 걸 처리합니다.

- **내기 활성화 스위치**: 켜면 현재 입력된 참가자/상금표로 내기가 시작되고, 끄면(확인 후) 내기가 종료·저장됩니다.
- 시작 전에는 참가자 닉네임(최대 10명)을 추가하고 등수별 상금/벌금 표를 입력합니다. **제로섬 검증**: 합계가 정확히 0원이 아니면 시작할 수 없습니다 (`src/lib/betting/zeroSum.ts`). 기본값은 스펙 예시(8명 기준 4000~-4000)와 동일한 로직으로 인원수에 맞게 자동 생성됩니다.
- 내기를 시작하지 않으면 게임은 순위 기록 없이 자유롭게 플레이됩니다(각 게임 페이지의 "게임 시작" 버튼은 이 경우 항상 바로 눌러도 되도록 `Player 1`/`Player 2` 같은 기본 이름이 자동으로 채워집니다).
- **진행 중에도 닉네임과 상금/벌금을 수시로 수정**할 수 있습니다. 닉네임을 바꾸면 현재 진행 중인 게임의 화면에도 즉시 반영되고(같은 전역 스토어를 구독), 상금표를 바꾸면 제로섬 검증을 다시 통과해야 저장됩니다(통과 전까지는 마지막으로 저장된 값이 유지). 다만 참가자 추가/삭제는 세션 중 지원하지 않습니다 — 이미 기록된 판들의 등수표 길이와 어긋나기 때문에, 내기를 끝내고 새로 시작해야 합니다.
- 내기 중에는 게임을 몇 개든 이어서 고를 수 있고, 매 판의 결과가 등수표를 소비해 상금/벌금을 계산 → 누적됩니다(사이드바에 실시간으로 표시). 실제로 플레이한 인원(예: 2인 전용 게임)만 자동 순위가 매겨지고, 나머지 참가자는 공동 순위로 자동 배정되며 필요하면 직접 조정할 수 있습니다.
- **"내기끝"**을 누르면 오늘 날짜로 최종 순위/금액이 `기록` 페이지에 저장되고 내기 상태는 초기화됩니다.
- 동점(공동 순위) 처리 시 해당 구간의 등수표 금액을 평균 배분하므로, 어떤 방식으로 순위를 입력해도 항상 합계 0원이 보장됩니다.

## 플레이어 식별 (일자별 닉네임 매핑)

동일 인물이 날마다 닉네임을 바꿔도 데이터가 이어지도록 3가지 신호를 조합합니다 (`src/lib/identity/`):

1. **정확히 같은 닉네임**이 이미 있으면 자동으로 같은 사람으로 처리합니다.
2. 닉네임은 다르지만 **이전 닉네임(별칭) 기록**, **같은 기기의 최근 사용 이력**, 또는 (Supabase 연동 시) **같은 IP의 다른 기기 이력**과 일치하면 "동일 인물로 보입니다" 확인 프롬프트를 띄웁니다.
3. 최종 판단은 항상 **사용자 확인**을 거칩니다 — 자동으로 조용히 병합하지 않습니다. (한 기기로 여러 명의 이름을 입력하는 것이 일반적인 사용 패턴이라, 기기 ID만으로 자동 확정하면 서로 다른 사람이 잘못 합쳐질 수 있기 때문입니다.)

IndexedDB만으로는 브라우저 하나에 국한되므로, 서로 다른 기기 간 매칭(같은 IP)은 Supabase를 연동해야 동작합니다.

## 설계 결정 및 이슈 기록

이 프로젝트에서 판단이 필요했던 굵직한 사항들을 남깁니다.

- **"Dexie.js" 대신 기존 `idb` 유지**: 사이드바의 "내기 끝" 저장 로직에 Dexie.js를 쓰자는 요청이 있었지만, 이 프로젝트는 이미 IndexedDB를 `idb`(Jake Archibald) 래퍼로 접근하고 있습니다(`src/lib/db/client.ts`). 두 라이브러리는 같은 IndexedDB 위에서 동작하는 동급 도구라, 굳이 새 래퍼를 추가하면 커넥션/스키마 정의가 두 곳으로 갈라질 위험만 커집니다. 그래서 사이드바도 기존 `saveDailyRecord`/`endSession` 경로(=`idb`)를 그대로 재사용했습니다. 진짜 Dexie.js로 전환이 필요하면 `src/lib/db/` 전체를 다시 쓰는 별도 작업으로 진행하는 걸 권장합니다.
- **"BettingContext" = 기존 Zustand 스토어**: 요청에서 언급된 전역 내기 상태는 이미 있는 `useBettingStore`(Zustand)를 가리키는 것으로 해석했습니다. React Context를 별도로 추가하면 같은 데이터를 가리키는 상태가 두 군데로 나뉘어 동기화 버그가 생기기 쉬워, 기존 스토어에 `sidebarOpen`/`updateParticipantName`/`updatePayoutTable`만 추가하는 쪽을 선택했습니다.
- **하나미코지: 게임 로직/내기 로직 분리**: 기존 `HanamikojiGame.tsx`(보드 UI 전체)를 `HanamikojiBoard.tsx`(순수 게임 — 승자 ID만 `onGameEnd`로 보고)와 `HanamikojiGame.tsx`(얇은 어댑터 — `PlayableGameProps.onComplete`용 등수 배열로 변환)로 나눴습니다. 이렇게 하면 보드 컴포넌트를 다른 맥락(예: 내기 없는 단독 페이지, 다른 정산 방식)에서도 그대로 재사용할 수 있습니다.
- **발견된 버그: 고정 인원 게임에서 "게임 시작"이 사실상 눌러도 진행 불가였던 문제**: 참가자 수를 바꿀 수 없는 게임(하나미코지처럼 min===max)은 인원수 변경 이벤트가 한 번도 발생하지 않아, 이름 입력 배열이 끝까지 빈 배열로 남아 있었습니다(입력창 자체가 렌더링되지 않음). 내기 없이 자유 플레이를 시도하면 참가자가 0명인 채로 시작 버튼만 눌리는 상태였습니다. 기본값을 `Player 1`/`Player 2`로 즉시 채워 넣는 것으로 수정했습니다 (`src/app/games/[gameId]/page.tsx`).
- **사이드바 도입으로 헤더의 "🎲 내기시작" 모달 UI 제거**: 기존에는 헤더 버튼 → 모달(Overlay)에서 설정 → 종료까지 전부 처리했는데, 이번 요청의 "상시 노출 사이드바"와 기능이 겹쳐 두 UI가 따로 상태를 관리하면 혼란스러워집니다. 그래서 `BettingPanel.tsx`(모달 기반)를 제거하고 사이드바 하나로 통합했습니다. 헤더에는 사이드바를 여는 버튼만 남겼습니다.
- **사이드바에서 참가자 추가/삭제는 세션 중 막아둠**: 이미 여러 판이 기록된 뒤에 참가자를 늘리거나 줄이면 그 판들의 등수/상금표 데이터와 길이가 어긋나 제로섬이 깨질 수 있습니다. 그래서 진행 중에는 닉네임/상금 액수만 수정 가능하고, 인원 변경은 "내기끝" 후 새로 시작하도록 제한했습니다.
- **패스 앤 플레이 → 온라인 대전 전환은 하나미코지를 완전히 새로 씀**: "전면 수정" 요청이라 두 모드를 동시에 지원하도록 만들지 않고, 기존 로컬(한 기기를 주고받는) 방식을 온라인 대전으로 완전히 교체했습니다. `HanamikojiBoard`가 더 이상 자체 `useReducer`로 상태를 소유하지 않고, `HanamikojiGame`(Realtime 동기화 레이어)이 상태를 소유해 props로 내려주는 완전한 제어 컴포넌트(controlled component)로 바뀌었습니다.
- **서버 없이 두 클라이언트를 동기화하는 방법 — 시드 기반 락스텝**: 카드를 섞은 전체 덱을 네트워크로 보내는 대신, 방장이 숫자 시드 하나만 브로드캐스트하면 양쪽 클라이언트가 각자 `startRound(..., seededRng(seed))`를 호출해 **동일한** 패를 독립적으로 계산합니다. 이후 모든 액션(`EngineAction`)도 브로드캐스트로 전달되고, 양쪽 다 같은 순수 리듀서(`applyAction`)로 재생합니다. 이 게임은 구조상 "지금 차례인 사람만 쓸 수 있음"이 항상 보장되어 두 클라이언트가 동시에 쓰기를 시도할 일이 없으므로, Supabase Edge Function 같은 서버 권위 로직 없이도 안전하게 수렴합니다. `next-round`(다음 라운드 배분)도 액션 자체에 시드를 실어 보내 같은 방식으로 동기화합니다.
- **완전한 정보 은닉은 하지 않음 (문서화된 한계)**: 위 락스텝 구조상 상대의 손패 데이터가 (렌더링되진 않지만) 내 브라우저의 앱 상태 안에도 존재합니다. UI 상으로는 상대 카드가 항상 뒷면으로만 보이지만, 개발자 도구로 상태를 직접 들여다보면 알아낼 수 있습니다. 진짜 부정행위 방지가 필요하면 서버가 각 클라이언트에 필요한 정보만 필터링해서 보내주는 서버 권위 엔진이 필요한데, 친구들끼리 하는 캐주얼 파티 게임 범위에서는 과한 엔지니어링이라 판단해 채택하지 않았습니다.
- **온라인 대전은 (현재는) 내기 시스템과 별개로 동작**: 내기 세션은 IndexedDB에 저장되는 **기기 로컬** 상태입니다(스펙상 원래 그렇게 설계됨). 온라인 대전은 서로 다른 두 기기에서 진행되므로, 애초에 한 기기의 내기 세션이 상대 기기와 공유될 방법이 없습니다. 그래서 `/games/[gameId]`는 `onlineMultiplayer` 게임에 한해 로컬 참가자 선택 단계를 건너뛰고, 결과는 이 기기의 게임 기록에만 저장됩니다. 온라인 대전 결과를 내기에 반영하려면 내기 세션 자체를 Supabase로 옮기는 별도의 더 큰 작업이 필요합니다.

## Vercel 배포

1. https://vercel.com/new 에서 GitHub 저장소(`gud1107/BoardGame`)를 Import 합니다.
2. **Framework Preset: `Next.js`** 를 선택하세요 (레포에 `next.config.ts`가 있어 대부분 자동 인식됩니다). Build Command / Output Directory / Install Command는 전부 Next.js 기본값(`next build` / `.next` / `npm install`) 그대로 두면 됩니다.
3. Supabase 기능(하나미코지·뱅!·그리드 포커·아발론·노땡스 온라인 대전, 기기 간 식별 매칭, 내기 기록 클라우드 백업)을 쓰려면 Environment Variables에 `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`를 추가합니다. 비워두면 그 기능들만 "설정 필요" 화면으로 자동 비활성화되고 나머지(대시보드, 내기 정산 등)는 정상 동작합니다.
4. Deploy. IndexedDB가 주 데이터베이스이므로 별도 DB 프로비저닝 없이 바로 배포됩니다.
