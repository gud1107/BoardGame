# 시각 검증(Playwright 스크린샷) — 방법, 토큰 비용, 스킬 설계 시행착오

이 문서는 2026-09-03 대화에서 정리된 내용을 남겨둔 기록이다. "육안으로 확인하기 어렵다"는
피드백에서 출발해 (1) 실제로 가능한가, (2) 얼마나 드는가, (3) 낭비 없이 어떻게 쓸 것인가를
다룬다. 실제 적용되는 규칙은 [`.claude/skills/visual-check-gate/SKILL.md`](../.claude/skills/visual-check-gate/SKILL.md)이고,
이 문서는 그 규칙이 왜 지금 형태가 됐는지의 배경 설명이다.

---

## 1. 애초에 육안 확인이 가능한가 — 가능하고, 이미 검증됨

방법: 스크래치패드에 캐싱한 Playwright(Chromium)로 headless 브라우저를 띄우고, 게임 화면을
스크린샷으로 저장한 뒤, `Read` 툴로 그 이미지를 Claude가 직접(비전 모델로서) 확인한다.

이게 필요한 이유는 이 저장소에 이미 문서화되어 있다: [`docs/README.md`](./README.md#기억할-것-하나)의
"기억할 것 하나"에 적혀 있듯, `npm run test`가 전부 통과해도 UI 컴포넌트 버그는 하나도 못 잡는다
(컴포넌트 렌더링 테스트 인프라 자체가 없음). 실제로 코드 리뷰만으로 "고쳤다"고 잘못 판단했다가
실제 화면 확인 후에야 드러난 버그가 최소 3건 있었다(하나미코지 제출 버튼 비활성화, 뱅! 손패 제한
로직, 노땡스 코인 애니메이션이 카드 숫자 가림 — 전부 [troubleshooting.md](./troubleshooting.md) 참고).
이번 세션 이전에도 힐오브트루스(플로팅 버튼 겹침)와 코요테(카드 애니메이션 결함)에서 스크린샷
검증으로만 잡히는 버그를 두 번 더 확인했다.

알려진 함정([memory: headless-browser-verification-method] 참고):
- 브라우저를 `try/finally`로 안 닫으면 chrome.exe 프로세스가 좀비로 남아 이후 실행을 막음
- 일시적 hydration mismatch가 요소를 `getByRole`에서 숨길 수 있음 → `:text-is` CSS 폴백 필요
- 대기 루프에는 "봇이 이미 이겼음" 같은 탈출 조건이 반드시 필요

## 2. 토큰 비용이 얼마나 드는가

### 2.1 비전 토큰 계산 공식

`토큰 ≈ (가로px × 세로px) / 750` (긴 변이 1568px를 넘으면 자동 축소 후 계산).

| 해상도 | 용도 | 토큰/장 |
|---|---|---|
| 390×844 | 모바일 뷰포트 | ~440 |
| 1280×800 | 데스크톱 뷰포트(기본) | ~1,365 |
| 1920×1080 | Full HD (1568×882로 축소됨) | ~1,844 |

Sonnet 5 기준(input $2/1M) 스크린샷 1장 = 약 $0.0014~0.0037 (2~5원). 장 자체는 무시할 수 있는 수준.

### 2.2 "1회 시각 검증 사이클" 전체 비용

스크립트 작성 + 서버 로그 + 스크린샷 N장 + 분석까지 합치면:

| 항목 | 토큰 |
|---|---|
| Playwright 스크립트 작성 | ~800 |
| 서버 부팅/콘솔 로그 | ~1,000~3,000 |
| 스크린샷 3~6장 | ~4,200~8,400 |
| 시각 분석 응답 | ~1,000~3,000 |
| **1차 패스 합계** | **~7,000~15,000** |
| 재검증 1.5~2회 포함 | **~15,000~30,000** |

순수 코드 리뷰/수정 사이클(1,500~4,000 토큰) 대비 **3~8배**.

### 2.3 프롬프트 캐싱 효과

이미지도 캐싱 대상이다. 최초 턴은 정가, 이후 턴(5분~1시간 TTL 이내로 대화가 이어지는 동안)은
캐시 read 가격(정가의 ~10%)으로 재사용된다. 즉 "한 번 찍은 스크린샷을 다시 논의"하는 건 거의
공짜에 가깝지만, "새 스크린샷을 계속 찍는" 재검증 루프 자체의 비용은 캐싱으로 줄지 않는다.

### 2.4 5시간 세션 기준 감(感) — 상대 모델

Anthropic이 5시간 세션 한도의 절대 토큰 수를 공개하지 않으므로, 아래는 **세션 전체 처리량을
100%로 놓은 상대 모델**이다(앵커는 이 프로젝트의 실제 세션 이력 — 힐오브트루스급 전체 리빌드가
세션 하나를 거의 다 채운 사례를 100%에 가깝게 둠). 실측 아님.

| 작업 규모 | 실제 예시 | 텍스트만 | 육안 검증 포함 |
|---|---|---|---|
| 소규모 | 버그 1건, 파일 1~2개 | ~1% | ~4% |
| 중간 | 코요테 카드 애니메이션 급 | ~6% | ~13% |
| 대규모 | 힐오브트루스 엔진+UI+DB 급 | ~63% | ~80% |

실제 정확한 수치가 궁금하면 작업 전후로 `/cost`를 찍어 실측 비교하는 게 이 표보다 신뢰도 높다.

## 3. 스킬 설계 시행착오 — 왜 지금 형태가 됐는가

`.claude/skills/visual-check-gate/SKILL.md`를 만드는 과정에서 두 번 잘못된 방향으로 갔다가
폐기했다. 같은 실수를 반복하지 않기 위해 기록한다.

**1차 시도 — 상대 배율 게이트**: 시각 검증 추가 비용이 작업 자체 비용의 3배를 넘으면
`AskUserQuestion`으로 진행 여부를 물음. → 사용자가 "배율보다 절대 증가폭(%p)이 중요하다"고
교정(예: 10%→30%는 "3배"보다 "+20%p"로 체감된다).

**2차 시도 — 절대 %p 게이트**: 작업 규모별로 허용 가능한 %p 증가 한도를 두고, 초과 시
`AskUserQuestion`으로 옵션(전체검증/라이트검증/생략) 제시. → 사용자가 다시 교정: 진짜 문제는
"검증할지 말지를 %로 판단해서 되묻는 절차" 자체가 아니었다. **사람은 화면을 1초 보면 이상 여부를
바로 안다. 실제 낭비는, 브라우저를 띄운 김에 Claude가 "혹시 다른 버그도 있나" 하며 스크린샷을
더 찍고 다른 화면을 탐색하고 재검증을 여러 라운드 도는 범위 확장이다.** 1차·2차 버전 모두 이
지점을 안 건드렸고, 근거 숫자도 미검증 추정치였으며, 매번 되묻는 것 자체가 왕복 비용을 더했다.

**최종본 — 범위 규율(scope discipline)**: %나 배율 추정, `AskUserQuestion` 게이트를 전부 제거.
대신:
1. 찍기 전에 확인할 질문을 한 문장으로 정한다
2. 그 질문에 필요한 최소 장수만 찍는다(거의 1장, 전/후 비교 시 최대 2장)
3. 답이 나오면 멈춘다 — 요청받지 않은 이상 다른 화면/기능을 스스로 탐색하지 않는다
4. 재검증은 실제 코드 수정이 있을 때, 같은 질문에 대해서만 1회
5. 화면에 영향 없는 순수 로직 변경은 애초에 스크린샷을 안 찍는다

전문은 [`.claude/skills/visual-check-gate/SKILL.md`](../.claude/skills/visual-check-gate/SKILL.md) 참고.
**%/배율 기반 승인 게이트는 두 번 시도하고 두 번 폐기됐다 — 다시 도입하지 말 것.**

## 4. 실무 기준 요약

| 상황 | 시각 검증 필요? |
|---|---|
| 순수 로직/상태 계산 버그 | ❌ 텍스트/로그로 충분 |
| CSS 겹침, 반응형 레이아웃, z-index | ✅ 필요 (질문 하나, 최소 장수) |
| 애니메이션 타이밍/시퀀스 | ✅ 필요 |
| "화면이 이상하다"는 모호한 리포트 | ✅ 먼저 스크린샷으로 재현 |
| 이미 확인한 화면을 다시 논의 | ✅ (프롬프트 캐싱으로 거의 무료) |
| 확인 중 "혹시 다른 것도" 하는 탐색 | ❌ 요청받았을 때만 |
