실제로 발생했던 버그를 시간순으로 기록한다. 각 항목은 **증상 → 원인 → 해결법 → 교훈 → 검증 방법** 순서로 정리했다. "왜 처음에 그렇게 짰는지"와 "다음에 비슷한 걸 또 만들지 않으려면 뭘 봐야 하는지"에 초점을 둔다.

## 1. 하나미코지 "경쟁(compete)" 액션 제출 버튼이 영원히 비활성화됨

**커밋**: `be7914c` · **파일**: `src/games/hanamikoji/HanamikojiBoard.tsx`

### 증상
경쟁(compete) 액션은 손에서 카드 4장을 골라 2장씩 A/B 두 묶음으로 나눠 제출해야 하는데, 정상적인 흐름(카드를 눌러 선택 → 묶음 배지를 눌러 A로 옮김)을 따라가면 제출 버튼이 **절대 활성화되지 않는** 경우가 있었다.

### 원인
"어떤 카드가 그룹 A에 속하는가"를 **별도의 선택 리스트에서 파생시킨 값**으로 관리했다. 카드를 선택하면 기본적으로 그룹 B에 들어가고, 작은 중첩 배지를 한 번 더 눌러야 그룹 A로 "태그"되는 2단계 흐름이었다. 문제는 이미 그룹 A에 태그된 카드를 선택 해제(deselect)해도 그룹 A 소속 정보가 함께 지워지지 않아, 그룹 A 카운트가 실제 선택된 카드 수와 어긋나 버렸다 — 즉 "선택된 카드 목록"과 "그룹 A 소속 여부"라는 **같은 사실을 표현하는 두 개의 상태가 서로 동기화되지 않고 따로 놀았다**.

### 해결법
파생 상태를 없애고, 카드가 "그룹 A / 그룹 B 둘 중 정확히 하나에만 속한다"는 **상호 배타적 상태**로 직접 모델링했다. 카드를 탭하면 자리가 남은 그룹에 바로 들어가고, 다시 탭하면 놓여난다 — 중간에 거쳐야 하는 "선택 후 재태그" 2단계 흐름 자체를 없앴다.

### 교훈
두 개의 상태가 같은 사실을 다른 방식으로 표현하고 있다면(하나가 다른 하나에서 파생되어야 마땅한데 독립적으로 갱신되고 있다면), 결국 어느 한쪽이 갱신을 놓치는 경로가 생긴다. 처음부터 상호 배타적인 단일 상태로 모델링하면 이런 드리프트가 구조적으로 불가능해진다. 이 원칙은 이후 "파생 상태 금지"라는 프로젝트 전역 가이드라인으로 굳어졌고, 4번 항목(뱅! 손패 제한 버그)도 같은 패턴의 재발이었다.

### 검증 방법
UI 컴포넌트 테스트 인프라가 없어(아래 "알려진 사각지대" 참고) 수동으로 "선택 → 재태그 → 해제 → 재선택"을 반복하며 버튼 활성화 조건을 추적, 콘솔에 상태를 찍어 그룹 A 카운트와 실제 선택 카드 수가 어긋나는 시점을 확인했다.

## 2. 고정 인원 게임에서 "게임 시작" 버튼이 사실상 진행 불가

**커밋**: `ab82796` (내기 사이드바 도입과 함께 수정) · **파일**: `src/app/games/[gameId]/page.tsx`

### 증상
참가자 수를 바꿀 수 없는 게임(하나미코지처럼 `players.min === players.max`인 경우)에서, 내기를 시작하지 않고 자유 플레이를 시도하면 "게임 시작" 버튼은 눌리는데 참가자가 0명인 채로 게임이 시작됐다.

### 원인
인원수 변경 UI(+/− 버튼)는 `min !== max`인 게임에서만 렌더링된다. 이름 입력 배열을 "인원수가 바뀔 때" 채우는 이벤트 핸들러에만 의존했는데, `min === max`인 게임은 그 이벤트가 **한 번도 발생하지 않는다** — 그래서 이름 입력창 자체가 렌더링되지 않고, 참가자 배열은 끝까지 빈 배열로 남았다.

### 해결법
이름 배열의 기본값을 이벤트 핸들러가 아니라 **초기값 자체**에서 `Player 1`, `Player 2` 같은 자리표시자로 즉시 채워 넣도록 바꿨다(`useState(() => Array.from({ length: min }, ...))`). 인원수가 바뀌는 게임도 같은 초기화 로직을 재사용해 일관성을 유지했다.

### 교훈
"카운트가 바뀔 때 배열을 다시 채운다"는 로직은 **카운트가 애초에 안 바뀌는 케이스**를 암묵적으로 가정하지 않는지 항상 의심해야 한다. `min === max`처럼 "그 경로가 아예 실행되지 않는" 입력값은 일반적인 수동 테스트에서 놓치기 쉽다 — 애초에 초기 렌더링 시점에 올바른 상태였는지를 별도로 확인하는 습관이 필요하다.

### 검증 방법
하나미코지(min=max=2)로 내기 없이 "게임 시작"을 눌러 실제로 두 플레이어 이름이 채워진 채 게임이 시작되는지 수동 확인.

## 3. 그리드 포커: 조커가 낀 손패의 문양 타이브레이커 오판정 + 로열 스트레이트 플러시 이름 누락

**커밋**: `75b7707` · **파일**: `src/games/grid-poker/engine.ts`

### 증상
조커가 포함된 라인을 평가할 때, 실제로는 더 높은 문양 타이브레이크 값을 받을 수 있는 조합인데도 낮은 평가를 받는 경우가 있었다. 또한 에이스 하이 스트레이트 플러시가 일반 "스트레이트 플러시"로만 표시되고 "로열 스트레이트 플러시"라는 이름을 받지 못했다.

### 원인
`evaluateHand`는 조커(와일드 카드)에 어떤 문양을 배정할지 브루트포스로 탐색하는데, 원래 로직은 **"고정 카드들이 공유하는 문양으로 플러시를 완성하는 경우"만** 후보로 시도했다. 하지만 (예: 포카드처럼) 플러시가 아닌 족보가 애초에 더 높은 카테고리로 이기는 경우, 조커의 문양은 고정 카드 문양과 맞출 필요가 전혀 없고, 오히려 문양 서열 최고값인 스페이드로 배정하는 게 최종 타이브레이크 값을 최대화한다. 즉 **"플러시를 완성하는 문양"과 "타이브레이크를 최대화하는 문양"이 다른 케이스를 놓치고 있었다.**

### 해결법
후보 문양 집합에 "플러시 완성 문양"뿐 아니라 **스페이드도 항상 포함**시켜 두 후보를 모두 시도하고 더 나은 결과를 채택하도록 바꿨다(엔진 주석에 "와일드 카드 하나에 섞인 문양 조합이 이 두 균일 후보보다 나을 수 없다"는 증명 스케치를 남겨둠 — 플러시가 성립하려면 모든 와일드가 같은 문양이어야 하고, 최종 족보에 안 들어가는 와일드의 문양은 결과에 영향을 안 주기 때문). 동시에 `category === 8 && ranks[0] === 14`(에이스 하이 스트레이트 플러시)인 경우를 "로열 스트레이트 플러시"로 별도 라벨링했다 — 비교 로직(카테고리 번호, 랭크 튜플)은 그대로 둬도 이미 최고 랭크로 정렬되므로 승패 판정에는 영향이 없고, **오직 `categoryName`이라는 표시용 문자열만** 분리했다.

### 교훈
"최적 문양을 찾는" 탐색 공간을 줄일 때는 그 축소가 **모든 승리 카테고리**에 대해 유효한지 따로 확인해야 한다 — 이 버그는 플러시 계열 족보에서만 테스트하고 넘어갔을 가능성이 높다. 또 "판정 로직"과 "표시용 이름"을 같은 매핑 테이블에서 1:1로 끌어오면, 룰상 별도 이름이 필요한 서브카테고리(로열 vs 일반 스트레이트 플러시)를 표현할 방법이 없다 — 판정과 표시는 항상 분리해서 설계하는 게 안전하다.

### 검증 방법
`GridPoker.test.ts`에 조커 + 비-플러시 카테고리 조합, 조커 + 로열 스트레이트 플러시 조합을 각각 직접 구성한 유닛 테스트 추가 (커밋에 40줄 분량 테스트 포함). `vitest run` 통과로 회귀 방지.

## 4. 뱅!: 부관을 사살한 보안관의 장비 미폐기 + "응급 맥주" 생존 규칙 누락

**커밋**: `208c0fb` · **파일**: `src/games/bang/engine.ts`

### 증상
공식 룰 7번 규칙 두 가지가 구현에서 빠져 있었다: (a) 보안관이 실수로 자기 팀 부관을 사살하면 페널티로 **손패와 장비 전부**를 버려야 하는데 손패만 버려지고 장비는 그대로 남아 있었다. (b) 체력이 0이 되는 플레이어가 손에 맥주(Beer) 카드를 갖고 있으면 그걸 버리고 체력 1로 생존하는 "응급 맥주" 규칙이 아예 구현되어 있지 않아 무조건 즉시 탈락했다.

### 원인
`eliminate()` 함수의 보안관 페널티 분기가 `discard: [...s.discard, ...killer.hand]`처럼 손패만 버림 목록에 넣고 `equipment`는 건드리지 않았다 — 애초에 "장비도 포함"이라는 룰 조항 자체가 최초 구현 시점에 누락된 것으로 보인다(별도의 회귀가 아니라 처음부터 없었던 기능). 응급 맥주도 마찬가지로 `applyDamage()`가 체력을 0 이하로 깎으면 조건 없이 바로 `eliminate()`를 호출하고 있었다.

### 해결법
- `eliminate()`의 보안관-부관 페널티 분기에서 `killer.equipment`의 모든 슬롯을 순회해 discard로 옮기고 `equipment: emptyEquipment()`로 초기화하도록 확장.
- `tryEmergencyBeerSave(state, seat)` 함수를 신설: 생존자가 2명 이하면 무효(룰 예외), 아니면 손패에서 맥주를 찾아 체력을 1로 만들고 그 카드를 버림 처리 후 새 상태를 반환(못 살리면 `null`). `applyDamage()`는 체력이 0 이하가 되면 `tryEmergencyBeerSave`를 먼저 시도하고, 실패했을 때만 `eliminate()`로 폴백.

### 교훈
룰북 기반 게임 엔진에서는 "룰이 언급하는 예외 조항이 코드에도 전부 반영됐는가"를 체크리스트로 관리할 필요가 있다 — 이번 두 건은 로직 버그가 아니라 **범위 누락**이었다. `boardGameRule/bang.md` 같은 원문 대조 자료를 갖고 있는 이유가 바로 이런 누락을 나중에라도 diff로 잡아내기 위함이다.

### 검증 방법
`Bang.test.ts`에 세 가지 케이스 추가: (1) 보안관이 부관을 죽였을 때 장비까지 discard로 가는지, (2) 응급 맥주로 살아남아 체력 1이 되는지, (3) 생존자 2명 이하일 때는 응급 맥주가 발동하지 않고 정상 탈락하는지(3번은 리셔플 시 방금 버린 맥주가 덱에 다시 섞이지 않도록 덱 길이를 충분히 준 상태로 구성). `vitest run` 133개 전부 통과 확인.

## 5. 뱅!: 재접속 클라이언트가 대기 화면에 영원히 머무름 + 좌석 중복 배정

**커밋**: `5260172` · **파일**: `src/games/bang/BangGame.tsx` (아발론·그리드 포커에도 동일하게 적용)

### 증상
게임이 이미 시작된 방에 새로 접속(새로고침, 재접속, 뒤늦은 초대 링크 클릭)한 클라이언트가 대기 화면에서 멈춘 채 게임 화면으로 못 넘어갔다. 별개로, 두 사람이 거의 동시에 방에 들어오면 둘 다 좌석 0을 잡아버리는 충돌도 멀티탭 테스트로 재현됐다.

### 원인
- **재접속**: `game-start` 브로드캐스트는 **1회성 이벤트**라, 그 순간 채널을 구독하지 않은 클라이언트는 영원히 못 받는다. 시드를 모르니 `startGame()`을 재현할 수도 없다.
- **좌석 충돌**: `channel.subscribe()`가 `SUBSCRIBED`를 알린 직후 바로 `presenceState()`를 읽으면, 그 순간 아직 다른 참가자의 Presence 레코드가 반영되기 전일 수 있다(비동기 sync 지연) — 그래서 두 클라이언트가 동시에 "지금 아무도 없다"고 착각해 같은 좌석을 잡을 수 있었다.

### 해결법
`docs/cloud-sync.md`의 §2.3(재접속 `state-request`/`state-sync`), §2.1(첫 Presence sync를 기다림), §3(좌석 충돌 시 deviceId 사전순 자가치유)에 상세 기록. 요약하면: 구독 직후 항상 `state-request`를 보내 이미 상태를 가진 아무 피어에게서 전체 스냅샷을 받고, 좌석 계산 전에 최초 Presence sync를 최대 800ms까지 기다리며, 그래도 충돌하면 결정론적 타이브레이크로 스스로 자리를 옮긴다.

### 교훈
"1회성 브로드캐스트로 초기 상태를 전달"하는 설계는 **그 이벤트를 놓친 클라이언트가 항상 존재할 수 있다**는 전제를 깔아야 한다(늦게 옴, 재연결함, 네트워크가 잠깐 끊김 등). 이벤트 기반 동기화에는 반드시 "현재 상태를 다시 물어볼 수 있는" 풀(pull) 경로를 짝지어야 한다. Presence 같은 최종 일관성(eventually consistent) 데이터는 "구독 완료 = 최신 스냅샷 확보"를 의미하지 않는다는 것도 별도로 기억할 점.

### 검증 방법
멀티탭(같은 브라우저 여러 탭 또는 여러 기기)으로 방을 만들고 게임 시작 후 새 탭으로 재접속해 게임 화면이 뜨는지, 두 탭을 거의 동시에 열어 좌석이 겹치지 않는지 수동 확인. 이 레이어는 Realtime 네트워크 타이밍에 의존해 결정론적 유닛 테스트로 표현하기 어려워 자동 테스트는 추가하지 않았다(알려진 사각지대, 아래 참고).

## 6. 뱅!: 손패가 체력 한도를 초과하면 카드 사용 자체가 막히는 치명적 버그

**커밋**: `a464895` · **파일**: `src/games/bang/BangBoard.tsx`

### 증상
"뱅!, 맥주, 장비, 이벤트 카드 등 모든 카드를 터치/드래그해도 액션이 트리거되지 않고 버리기만 가능하다"는 보고. 체력이 낮은 플레이어가 자주 겪었다.

### 원인
`mustDiscard` 변수가 `turnPhase === "action" && myTurn && hand.length > viewer.life`라는 **순수 파생값 하나**로 계산되고, 이 값이 참이면 카드 클릭이 무조건 "버릴 카드 선택" 토글로만 동작하도록 되어 있었다. 실제 뱅! 룰(`boardGameRule/bang.md`)에서 손패 제한은 **턴을 종료할 때만** 적용되는 규칙인데, 구현은 액션 페이즈 진입 즉시(카드를 한 장도 못 낸 시점부터) 이 조건이 참이 되는 순간부터 손패 전체를 버리기 전용 모드로 강제 전환시켰다 — 체력이 낮은 상태로 턴 시작 드로우 2장만 받아도 흔히 발생하는 상황이었다. `engine.ts`의 각 `play-*` 함수는 애초에 `turnPhase === "action"`만 확인할 뿐 손패 크기와 무관하게 정상 동작했으므로, **문제는 순수히 UI 컴포넌트 레이어**에 있었다.

이 버그가 [architecture.md §1.4](./architecture.md#14-파생-상태derived-state-금지-원칙)의 "파생 상태 금지" 원칙이 명시적 가이드라인으로 굳어진 계기이자, 1번 항목(하나미코지 경쟁 액션) 버그와 **정확히 같은 근본 패턴의 재발**이다 — "실제 사용자 트리거"가 아니라 "현재 값에서 항상 계산되는 파생값"만으로 UI 모드 전체를 잠갔다는 점에서 동일하다.

### 해결법
손패 제한을 나타내는 상태를 둘로 분리했다:
- `overHandLimit` — 여전히 순수 파생값(`hand.length > life`), **표시 문구용으로만** 사용.
- `discarding` — 플레이어가 실제로 "턴 종료" 버튼을 눌렀을 때만 `true`가 되는 명시적 상태(`useState`). 취소 버튼으로 다시 `false`로 되돌릴 수 있음.

실제 UI 분기(카드 클릭이 버리기 토글인지 사용인지)는 **`discarding && overHandLimit` 조합**으로만 판단한다 — `discarding` 단독으로는 절대 분기하지 않는다(턴이 넘어간 뒤에도 이전 턴의 `discarding=true`가 stale하게 남아있는 엣지케이스에 대한 자가 방어).

### 교훈
1. "규칙이 적용되는 시점"과 "규칙을 계산할 수 있는 조건"을 혼동하면 안 된다 — 손패가 체력을 초과했다는 **사실**은 액션 페이즈 내내 참일 수 있지만, 그 사실이 **강제되는 시점**은 턴 종료 시도 단 한 번뿐이다. 파생값이 "언제 이 사실이 참인가"는 정확히 계산해도, "언제 이 사실에 따라 행동을 제한해야 하는가"까지 자동으로 알려주지는 않는다.
2. **UI 컴포넌트는 엔진 테스트로 검증되지 않는다.** `Bang.test.ts`를 비롯한 4게임의 모든 `*.test.ts`는 `engine.ts`만 import해서 테스트한다(`vitest.config.mts`가 `environment: "node"`이고 jsdom/React Testing Library가 프로젝트에 아예 설치되어 있지 않음). 즉 "테스트가 전부 통과한다"는 사실이 "UI가 엔진 값을 올바르게 소비한다"는 보장을 전혀 해주지 않는다 — 이 버그도 엔진 자체는 처음부터 정상이었다.

### 검증 방법
`tsc --noEmit` / `lint` / `vitest run`(134개 전부 통과, 신규 회귀 테스트 1개 포함) 통과 확인. 추가된 엔진 테스트는 "손패가 체력을 초과한 상태에서도 `play-beer` 등 카드 사용 액션이 정상적으로 적용된다"는 **엔진 레벨 계약**만 검증한다 — UI가 그 계약을 실제로 지키는지는(즉 이 버그의 재발 자체를 자동으로 잡는지는) 사람이 코드를 직접 읽어 확인했다. 아래 "알려진 사각지대" 참고.

## 7. 노땡스: 코인/칩 배지가 중앙 카드의 숫자를 가리는 버그 (1차 시도 실패 → 구조적 재수정)

**커밋**: 1차 시도(실패) `2e8707c`, 진짜 수정 `e778f40` · **파일**: `src/games/no-thanks/NoThanksBoard.tsx`, `src/games/no-thanks/AuctionEffects.tsx`

### 증상
사용자가 iPhone Safari 실제 스크린샷을 첨부해 재현: 중앙 경매 카드의 큰 숫자(예: "10") 위에 코인(🪙) 모양 아이콘이 겹쳐서 숫자를 가리고 있었다. "가끔" 발생한다고 보고됨.

### 원인 — 1차 진단(틀렸음)
중앙 카드의 `chipsOnCard` 배지가 `absolute -bottom-3`만 있고 `left`가 없어, 브라우저가 flex 자식의 static-position을 자체 규칙으로 추정해 배치한다고 판단했다. 그래서 `left-1/2 -translate-x-1/2`로 배지를 수평 중앙에 명시적으로 고정하는 커밋(`2e8707c`)을 만들고 "해결됨"으로 보고했다.

**사용자가 실제 기기 스크린샷으로 재현해 보여줌 — 여전히(오히려 매번 더 정확하게 가운데로) 숫자 위에 코인이 얹혀 보였다.** 이 시점에 1차 진단이 틀렸다는 게 확인됐다.

### 진짜 원인
문제는 정적 배지의 위치가 아니라 **`AuctionEffects.tsx`의 "노 땡스!"(pass) 코인 토스 애니메이션의 착지 지점**이었다. `FlyingToken`의 `getTargetEl`이 `centerCardRef`(카드 박스 전체, 즉 숫자가 렌더링되는 바로 그 요소)의 중심으로 설정돼 있어서, 애니메이션이 끝나갈 때마다 코인이 **정확히 숫자 위**로 날아와 앉는 구조였다. 정적 배지 위치를 아무리 정교하게 조정해도, 애니메이션 자체가 매번 카드 중앙에 코인을 내려놓는 한 이 버그는 사라질 수 없었다.

### 해결법
카드 박스와 칩 배지를 `absolute` 겹침 구조에서 **완전히 분리된 두 개의 일반 flow 블록**으로 재구성했다 — 위: 카드 숫자 박스, 아래: 고정 높이(`h-7`) 슬롯 안의 칩 배지(칩이 0개면 빈 슬롯이라 레이아웃도 안 흔들림). 그리고 `coinLandingRef`라는 새 ref를 그 배지 슬롯에 달아, "pass" 애니메이션의 `getTargetEl`을 `centerCardRef`(카드 자체) 대신 `coinLandingRef`(배지 슬롯)로 바꿨다. 이제 코인/배지가 숫자와 **같은 박스에 존재할 수 없는 구조**라, 칩이 몇 개든(두 자리 수 포함) 애니메이션 도중이든 정지 상태든 겹칠 수 없다.

### 교훈
1. **시각적 버그는 코드 추론만으로 "고쳤다"고 단정하면 안 된다.** 1차 시도는 논리적으로 그럴듯했지만(실제로 존재하는 CSS 이슈이긴 했다) 진짜 원인이 아니었다 — `tsc`/`lint`/`vitest`/`build`가 전부 통과해도 이런 종류의 버그는 절대 못 잡는다(아래 "알려진 사각지대" 참고). 사용자가 실제 스크린샷을 보내주지 않았다면 틀린 수정을 "해결됨"으로 계속 믿고 있었을 것이다.
2. **정적 위치와 애니메이션 목적지는 별개의 버그 표면이다.** 배지가 최종적으로 어디 그려지는지(CSS 레이아웃)와 애니메이션이 어디로 날아가는지(`getTargetEl`)는 서로 다른 코드 경로라서, 하나만 고치고 다른 하나를 놓치기 쉽다. 두 요소가 시각적으로 "같은 곳에 있어야 하는" 관계라면, 가능하면 **같은 DOM 참조(ref)를 공유**해서 위치가 어긋날 여지 자체를 구조적으로 없애는 게 안전하다(이번 수정이 정확히 이 방식).
3. **"겹칠 수 있는 구조"를 고치는 것이 "안 겹치게 좌표를 맞추는 것"보다 낫다.** `absolute` 좌표 미세조정은 폰트 크기·칩 자릿수·뷰포트마다 다시 깨질 수 있지만, 애초에 두 요소가 같은 박스를 공유하지 않는 구조는 그 축의 버그 자체를 원천 차단한다.

### 검증 방법
`tsc --noEmit`/`lint`/`vitest run`(189개)/`build` 전부 통과 확인. **단, 이번에도 실제 브라우저 육안 재확인은 다음 세션 몫으로 남아 있다** — 1차 시도가 바로 이 단계를 건너뛰어서 실패했으므로, 이 항목만은 코드 검증만으로 "완료"라고 부르지 않기로 함(`HANDOFF.md`의 최우선 Next Action Item으로 명시).

## 8. 페루도: 최대 인원 6→8인 확장 직후 베팅 트랙이 런타임 `throw`로 즉시 깨짐

**커밋**: `a749f3a` · **파일**: `src/games/perudo/PerudoBoard.tsx`, `src/games/perudo/engine.ts`

### 증상
**정직하게 밝혀두면, 이건 실제로 화면이 깨진 걸 목격한 사후 대응이 아니라 구현 도중 코드 리뷰로 미리 잡은 케이스다** — `MAX_PLAYERS`를 6에서 8로 올리는 편집을 하기 직전, 베팅 트랙 코드를 다시 읽다가 "이 그리드 치수가 하드코딩돼 있으니 곧 깨지겠다"는 걸 먼저 알아채고 같은 편집 묶음 안에서 바로 고쳤다. 즉 `MAX_PLAYERS = 8`과 하드코딩된 9×8 그리드가 동시에 존재한 채로 실제 실행(`vitest`/`build`/브라우저)된 적은 없다. 그래도 기록해두는 이유: 만약 먼저 알아채지 못하고 그대로 `MAX_PLAYERS`만 바꿔 커밋했다면, 페루도 보드 컴포넌트가 모듈 로드 시점에 `Error: Perudo bid track expected 40 cells, got 30`을 던져 화면 자체가 뜨지 않았을 것이다(아래 방어 코드가 정확히 그렇게 설계돼 있었음).

### 원인
직전 세션에서 만든 클릭형 베팅 트랙(`BidTrack`)의 그리드 치수를 `TRACK_COLS = 9`, `TRACK_ROWS = 8`로 **하드코딩**해뒀다 — 당시 `TRACK_LENGTH`(= `MAX_PLAYERS × STARTING_DICE`)가 정확히 6×5=30이었고, 9×8 그리드의 테두리 칸 수(`2×9 + 2×8 − 4 = 30`)가 우연히 딱 맞아떨어졌기 때문이다. 컴포넌트 하단에 "치수가 어긋나면 알려달라"는 방어적 `if (TRACK_CELLS.length !== TRACK_LENGTH) throw`만 있었을 뿐, 치수 자체를 `TRACK_LENGTH`로부터 다시 계산하는 로직은 없었다. `MAX_PLAYERS`를 8로 올렸다면 `TRACK_LENGTH`가 30→40으로 바뀌는데 그리드는 여전히 9×8(30칸)에 머물러 있었을 것이므로, 그 방어 코드가 정확히 설계된 대로 즉시 터졌을 상황이었다.

### 해결법
`computeTrackDimensions(length)` 함수를 새로 작성해, 사각형 둘레 칸 수 공식(`2×cols + 2×rows − 4 = length`, 즉 `cols + rows = length/2 + 2`)을 풀어 그리드 가로/세로를 **매번 `TRACK_LENGTH`로부터 역산**하도록 바꿨다. `TRACK_COLS`/`TRACK_ROWS`라는 독립 상수를 완전히 제거하고, 이제는 오직 `MAX_PLAYERS`/`STARTING_DICE`(및 그 곱인 `TRACK_LENGTH`)만 소스로 삼는다. 기존의 방어적 `throw`는 "이제는 구조적으로 절대 트립되지 않는 백스톱"이라는 주석과 함께 그대로 남겨뒀다.

### 교훈
**다른 상수로부터 계산 가능한 값을 매직 넘버로 하드코딩하면, 그 원본 상수가 바뀌는 순간 반드시 드리프트가 생긴다.** 이번엔 코드 리뷰가 먼저 잡아냈지만, 설사 놓쳤더라도 방어적 sanity-check(`throw`) 덕분에 조용히 잘못된 화면을 보여주는 대신 즉시 시끄럽게 실패했을 것이다 — "조용한 오작동보다 시끄러운 실패가 낫다"는 방어적 설계가 왜 값어치 있는지 보여주는 예이면서도, 애초에 "치수를 길이로부터 역산"했다면 그 실패 시나리오 자체가 성립할 일이 없었다는 것도 함께 기억할 것. 이번 프로젝트에서 "파생 상태 금지"([architecture.md §1.4](./architecture.md#14-파생-상태derived-state-금지-원칙))가 *state*에 대한 원칙이라면, 이 버그는 그 사촌뻘 원칙("파생 가능한 상수를 재계산 없이 복제하지 말 것")이 *모듈 레벨 상수*에도 똑같이 적용된다는 걸 보여준 사례다.

### 검증 방법
`npx tsc --noEmit`/`npm run lint`/`npx vitest run`(228개, `startGame(8, seed)` 케이스 포함)/`npm run build` 전부 통과 확인. **단, 이 수정도 실제 브라우저에서 8인 풀 테이블 트랙 렌더링을 육안으로 확인하지는 않았다** — `HANDOFF.md`의 최우선 Next Action Item으로 남아 있음.

## 9. 센추리: 자원 번들에 값이 0인 키가 남아 업그레이드 테스트가 계속 실패함

**커밋**: `135d716` (수정된 채로 최초 커밋됨, 아래 "정직하게 밝혀두면" 참고) · **파일**: `src/games/century/engine.ts`

### 증상
**이것도 8번 항목과 같은 방식으로 정직하게 밝혀두면, 사용자가 실제로 겪은 버그가 아니라 구현 도중 vitest가 바로 잡아낸 케이스다** — 업그레이드 카드 관련 유닛 테스트 3개(`chains a single cube through multiple tiers`, `spreads upgrades across two different cubes`, `allows using fewer upgrade steps than the card's maximum`)가 계속 실패했다. 예: 노란색 2개를 전부 빨간색으로 업그레이드하면 결과가 `{ red: 2 }`여야 하는데 실제로는 `{ yellow: 0, red: 2 }`가 나와 `toEqual`이 실패했다.

### 원인
`playUpgrade`(엔진의 업그레이드 처리 함수)가 `working[from] = have - 1`로 자원 개수를 그냥 덮어썼다 — 개수가 0이 되어도 **키 자체를 지우지 않았다**. `ResourceBundle`은 "없는 키 = 0개"를 값으로 삼는 sparse map 타입(`Partial<Record<Resource, number>>`)으로 설계했는데(`cards.ts`의 `addBundle`/`subtractBundle`은 이미 0이 되면 키를 지우도록 짜여 있었음), 새로 짠 업그레이드 로직만 이 불변식을 안 지키고 있었다.

### 해결법
`have - 1 === 0`이면 `delete working[from]`, 아니면 `working[from] = have - 1`로 분기하도록 고쳤다(`simulateUpgrade`, engine.ts). 같은 파일 안에 이미 이 불변식을 지키는 `subtractBundle`류 헬퍼가 있었으므로, 그 관례를 따라가지 못한 새 코드를 기존 패턴에 맞춘 것뿐이다.

### 교훈
sparse map(부분 레코드)을 값으로 쓰는 타입은 "0이 된 키는 지운다"는 불변식을 파일 전체가 지켜야 `toEqual`류 구조적 비교(및 `bundleTotal`처럼 `Object.keys`를 순회하는 헬퍼)가 어긋나지 않는다. 같은 타입을 다루는 함수를 새로 추가할 때는 그 타입을 이미 다루고 있는 다른 함수(`addBundle`/`subtractBundle`)의 불변식을 먼저 확인하고 그대로 재사용하거나 명시적으로 따라야 한다 — 이번엔 유닛 테스트가 커밋 전에 즉시 잡아냈지만, `toEqual` 대신 개별 필드만 비교하는 테스트였다면 조용히 통과했을 수 있다(구조적 동등성 비교가 이런 종류의 버그에 특히 강하다는 부수적 교훈).

### 검증 방법
`npx vitest run src/games/century/Century.test.ts`로 실패하던 3개 테스트가 통과로 바뀌는 것 확인, 이후 `npx tsc --noEmit`/`npm run lint`/`npx vitest run`(272개)/`npm run build` 전부 통과 확인. 커밋에는 이미 수정된 버전만 들어갔다(버그가 있던 중간 상태는 커밋되지 않음).

## 10. 센추리: 금화/은화 공급량이 똑같은데도 금화 코인 스택만 짧게 보임

**커밋**: `style(century): overhaul UI to realistic spice road game board design` · **파일**: `src/games/century/CenturyBoard.tsx`

### 증상
UI 전면 개편 세션에서 임시 라우트로 실제 렌더링을 스크린샷 검증하던 중 발견됐다(사용자가 신고한 버그 아님) — 점수 카드 마켓 0번 슬롯(금화 보너스) 위의 동전 스택이 은화 스택(1번 슬롯)보다 눈에 띄게 짧아 보였다. `state.goldSupply`/`state.silverSupply`를 화면에 직접 찍어보니 둘 다 8(플레이어 4명×2)로 완전히 같았는데도 그랬다.

### 원인
처음엔 금색 동전 자체의 색 대비가 어두운 펠트 배경과 비슷해서 안 보이는 줄 알고 각 동전에 밝은 테두리 링을 추가했지만 증상이 그대로였다 — 색 대비 문제가 아니었다. 빨간 반투명 배경을 동전 스택 wrapper에 임시로 씌워 실제 바운딩 박스를 그려보니, 은화 스택은 카드 내용 위로 올라와 온전히 보이는 반면 금화 스택은 카드 뒤로 깔려 대부분 가려져 있었다 — **두 스택의 렌더링 크기는 같았고, 페인트 순서(어느 쪽이 카드 위로 그려지는지)만 달랐다.** 동전 스택 wrapper(`-top-9` 절대 위치)가 카드의 다른 자식 요소(점수 숫자, 비용 아이콘)와 같은 스태킹 컨텍스트에서 `z-index: auto`로 경쟁하고 있었는데, 카드 쪽의 조건부 클래스(구매 가능/불가 여부에 따라 `opacity-90`이 붙거나 안 붙는 등)가 두 카드 인스턴스의 스태킹 순서를 서로 다르게 만들어, 우연히 한쪽은 위로 한쪽은 아래로 깔린 것이었다.

### 해결법
동전 스택 wrapper에 명시적으로 `z-20`(+ 장식용이므로 `pointer-events-none`)을 주어, 카드 자신의 조건부 클래스가 무엇이든 항상 카드 내용 위로 그려지도록 고정했다.

### 교훈
`-top-9`처럼 부모 박스 경계를 넘어서는 절대 위치 장식 요소는 `z-index: auto`에 기대지 말 것 — 같은 컴포넌트를 여러 인스턴스로 반복 렌더링할 때, 인스턴스마다 달라지는 조건부 클래스(여기선 `affordable` 분기)가 우연히 스태킹 순서를 바꿔 "똑같은 데이터인데 한쪽만 다르게 보이는" 미묘한 버그를 만들 수 있다. 이런 종류는 코드만 봐서는 두 인스턴스가 완전히 동일해 보여 리뷰로 못 잡고, 실제 렌더링 스크린샷(이번처럼 값 자체를 화면에 찍어 데이터 문제가 아님을 먼저 배제하고, 그다음 반투명 배경으로 실제 바운딩 박스를 눈으로 확인하는 단계적 이분법)으로만 드러난다 — HANDOFF.md가 계속 강조해온 "레이아웃 버그는 코드 리뷰만으로 고쳤다고 단정하지 말 것" 원칙의 또 다른 실례.

### 검증 방법
임시 `dev-century-preview` 라우트 + `npx playwright screenshot`으로 (1) 값 디버그 출력 → 공급량이 실제로 같음을 확인, (2) 빨간 반투명 배경 임시 삽입 → 페인트 순서 문제임을 확인, (3) `z-20` 적용 후 재스크린샷 → 금화/은화 스택이 동일한 높이로 렌더링됨을 확인. 이후 `npx tsc --noEmit`/`npm run lint`/`npx vitest run`(273개)/`npm run build` 전부 통과 확인.

## 알려진 사각지대 (다음에 볼 것)

- **컴포넌트 레벨 테스트 인프라 없음**: `<Game>Board.tsx`(조건부 렌더링, 이벤트 핸들러)는 7게임 전부 자동 테스트 대상 밖이다. 6번 버그가 정확히 이 사각지대에서 나왔다. `@testing-library/react` + jsdom 환경(현재 `vitest.config.mts`는 `environment: "node"`)을 별도 프로젝트/워크스페이스로 추가하는 걸 최우선 후보로 남겨둔다.
- **레이아웃/시각적 버그는 자동 테스트로 원천적으로 못 잡는다**: 7번(노땡스 코인/숫자 겹침)이 정확한 사례 — `tsc`/`lint`/`vitest`/`build`가 전부 그린이어도 실제 렌더링 결과가 겹쳐 보이는지는 아무것도 검증하지 않는다. 컴포넌트 테스트 인프라(위 항목)가 생기더라도 jsdom은 레이아웃 계산을 하지 않으므로 이런 버그는 여전히 못 잡는다 — 진짜 해결하려면 Playwright 같은 브라우저 스크린샷 회귀 테스트가 필요하다(미착수, 저비용 후보로 남겨둠).
- **Realtime 네트워크 타이밍 관련 버그(5번)는 자동 테스트가 없다**: Presence sync 지연, 좌석 경쟁 조건 같은 건 실제 네트워크 타이밍에 의존해 결정론적 유닛 테스트로 재현하기 어렵다. 최소한 "좌석 충돌 자가치유 로직"(순수 함수로 분리 가능한 부분)만이라도 단위 테스트화할 여지가 있다.
- **대규모 동시 접속(5~7인) 스트레스 테스트 미실행**: 뱅!의 좌석 자가치유 로직은 2~3인 충돌만 수동 확인했고, 정원 가득 찬 상태에서의 동시 접속은 실측하지 않았다.
