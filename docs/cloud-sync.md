# 실시간 온라인 대전 동기화 (Supabase Realtime)

하나미코지·뱅!·그리드 포커·아발론·노땡스·페루도·센추리 등 대부분의 게임이 **같은 락스텝(lockstep) 동기화 패턴**을 쓴다. 이 문서는 그 패턴이 왜 이런 모양이 됐는지, 그리고 실제로 재접속·좌석 충돌 등 엣지케이스를 어떻게 다루는지를 기록한다. **단 하나의 예외(지렁이)가 있다 — §5 참고.**

설계 배경(신뢰 모델, 게임별 정보 노출 심각도 비교)은 [architecture.md §2](./architecture.md#2-온라인-대전의-신뢰-모델-문서화된-의도적-한계)를 먼저 읽을 것.

---

## 1. 왜 서버 권위 엔진이 아니라 락스텝인가

이 프로젝트는 게임 상태를 저장·중재하는 백엔드 서버를 두지 않는다(§ IndexedDB가 1차 저장소라는 원칙, [architecture.md §1.1](./architecture.md#11-indexeddb가-주-저장소-supabase는-선택적-보강-레이어) 참고). Supabase Realtime의 **Broadcast**(메시지 중계)와 **Presence**(누가 접속해 있는지)만 쓰고, 상태 자체는 저장하지 않는다 — Realtime은 순수히 "메시지 배달부" 역할만 한다.

그래서 두 클라이언트가 "같은 게임을 보고 있다"는 확신을 얻으려면 다음이 필요하다:

1. **초기 상태가 결정론적으로 동일해야 한다** — 방장이 정수 시드 하나만 브로드캐스트(`game-start` 이벤트, `payload: { seed, playerCount }`)하면, 모든 클라이언트가 `startGame(playerCount, seed)`를 각자 호출한다. 내부적으로 `seededRng(seed)`(mulberry32 알고리즘, 각 게임 `engine.ts`에 동일하게 구현)가 셔플/역할배정에 쓰이므로, 같은 시드 → 같은 카드 순서 → 같은 역할 배정이 모든 기기에서 재현된다. **덱 전체를 네트워크로 보내지 않고 시드 정수 하나만 보낸다**는 것이 핵심 — 페이로드가 작고, 재전송/재접속 시에도 그대로 재사용 가능하다.
2. **이후의 모든 변화가 같은 순서로 재생돼야 한다** — 유저 액션은 `game-action` 이벤트로 `{ action: EngineAction }`을 브로드캐스트하고, 받은 쪽은 자신의 로컬 상태에 `applyAction(prevState, action)`을 적용한다. 리듀서가 순수 함수이므로 같은 입력 시퀀스 → 같은 출력이 보장된다.

### 왜 안전한가 (그리고 그리드 포커에서는 왜 예외가 필요했는가)

하나미코지·뱅!·아발론은 구조상 **"지금 차례인 사람만 액션을 보낼 수 있다"**가 항상 성립해서, 두 클라이언트가 동시에 서로 다른 액션을 브로드캐스트해 충돌할 여지가 없다(단일 쓰기자 보장). 반면 그리드 포커는 **매 라운드 전원이 동시에 배치**하는 구조라 이 보장이 없다 — 그래서 "공통 카드를 뽑는" `draw-common` 액션만은 호스트(0번 좌석)가 `phase === "placing" && currentCard === null`을 감지해 **자신만** 브로드캐스트하도록 강제해 단일 쓰기자를 인위적으로 만들었다. 배치·라인 제출처럼 "자기 몫만 쓰는" 액션은 원래도 각자 자기 것만 브로드캐스트하므로 문제가 없다.

## 2. 방 생명주기

### 2.1 방 생성/참여

- 방장이 "방 만들기"를 누르면 4자리 숫자 코드(`generateRoomCode()`, `1000~9999`)를 생성하고 URL을 `?room=XXXX`로 바꿔 공유 링크로 쓴다.
- Supabase Realtime 채널 이름은 게임별로 고정 프리픽스를 쓴다(예: `bang-room-${roomCode}`). 채널 자체가 방의 정체성이다 — 별도 "방 목록" 테이블이 없다(§4 참고).
- `channel.subscribe()`의 `SUBSCRIBED` 콜백 안에서 좌석을 배정한다: 저장된 좌석(`localStorage`의 `<game>-seat-${code}`)이 있으면 재사용, 없으면 Presence 스냅샷에서 비어있는 가장 작은 인덱스를 고른다.
- **Presence sync 경쟁 조건에 대한 방어**: `channel.subscribe()`가 `SUBSCRIBED`를 알린 직후 바로 `channel.presenceState()`를 읽으면, 그 시점에 이미 접속해 있던 다른 사람의 기록이 아직 반영 안 됐을 수 있다(Presence sync 이벤트가 비동기로 뒤늦게 옴). 그래서 **최초 1회의 `presence: sync` 이벤트를 기다리거나(최대 800ms 타임아웃) 먼저 온 쪽을 채택**하는 `Promise.race`를 건 다음에야 좌석을 계산한다. 이 방어가 없으면 두 사람이 거의 동시에 들어왔을 때 둘 다 "아직 아무도 없다"고 착각해 똑같이 좌석 0을 잡아버린다(§3의 자가치유는 이 경쟁이 그래도 뚫렸을 때의 2차 방어선).

### 2.2 정원 도달 시 자동 시작

방장 클라이언트가 `occupants.length >= knownTargetPlayerCount`를 감지하면 `game-start`를 자동 브로드캐스트한다(`useEffect` 하나로 구현, `startSentRef`로 중복 전송 방지). 인원수가 가변인 게임(뱅! 4~7인, 그리드 포커 2~6인, 아발론 5~10인)은 방장이 대기실에서 목표 인원을 먼저 정해 Presence에 `targetPlayerCount`로 실어 보낸다.

### 2.3 재접속: `state-request` / `state-sync`

**문제**: 게임이 이미 시작된 뒤에 새로 구독한 클라이언트(새로고침, 네트워크 끊김 후 재연결, 뒤늦게 초대 링크 클릭 등)는 1회성 `game-start` 브로드캐스트를 놓친다. 시드를 모르니 `startGame`을 재현할 방법이 없고, 이후의 `game-action`들만 받아봤자 그 이전 상태를 모르므로 리듀서를 적용할 기준점이 없다.

**해결**: 채널 구독 직후 항상 `state-request` 이벤트를 브로드캐스트한다(payload 없음, 게임이 아직 시작 안 됐으면 그냥 무시됨 — no-op). 이미 게임 상태를 들고 있는 아무 클라이언트나(먼저 반응하는 아무나) 자신의 **현재 전체 상태**를 `state-sync` 이벤트로 되돌려주고, 요청자는 그 스냅샷을 그대로 자신의 상태로 채택한다 — 시드를 몰라도 `startGame`을 재현할 필요가 없다(어차피 상태 자체를 받으니까).

```
새 클라이언트                     기존 클라이언트(들)
     │  subscribe 완료                    │
     │──── state-request ────────────────▶│ (게임 상태 있으면)
     │◀─── state-sync { state } ──────────│
     │  setGameState(state); setPhase("playing")
```

이 핸들러는 `gameStateRef`(useRef)로 최신 상태를 참조한다 — 클로저로 캡처된 `useState` 값이 아니라 ref를 쓰는 이유는, 채널 이벤트 핸들러가 `channel.on(...)` 등록 시점(마운트 시 1회)의 상태를 그대로 캡처해버리면 이후 상태가 바뀌어도 핸들러 안에서는 계속 "구식" 값을 보게 되기 때문이다(전형적인 stale-closure 버그, 4게임 전부 동일 패턴 적용).

### 2.4 정원 초과 차단 (`room-full`)

호스트의 Presence 레코드에 실린 `targetPlayerCount`를 볼 수 있는 상황이라면, 새로 들어오려는 좌석 번호가 그 값 이상이면 즉시 `room-full` 화면으로 보낸다. **호스트 레코드를 아직 못 본 경우(자신이 방의 첫 참가자인 정상적인 경우 포함)는 절대 막지 않는다** — "알 수 없음"을 "차단"으로 취급하면 방장 본인이 자기 방에 못 들어가는 방향으로 실패할 수 있기 때문에, 판단 근거가 있을 때만 막고 없으면 항상 통과시키는 쪽으로 실패 모드를 정했다.

## 3. 좌석 충돌 자가치유 (Bang!/Grid Poker/Avalon/No Thanks!/Perudo 공통 패턴)

§2.1의 Presence 경쟁 조건 방어를 뚫고, 두 기기가 진짜로 동시에 같은 좌석을 잡아버리는 경우가 실측(멀티탭 테스트)으로 확인됐다. 즉시 "방이 꽉 찼습니다"로 실패시키는 대신, **결정론적 타이브레이크로 자가치유**한다:

1. 자신의 좌석에 다른 `deviceId`가 겹쳐 있는 걸 감지하면(Presence 목록에서 같은 seat, 다른 deviceId),
2. 두 deviceId를 **문자열 비교**해서 사전순으로 더 작은 쪽이 "이긴다"(그대로 유지), 큰 쪽이 자리를 양보하고 다음 빈 좌석으로 이동.
3. 매번 다시 track()으로 Presence를 갱신 — 상대 쪽도 같은 로직으로 자신이 이겼는지 졌는지 **독립적으로 동일하게 판단**하므로 조율 메시지 없이도 수렴한다(어느 한쪽만 움직이므로 무한 루프 없음).
4. 3회 재시도해도 계속 충돌하면(비정상 상황) 그제서야 `room-full`로 포기 — 이건 진짜 "다른 세션이 이 방 코드를 이미 쓰고 있는" 경우를 위해 남겨둔 최종 방어선이다.

**왜 deviceId 사전순인가**: 두 기기가 합의 없이도 같은 결론에 도달해야 하므로, 양쪽 모두가 계산 가능한 대칭적 기준이 필요하다. deviceId는 각자 로컬에 이미 갖고 있는 값이라 별도 통신 없이 즉시 비교 가능하다 — 방장 여부나 접속 시각처럼 상대方에게 물어봐야 아는 값은 이 용도에 못 쓴다(경쟁 조건이 애초에 "누가 먼저인지 모르겠다"는 상황이므로).

## 4. 의도적으로 없는 것들

- **"방 목록 조회" 기능 자체가 없다** — 서버가 없는 구조상 "지금 열려 있는 방이 뭐가 있는지" 질의할 대상이 없다(Presence는 채널을 이미 구독해야만 볼 수 있음). 초대 코드를 아는 사람만 들어올 수 있는 게 의도된 설계다.
- **호스트 이탈 시 권한 승계 로직 없음** — 방장이 대기 중 이탈하면 아무도 `game-start`를 자동 트리거할 수 없다(다른 클라이언트는 `isHost`가 아니므로 정원 도달 감지 `useEffect`가 동작 안 함). 알려진 미해결 항목, [README.md의 다음 우선순위](./README.md#다음에-할-일--알려진-한계) 참고.
- **4자리 초대 코드 중복 검사 없음** — 서로 다른 그룹이 우연히 같은 코드로 동시에 방을 만들면 같은 Realtime 채널을 공유하게 된다(충돌). 확률이 낮다고 판단해 검사를 생략했다(알려진 한계).
- **RLS(Row Level Security) 불필요** — Realtime Broadcast/Presence는 프로젝트가 기본 상태(Authorization 미적용)라면 별도 테이블/정책 없이 바로 동작한다. Supabase 프로젝트에서 Broadcast/Presence에 RLS 인가를 요구하도록 켜둔 경우에만 `realtime.messages`에 대한 정책 추가가 필요하다.

## 5. 예외: 지렁이는 락스텝이 아니라 "호스트 권위 실시간 동기화"를 쓴다

지렁이(`src/games/worm/`)는 2026-08-12 세션에서 턴제 주사위 게임(락스텝에 딱 맞는 구조)에서 Slither.io 스타일 **실시간 물리 시뮬레이션**(초당 수십 번 위치가 갱신되는 연속 움직임)으로 전면 재설계됐다. §1의 "왜 락스텝인가"의 전제 — *"이산적인 유저 액션을, 모든 클라이언트가 각자 재생한다"* — 가 애초에 성립하지 않는다: 매 프레임 "누가 지금 어느 각도로 이동 중인가"만 있을 뿐 재생할 만한 "액션"이 없고, 초당 수십 번의 이벤트를 매번 전체 재생하는 건 대역폭·연산 양쪽으로 락스텝의 장점(작은 시드/액션 페이로드)을 완전히 잃는다.

그래서 지렁이만 다음 프로토콜을 쓴다(`engine.ts`/`WormGame.tsx` 모듈 상단 주석에도 동일 내용 기록):

1. **호스트가 유일한 시뮬레이터.** 방장 클라이언트만 `stepWorm(state, dtMs, inputs, rng)`를 `requestAnimationFrame` 고정 스텝 루프(20Hz)로 계속 호출해 먹이 섭취·충돌·사망·부활을 판정한다. 다른 클라이언트는 이 함수를 아예 호출하지 않는다.
2. **호스트가 결과를 스냅샷으로 브로드캐스트.** 매 틱마다 시뮬레이션은 돌지만, 네트워크에는 `state-snapshot` 이벤트로 완성된 `WormState` 전체를 초당 약 11회(`BROADCAST_INTERVAL_MS`)만 실어 보낸다 — 대역폭을 아끼는 유일한 장치다. 다른 클라이언트는 받은 스냅샷을 그대로 `setGameState`해서 그릴 뿐, 보간(interpolation)이나 재조정(reconciliation) 없이 단순 렌더링만 한다(±90ms 지연은 캐주얼 파티게임 스코프에서 감내 가능하다고 판단, 알려진 한계).
3. **입력은 각자 브로드캐스트, 호스트만 소비.** 모든 클라이언트가 자신의 `{angle, boosting}`을 `player-input` 이벤트로 쏘고(`WormCanvas.tsx`가 이미 ~14Hz로 스로틀링), 호스트만 이걸 받아 다음 틱의 `stepWorm` 입력으로 merge한다. 단, 호스트 자기 자신의 입력은 네트워크 왕복 없이 로컬 ref를 직접 merge해 자기 조작만큼은 지연 없이 반영한다.
4. **초기 상태 재현은 기존과 동일.** `game-start`가 시드 하나를 브로드캐스트하고 모든 클라이언트가 `startGame(playerCount, seed)`를 각자 계산하는 것까지는 다른 게임들과 완전히 같다 — 달라지는 건 게임이 **시작된 이후**뿐이다.
5. **재접속(`state-request`/`state-sync`)도 그대로 재사용된다** — 새로 들어온 클라이언트가 "지금 상태를 아는 아무나"에게 최신 `WormState` 스냅샷을 요청하는 흐름은 호스트/논호스트 구분 없이 동일하게 작동한다(어차피 상태 자체를 스냅샷으로 주고받으므로).

**알려진 한계(문서화된 트레이드오프, 버그 아님)**: 호스트 탭이 닫히면 시뮬레이션이 완전히 멈춘다(호스트 이전/승계 로직 없음 — §4의 로비 단계 호스트 이탈 미해결 항목과 같은 성격). 논호스트 클라이언트는 자기 조작에 최대 `BROADCAST_INTERVAL_MS` + 왕복 지연만큼 반응이 늦게 보일 수 있다(스냅샷 그대로 렌더링, 예측/보정 없음).

이건 ARCHITECTURE.md §4 "새 게임도 새 프로토콜을 발명하지 말 것" 원칙의 **의도적이고 유일한 예외**다 — 그리드 포커의 단일 쓰기자 예외(§1)처럼 원래 프로토콜을 살짝 비트는 수준이 아니라, 애초에 이산 액션 재생이라는 전제 자체가 성립하지 않는 게임 장르라서 프로토콜 자체를 새로 정의했다. 앞으로 또 다른 실시간 물리/액션 게임을 추가한다면 락스텝이 아니라 이 절의 "호스트 권위 스냅샷 브로드캐스트" 패턴을 재사용할 것.
