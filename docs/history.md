**커밋**: `6a4787f`(최초 커밋) → `ab82796`

Next.js 대시보드 + 게임 카탈로그 + IndexedDB 기반 내기(정산) 시스템 + 첫 플레이 가능 게임인 하나미코지를 한 번에 갖춘 초기 골격. 이 시점에 이미 오늘날까지 유지되는 핵심 결정이 내려졌다:

- **IndexedDB를 1차 저장소로**(서버 DB 없이 완전 오프라인 동작) — [architecture.md §1.1](./architecture.md#11-indexeddb가-주-저장소-supabase는-선택적-보강-레이어).
- **게임 로직과 내기 정산 로직을 처음부터 분리** — 게임은 `onComplete(rankings)`만 상위에 보고([architecture.md §1.5](./architecture.md#15-게임-로직과-내기정산-로직의-완전한-분리)).
- 제로섬 상금표 검증(`validatePayoutTable`) — 합계 0이 아니면 세션 시작 자체를 막는 설계, 이후 한 번도 안 바뀜.

## Phase 1 — 하나미코지 실시간화 + 뱅!·그리드 포커 추가

**커밋**: `738c7f9`(하나미코지를 Supabase Realtime 기반 실시간 대전으로 전환) → `1fc9607`(뱅!·그리드 포커 신규 추가, 허브 연동)

이 시점에 **락스텝(lockstep) + 전체 상태 공유** 동기화 패턴이 처음 확립됐다(시드 하나만 브로드캐스트 → 각 클라이언트가 독립적으로 같은 초기 상태 계산 → 이후 `EngineAction`을 재생). 서버 권위 엔진을 두지 않기로 한 이유와 트레이드오프는 [architecture.md §2](./architecture.md#2-온라인-대전의-신뢰-모델-문서화된-의도적-한계)에 정리되어 있다 — "친구끼리 캐주얼 플레이" 기준으로 서버 인프라를 새로 두는 비용을 지지 않기로 한 판단이며, 이후 추가되는 모든 온라인 게임(아발론, 노땡스)이 예외 없이 같은 패턴을 그대로 재사용했다.

뱅!·그리드 포커 추가로 "엔진(순수 리듀서) + 보드 UI(제어 컴포넌트) + 네트워크 어댑터" 3계층 패턴이 게임마다 반복되는 **표준 구조로 굳어졌고**([architecture.md §1.6](./architecture.md#16-순수-엔진--제어-컴포넌트--얇은-네트워크-어댑터-3계층)), `src/games/registry.ts`를 순수 데이터 배열로 두고 `playable` 플래그로 "카탈로그엔 있지만 미구현"인 게임과 실제 구현을 분리하는 설계([architecture.md §4](./architecture.md#4-게임-카탈로그-데이터-중심-확장-설계))도 이 무렵 확정됐다.

- **재접속 시 게임 화면으로 못 넘어가는 문제** → `state-request`/`state-sync` 풀(pull) 경로 신설.

## Phase 7 — 노땡스(No Thanks!) 신규 게임: 5-Part 세션 (2026-08-07~08)

5번째 플레이 가능 게임으로 **마이너스 경매(No Thanks!)**를 추가한 연속 세션. 순서대로 진행된 5개 파트를 그대로 기록한다(각 파트가 이전 파트의 완료를 전제로 순차 진행됨).

### Part 1 — 순수 엔진 + 온라인 대전 UI 신규 구현
**커밋**: `67252f9`(룰북 문서화) → `5d42daf`(엔진+유닛테스트 33건) → `310497e`(보드 UI+룰북 모달+온라인 방) → `e06621d`(카탈로그 등록) → `0ce0c9a`(README 문서화)

`boardGameRule/noThanks.md`를 먼저 룰북으로 완성한 뒤 그걸 근거로 엔진을 구현하는 순서로 진행(Phase 3에서 확립된 습관의 재사용). 3~35 숫자 카드 33장 중 시드 기반 9장 무작위 제외, 인원별 시작 칩, "패스(칩 1개 소모)/인수(카드+누적 칩 획득 후 즉시 다음 카드 공개, 같은 사람이 턴 유지)" 리듀서, 연속 숫자 그룹화 채점 규칙(`computeGroups`)까지 다른 4게임과 동일한 3계층 구조·락스텝 동기화 패턴을 그대로 재사용해 구현했다.

### Part 2 — 칩 표시 로직 개선 + 코인토스/수거 애니메이션
**커밋**: `6388b24`(상태-diff 기반 이펙트 엔진) → `1fe1f8c`(애니메이션 배선 + 상대 칩 공개 토글) → `3c1be79`(README 문서화)

**새로 확립된 패턴**: 보드 컴포넌트는 리듀서가 만든 *결과 state*만 props로 받으므로("state가 fully controlled by the caller"), "방금 무슨 행동이 있었는지"를 알아내려면 연속된 두 상태 스냅샷을 diff하는 수밖에 없다 — `AuctionEffects.tsx`의 `detectAuctionEvent`가 이 패턴을 처음 확립했다. 엔진의 모든 리듀서가 거부된/no-op 액션에 대해 항상 **원본 객체 참조를 그대로 반환**하는 기존 관례 덕분에 `prev !== next` 참조 비교만으로 "진짜 상태 변화"와 "거부된 액션"을 안전하게 구분할 수 있었다. 이 diff는 행동을 한 사람뿐 아니라 같은 방의 모든 클라이언트에서 동일하게 계산되므로, 애니메이션이 브로드캐스트를 받는 모든 화면에서 똑같이 재생된다 — 락스텝 구조와 자연스럽게 맞물리는 좋은 부수 효과였다. 새 라이브러리 없이 순수 CSS(`left`/`top` 전환 + `@keyframes`)로만 구현(Phase 4의 방침 계승).

같은 파트에서 **로컬 전용 "상대 칩 공개" 연습 토글**(`localStorage` 저장, 다른 사람 화면엔 영향 없음)도 추가 — 이 프로젝트의 "모든 클라이언트가 전체 상태를 메모리에 들고 있다"는 신뢰 트레이드오프([architecture.md §2](./architecture.md#2-온라인-대전의-신뢰-모델-문서화된-의도적-한계))를 굳이 숨기지 않고 오히려 연습용 UX 기능으로 승격시킨 사례.

### Part 3 — "칩 공개 여부"를 host-선택 게임 규칙으로 승격
**커밋**: `ffcd16a`(룰북에 §2 게임 모드 설정 반영) → `50ea10c`(엔진에 `ChipVisibility` 추가) → `6d7d602`(방 생성 UI 배선) → `5543c9d`(README 문서화)

Part 2의 로컬 토글과의 핵심 차이: `chipVisibility`를 **엔진 상태(`NoThanksState`)에 넣고 `game-start` 브로드캐스트로 실어 보내** 모든 클라이언트에 동일하게 적용되는 진짜 공유 규칙으로 만들었다(로컬 토글은 개인 화면에만 영향을 주는 반면, 이건 방장이 정하는 게임 설정값). 대기실 화면에도 현재 선택된 모드가 표시되도록 해 늦게 들어온 참가자도 무슨 모드로 시작될지 미리 알 수 있게 했다.

### Part 4 — 덱 스택 시각화
**커밋**: `ac3f5f7`(`DeckStack` 컴포넌트 신규)

**커밋**: `4e87a41`(`노땡스()` 콘솔 헬퍼) → `fc6176f`(README 문서화) → `6e98909`(자동 안내 로그 제거) → `2e8707c`(**1차 시도, 실패**) → `e778f40`(**진짜 수정**) → `1981799`(HANDOFF 갱신)

**콘솔 헬퍼**: 락스텝 구조상 모든 클라이언트가 이미 메모리에 덱 순서·제외된 9장을 들고 있다는, [architecture.md §2](./architecture.md#2-온라인-대전의-신뢰-모델-문서화된-의도적-한계)에 문서화된 기존 트레이드오프를, React DevTools 탐색 없이도 확인할 수 있는 지원되는 창구(`window.노땡스`)로 노출했다. 자동으로 뜨던 안내 `console.log`는 사용자 요청으로 곧 제거(기능은 유지).

**"코인이 숫자를 가리는" 버그**는 이 프로젝트에서 **Phase 6과 정확히 같은 유형의 실패가 재발한 사례**다: 코드 추론만으로 "고쳤다"고 판단했다가(1차 시도 `2e8707c` — 정적 칩 배지의 수평 위치만 고정) 사용자가 보내온 실제 스크린샷으로 여전히 겹쳐 보인다는 게 드러났다. 진짜 원인은 정적 배지 위치가 아니라 **코인 토스 애니메이션의 착지 지점(`getTargetEl`)이 카드 박스 정중앙(숫자가 있는 바로 그 지점)으로 지정돼 있던 것** — 최종적으로 카드와 칩 배지를 완전히 분리된 두 개의 일반 flow 블록으로 재구성하고 애니메이션 착지 지점도 그 분리된 슬롯으로 옮겨 구조적으로 겹칠 수 없게 만들었다. 상세 증상/원인/교훈은 [troubleshooting.md #7](./troubleshooting.md#7-노땡스-코인칩-배지가-중앙-카드의-숫자를-가리는-버그-1차-시도-실패--구조적-재수정) 참고.

## Phase 8 — 인수인계 문서 체계 재정비 (2026-08-08)

**이 문서(`docs/history.md`) 신설** + 루트 `HANDOFF.md`를 "매 세션 Part를 계속 쌓아가는 로그"에서 **"현재 스냅샷만 담는 살아있는 문서"**로 재구성. 이전까지는 `HANDOFF.md` 하나가 세션 로그·아키텍처 요약·다음 할 일을 전부 떠안고 있어서 세션이 쌓일수록 문서가 계속 길어지는 구조였다 — 이제부터는 **시간순 기록은 이 `history.md`로, 버그 대응은 `troubleshooting.md`로 넘기고, `HANDOFF.md`는 "지금 이 순간의 스냅샷"만 유지**한다(Executive Summary / 현재 아키텍처·상태 / 다음 할 일 / 재개 프롬프트 4개 섹션 고정 템플릿). `docs/README.md`·`architecture.md`·`features.md`·`cloud-sync.md`의 게임 수·테스트 수 등 뒤처진 수치도 노땡스를 반영해 동기화.
