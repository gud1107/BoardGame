## Phase 0 — 시작: 허브 골격 + 내기 시스템 + 하나미코지

**커밋**: `6a4787f`(최초 커밋) → `ab82796`

Next.js 대시보드 + 게임 카탈로그 + IndexedDB 기반 내기(정산) 시스템 + 첫 플레이 가능 게임인 하나미코지를 한 번에 갖춘 초기 골격. 이 시점에 이미 오늘날까지 유지되는 핵심 결정이 내려졌다:

- **IndexedDB를 1차 저장소로**(서버 DB 없이 완전 오프라인 동작) — [architecture.md §1.1](./architecture.md#11-indexeddb가-주-저장소-supabase는-선택적-보강-레이어).
- **게임 로직과 내기 정산 로직을 처음부터 분리** — 게임은 `onComplete(rankings)`만 상위에 보고([architecture.md §1.5](./architecture.md#15-게임-로직과-내기정산-로직의-완전한-분리)).
- 제로섬 상금표 검증(`validatePayoutTable`) — 합계 0이 아니면 세션 시작 자체를 막는 설계, 이후 한 번도 안 바뀜.

## Phase 1 — 하나미코지 실시간화 + 뱅!·그리드 포커 추가

**커밋**: `738c7f9`(하나미코지를 Supabase Realtime 기반 실시간 대전으로 전환) → `1fc9607`(뱅!·그리드 포커 신규 추가, 허브 연동)

이 시점에 **락스텝(lockstep) + 전체 상태 공유** 동기화 패턴이 처음 확립됐다(시드 하나만 브로드캐스트 → 각 클라이언트가 독립적으로 같은 초기 상태 계산 → 이후 `EngineAction`을 재생). 서버 권위 엔진을 두지 않기로 한 이유와 트레이드오프는 [architecture.md §2](./architecture.md#2-온라인-대전의-신뢰-모델-문서화된-의도적-한계)에 정리되어 있다 — "친구끼리 캐주얼 플레이" 기준으로 서버 인프라를 새로 두는 비용을 지지 않기로 한 판단이며, 이후 추가되는 모든 온라인 게임(아발론, 노땡스)이 예외 없이 같은 패턴을 그대로 재사용했다.

뱅!·그리드 포커 추가로 "엔진(순수 리듀서) + 보드 UI(제어 컴포넌트) + 네트워크 어댑터" 3계층 패턴이 게임마다 반복되는 **표준 구조로 굳어졌고**([architecture.md §1.6](./architecture.md#16-순수-엔진--제어-컴포넌트--얇은-네트워크-어댑터-3계층)), `src/games/registry.ts`를 순수 데이터 배열로 두고 `playable` 플래그로 "카탈로그엔 있지만 미구현"인 게임과 실제 구현을 분리하는 설계([architecture.md §4](./architecture.md#4-게임-카탈로그-데이터-중심-확장-설계))도 이 무렵 확정됐다.

## Phase 2 — 아발론 추가 + 재접속/좌석충돌 자가치유 공통화

**커밋**: `1a28b75`(아발론 엔진/UI/테스트 + 허브 연동) → `5260172`(재접속 상태 동기화 + 좌석 정원 초과 차단, 4게임 공통 적용)

아발론은 4게임 중 **비밀 정보 유출 위험이 가장 높은 게임**이다(메를린 정체가 게임이 끝날 때까지 아무에게도 공개 안 됨) — 그럼에도 같은 락스텝/전체 상태 공유 트레이드오프를 그대로 채택했다는 점이 [architecture.md §2의 위험도 비교표](./architecture.md#2-온라인-대전의-신뢰-모델-문서화된-의도적-한계)로 명문화됐다.

멀티탭 실측으로 두 가지 실전 버그가 드러나 바로 이 시점에 4게임 공통 패턴으로 해결됐다(자세한 증상/원인은 [troubleshooting.md #5](./troubleshooting.md#5-뱅-재접속-클라이언트가-대기-화면에-영원히-머무름--좌석-중복-배정) 참고):

- **재접속 시 게임 화면으로 못 넘어가는 문제** → `state-request`/`state-sync` 풀(pull) 경로 신설.
- **동시 접속 시 좌석 중복 배정** → Presence 최초 sync를 기다리는 방어 + deviceId 사전순 자가치유(§3, [cloud-sync.md §3](./cloud-sync.md#3-좌석-충돌-자가치유-banggrid-pokeravalon-공통-패턴)).

**커밋**: `a464895`

"손패가 체력을 초과하면 카드 사용 자체가 막혀버리는" 버그([troubleshooting.md #6](./troubleshooting.md#6-뱅-손패가-체력-한도를-초과하면-카드-사용-자체가-막히는-치명적-버그))가 발견됐다. 원인은 하나미코지의 "경쟁 액션 버그"([troubleshooting.md #1](./troubleshooting.md#1-하나미코지-경쟁compete-액션-제출-버튼이-영원히-비활성화됨))와 **정확히 같은 근본 패턴의 재발**이었다 — 순수 파생값 하나만으로 UI 모드 전체를 전환한 것. 이 재발이 계기가 되어 "파생 상태 금지"가 `architecture.md`에 프로젝트 전역 원칙(§1.4)으로 명문화됐고, 이후 모든 신규 코드(노땡스 포함)에서 이 원칙이 체크리스트처럼 적용됐다.

Phase 9 직후 같은 날 두 번의 요청이 이어졌다. 첫 번째는 **"파코"라는 임시 용어를 룰북·엔진·UI 전반에서 "페루도"로 통일**하고, 사용자가 보낸 실물 다이스 사진을 참고해 스컬 이모지를 손으로 그린 인라인 SVG 크레스트(`PerudoFaceIcon.tsx`)로 교체 — Phase 4의 "새 라이브러리를 추가하지 않는다"는 방침이 이번에도 이어져 외부 이미지 자산 없이 SVG로만 구현했다. 여기에 실물 보드판을 본뜬 **클릭형 베팅 트랙**(`BidTrack` — 트랙 칸을 직접 눌러 선언), **컵 쉐이킹→리빌 연출 + SFX**(`soundEngine.ts`에 `playDiceRattle`/`playCupThud` 추가, Phase 4의 순수 합성 사운드 방침 계승), **상단/하단 현황판**(전체 주사위 수, 내 눈금별 통계, 1/3 기대값)을 새로 얹었다.

Phase 1~11에서 굳어진 3계층 패턴(엔진/보드 UI/네트워크 어댑터, [architecture.md §1.6](./architecture.md#16-순수-엔진--제어-컴포넌트--얇은-네트워크-어댑터-3계층))과 락스텝 온라인 동기화([architecture.md §2](./architecture.md#2-온라인-대전의-신뢰-모델-문서화된-의도적-한계))를 그대로 재사용했다는 점에서, 이 프로젝트가 반복 가능한 구조를 갖췄음을 다시 확인한 세션이기도 하다.

Century는 다른 6게임과 성격이 다른 두 가지 특징이 있다:

- **비밀 정보가 사실상 없다.** 손패는 공개 시장에서 뽑은 카드(효과가 이미 공개돼 있음)라 아발론/뱅!의 비밀 역할과 질적으로 다르고, 노출되는 건 자원 개수 같은 숫자뿐이다. 그래서 [architecture.md §2 표](./architecture.md#2-온라인-대전의-신뢰-모델-문서화된-의도적-한계)에 노땡스와 함께 "정보 유출 위험 최저" 그룹으로 기록했다.
- **행동 하나가 여러 하위 선택으로 구성된다.** 업그레이드 카드는 "어떤 자원을 몇 단계"를, 교환 카드는 "몇 번 반복할지"를, 상인 카드 획득은 "어떤 색으로 낼지"를 플레이어가 매번 골라야 한다. 다른 게임들의 액션은 대체로 파라미터가 하나뿐(카드 1장 내기, 숫자 하나 선언하기)이었던 것과 달리, `EngineAction`이 `upgrades: Resource[]`/`repeats: number`/`payment: Resource[]` 같은 구조화된 페이로드를 받는 첫 사례다.

**설계에서 판단이 필요했던 지점** (전부 `engine.ts`/`cards.ts` 상단 doc comment와 `docs/features.md`에도 기록):

1. **자원 가치 순서 충돌**: 작업 지시 프롬프트는 "노란색<초록색<빨간색<갈색"이라고 썼지만, 사용자가 함께 준 룰북 문서(`boardGameRule/Century.md` §4.1)는 "노란색<빨간색<초록색<갈색"이라고 명시했다. 실제 공식 게임 순서와도 일치하는 룰북 쪽을 채택했다 — 이 저장소는 항상 "`boardGameRule/*.md`가 엔진 구현의 근거 자료"([architecture.md §5](./architecture.md#5-디렉토리-구조-및-계층-규칙))라고 명문화해왔으므로, 두 텍스트가 갈릴 때 룰북을 우선하는 것이 기존 관례와 일치한다.
2. **금화 소진 시 은화 대체 여부 충돌**: 작업 지시 프롬프트는 "금화 소진 시 은화가 이동함"이라 했지만, 룰북 §5-D-2는 "금화가 떨어진 경우 은화를 가져오지 않습니다"라고 정반대로 명시했다. 마찬가지로 룰북을 채택해 대체 로직을 아예 넣지 않았다.
3. **42/36장의 실제 공식 카드 데이터는 재현하지 않았다.** 상인 카드 32장/점수 카드 36장(`cards.ts`)은 공식 카드의 정확한 문구·수치를 기계가 읽을 수 있는 형태로 구할 수 없어, 룰북이 설명하는 카드 *유형*(생산/업그레이드/교환, 자원 비용 기반 점수)과 밸런스 의도를 따라 새로 설계한 자체 데이터셋이다. 엔진/UI는 카드 데이터의 *형태*(`MerchantCardEffect`/`PointCard`)에만 의존하고 특정 카드 목록엔 의존하지 않으므로, 나중에 실제 카드 리스트를 구하면 `cards.ts`만 교체하면 된다.
4. **105개 향신료 큐브의 공용 보울 재고는 모델링하지 않았다.** 생산/교환은 항상 성공한다고 가정(무한 은행) — 유한 재고를 넣으려면 "동시에 두 클라이언트가 같은 색을 집으려는 경합"을 조정할 서버 권위가 필요한데, 이 프로젝트는 모든 온라인 게임에서 그 트레이드오프를 이미 명시적으로 거부해왔다([architecture.md §2](./architecture.md#2-온라인-대전의-신뢰-모델-문서화된-의도적-한계)).
5. **가격 카드의 금/은 코인 부여를 "물리적으로 카드 위에 놓인 코인"이 아니라 "슬롯 0/1을 완성하면 은행 공급량에서 코인을 지급"으로 단순화**했다. 룰북 §5-D-3의 "왼쪽으로 밀려진 카드가 1/2번째 자리에 도착하면 보너스 대상이 된다"는 문장을 분석한 결과, claim마다 시장이 즉시 5장으로 다시 채워지므로 두 모델(코인을 카드에 붙여 옮기기 vs. 슬롯 인덱스 기반 지급)이 항상 같은 결과를 낸다 — 상태를 하나 줄이는 쪽(파생 상태 금지 원칙)을 택했다.

반대로 **상인 카드 위에 쌓인 자원은 슬롯이 아니라 카드 자체에 붙어 이동**하도록 구현했다(§5-B 문구 "그 카드 위에 올려져 있던 모든 향신료도 함께 가져갑니다"가 요구하는 그대로) — `merchantMarketResources` 배열을 `merchantMarket`과 항상 같은 인덱스로 `filter()`해서 같이 이동시키는 방식으로, 점수 카드 코인과 달리 이쪽은 "카드에 귀속된 상태"라 슬롯 기반으로 단순화할 수 없었다.

단위 테스트 44개(엔진 전용, 자원 10개 초과 버리기 게이트/N번째 상인 카드 획득 시 자원 배치·회수/업그레이드 체이닝·분산/교환 반복/금은화 지급과 소진/종료 조건 판정 포함)를 추가해 전체 테스트가 228개→272개가 됐다. `<Century>Board.tsx`는 이 프로젝트의 다른 6게임과 마찬가지로 자동 테스트 대상 밖이다(jsdom 미설치, [architecture.md §1.6](./architecture.md#16-순수-엔진--제어-컴포넌트--얇은-네트워크-어댑터-3계층)) — 실제 브라우저 렌더링(카드 시장 레이아웃, 업그레이드/교환/획득 모달, 10개 한도 버리기 UI, 8인이 아닌 5인 이하 방 로비)은 아직 육안으로 확인되지 않았다.

## Phase 13 — 센추리 실물 카드 비주얼 + 동전 스택 + 카드 위 자원 올리기 UI (2026-08-08, 같은 날 다섯 번째 세션)

**커밋**: `style(century): update realistic card designs, coin stack UI, and resource placement on cards`

Phase 12에서 "코드 검증만 하고 실제 화면은 안 봤다"고 명시해 둔 미검증 항목(§3 1번) 중 비주얼 파트를 먼저 손댔다 — 사용자가 실물 센추리 카드 사진 두 장(상인 카드 뒷면의 자원→화살표→자원 아이콘 배치, 점수 카드의 큰 숫자+하단 큐브 4개)을 보내며 그 느낌을 본떠 달라고 요청했다. 이 프로젝트의 "외부 이미지 자산을 쓰지 않고 순수 인라인 SVG/CSS로만 만든다" 방침([architecture.md](./architecture.md), `ResourceIcon.tsx`/`PerudoFaceIcon.tsx`와 동일 관례)은 이번에도 유지했다 — 픽셀 단위 재현이 아니라 Phase 11에서 세운 "스타일(색감·질감·모티프)만 계승한다" 원칙을 그대로 이어받은 것이다.

세 가지를 `CenturyBoard.tsx` 안에서 새로 만들었다:

1. **금화/은화 입체 동전 스택(`CoinStack`)** — 점수 카드 마켓 1/2번째 칸 위에, 남은 개수만큼 원판이 겹쳐 쌓인 것처럼 보이는 컴포넌트. `goldSupply`/`silverSupply`(즉 `playerCount * 2`, `engine.ts`의 초기 공급량)만큼의 슬롯을 **항상 전부 렌더링**해두고 `visible`한 슬롯만 opacity/transform을 켜는 방식을 택했다 — 코인이 소진될 때 DOM에서 갑자기 사라지는 대신 `transition-all duration-500`으로 스택이 부드럽게 낮아지는 것처럼 보이게 하기 위해서다(코인 실물 이미지 없이 `radial-gradient` + `box-shadow`만으로 3D 원판 느낌을 냄). 5인 게임 초기 공급량(10개)까지 물리적으로 다 쌓으면 카드보다 스택이 더 커지므로 시각적 슬롯 수는 8개로 캡하고, 그 이상은 숫자 라벨로만 표기한다.
2. **상인 카드/점수 카드 얼굴 재설계** — 두 카드 모두 레이어드 `inset box-shadow`(선명한 안쪽 이중 테두리 + 하이라이트/그림자)로 "엔그레이빙된 양피지 프레임" 느낌을 낸 `CARD_FRAME_STYLE`을 공유한다. 상인 카드는 사진 속 "자원 큐브 스택 → 보라색 화살표 → 자원 큐브 스택" 배치를 `CubeStack`/`ArrowGlyph`로 그대로 재현했고(생산/업그레이드/교환 세 종류 각각 라벨+아이콘 구성을 다르게), 업그레이드 카드는 카드 실물에 대응하는 그림이 없어 "일반 큐브 → 화살표 → 금색 큐브"로 추상화한 `UpgradeGlyph`를 새로 만들었다. 점수 카드는 사진처럼 상단에 큰 세리프체 숫자, 하단에 요구 자원 큐브 바를 배치했다.
3. **상인 카드 위 자원 "올리기" UI + 수거 애니메이션** — 이전엔 카드 아래에 작은 "+자원" 배지로만 표시하던 걸, 카드 이미지 **위**에 회전을가진 큐브들이 얹혀있는 것처럼(`absolute -top-2.5`, 큐브마다 약간 다른 `rotate`) 보이도록 바꿨다. 카드가 실제로 획득될 때 그 카드 위에 있던 자원이 "함께 수거되는" 효과는, no-thanks의 `AuctionEffects.tsx`가 이미 확립해 둔 기법(연속된 두 락스텝 상태를 diff해서 "무슨 일이 일어났는지" 추론 → `document.body`에 포탈한 고정 위치 엘리먼트를 `left`/`top` CSS *트랜지션*으로 날리고, `globals.css`의 키프레임으로 부가 연출을 얹는 방식)을 그대로 재사용해 `MerchantEffects.tsx`(신규 파일, `detectAcquireEvent` + `FlyingResourceBurst`)로 옮겼다. 새 키프레임을 추가하지 않고 기존 `card-collect-fade`(축소+회전+페이드)를 그대로 빌려 썼다 — "카드+코인 무더기가 줄어들며 사라진다"는 의미가 그대로 들어맞았기 때문. 애니메이션의 시작 좌표는 **카드 id가 아니라 시장 슬롯 인덱스**에 매달린 ref로 읽는다(`merchantSlotRefs`) — no-thanks의 `centerCardRef`와 동일한 트릭으로, 카드가 사라지고 뒤 카드들이 한 칸씩 당겨진 뒤에도 "그 카드가 있던 화면 위치"를 여전히 정확히 읽을 수 있다. 이 방식은 액션을 누른 로컬 클라이언트뿐 아니라 **락스텝으로 같은 상태를 받는 모든 접속자**에게 동일하게 재생된다(행동 타입이 아니라 상태 diff에서 추론하므로).

이 세션도 Phase 12와 마찬가지로 **UI는 코드 리뷰 + `tsc`/`lint`/`vitest`/`build`만으로 검증했고 실제 브라우저 육안 확인은 하지 않았다** — 특히 동전 스택의 시각적 캡(8개)이 8인이 아닌 5인 이하 방에서 실제로 자연스러운지, 카드 위 자원 회전 배치가 자원 개수가 많을 때(획득 비용이 5인 마지막 칸) 서로 겹치지 않는지, 날아가는 자원 이펙트가 실제 클릭 흐름에서 타이밍 좋게 보이는지는 다음 세션 §3 1번 항목에 그대로 이월한다.

3. **통계 현황판 재배치** — 기존에는 "내 주사위" 컵 섹션 *다음*에 있던 `MyDiceStatsPanel`을, `BidTrack`(그 안에 "페루도!"/"맞아!" 버튼이 있음) 바로 아래로 옮겼다 — 사용자가 명시한 "액션 버튼 바로 아래쪽 영역"을 문자 그대로 만족시키기 위해 위치만 이동했다(내부 로직은 그대로). 표시 문구도 사용자 예시("전체 주사위: 20개 | 1/3 기대값: 6.6개")에 맞춰 기존의 "약 N~M개" 범위 표기를 소수점 한 자리 값 하나로 단순화하고, 얼굴 1 배지 라벨을 "페루도" → "페루도(1)"로 바꿨다.

**이번 세션은 실제 화면을 육안으로 확인했다** — Phase 9~13에서 반복적으로 "코드 검증만 하고 실제 화면은 안 봤다"고 남겨온 관행을 이번엔 깼다. `PerudoGame.tsx`가 Supabase Realtime 로비를 거쳐야만 `PerudoBoard`에 도달하는 구조라 오프라인 상태로는 직접 도달할 수 없어서, `src/app/perudo-preview/`에 `PerudoBoard`를 고정 상태(내 패에 1을 포함시키고, 내 차례로 만들고, 현재 베팅을 채워 두 액션 버튼을 모두 활성화한 상태)로 직접 렌더링하는 임시 라우트를 만들어 `npm run dev` + `npx playwright screenshot`으로 스크린샷을 찍어 확인한 뒤, 확인이 끝나자마자 그 라우트를 삭제했다(커밋에는 포함되지 않음). 확인한 것: 주사위가 둥근 모서리·광택 하이라이트로 렌더링되는지, 페루도(1) 얼굴에 새 아이콘이 또렷하게 보이는지, 통계 현황판이 정확히 액션 버튼 바로 아래에 오는지, 룰북 모달의 아이콘도 함께 바뀌는지 — 전부 스크린샷으로 육안 확인 완료. **다만 이 확인은 "이번에 바뀐 부분"에 한정된다** — 8인 만석 레이아웃, 컵 쉐이킹 애니메이션의 실제 타이밍, reveal/gameOver 화면, 팔라피코 배너, 그리고 무엇보다 **실제 Supabase 온라인 로비를 거친 멀티 디바이스 동기화**는 이번에도 검증 대상 밖이다 — Phase 11에서 이월된 §3 항목은 이 범위만큼만 좁혀졌을 뿐 완전히 해소되지는 않았다.

## Phase 15 — 센추리 상인 카드 덱 필터링 버그 수정 + 수레 10칸 인벤토리 슬롯 UI (2026-08-08, 같은 날 일곱 번째 세션)

**커밋**: `fix(century): exclude starter cards from merchant deck and add 10-slot cart inventory UI`

사용자가 두 가지를 요청했다: (1) 게임 시작 시 각 플레이어가 받는 기본 상인 카드 2장(노란색 2개 생산 / 자원 2단계 업그레이드)과 **효과가 완전히 같은 카드**가 중앙 마켓/덱에도 다시 등장하는 문제 수정, (2) 개인 수레(자원 보관함)를 10개 한도가 한눈에 보이는 슬롯 그리드 UI로 개편.

**버그 원인 재확인**: `startGame()`(`engine.ts`)은 애초부터 `createMerchantDeck()`이 반환한 배열만 셔플해 시장/덱을 채웠고, 시작 카드(`basicProductionCard`/`basicUpgradeCard`, `startGame`이 각 좌석 `hand`에 직접 심음)를 그 배열에 추가로 합치는 코드는 없었다 — 즉 "시작 카드 자체가 마켓에 다시 섞여 들어가는" 것이 아니라, `cards.ts`의 32장 원본 데이터 중 `merchant-u3`/`merchant-u4`(둘 다 `{kind:"upgrade", upgrades:2}`)가 **id만 다르고 효과 수치가 시작 카드와 완전히 같아서**, 플레이어 입장에서는 "내 시작 카드가 마켓에 또 있다"로 보이는 게 실제 증상이었다. 생산 카드 쪽(`merchant-p1~p9`)은 현재 `{yellow:2}}` 그대로인 항목이 우연히 없어 증상이 관측되지 않았을 뿐, 같은 문제에 노출돼 있었다.

**수정**: `cards.ts`에 `isStarterMerchantEffect(effect)`를 신설 — 카드 `id`가 아니라 **효과의 종류+수치를 구조적으로 비교**해 시작 카드 두 종류(`basicProductionCard(0).effect`, `basicUpgradeCard(0).effect`)와 일치하는지 판정한다. `createMerchantDeck()`이 반환 직전에 이 필터를 거쳐, 결과적으로 `merchant-u3`/`merchant-u4` 두 장이 제외되고 실제 셔플되는 덱은 32장이 아니라 **30장**이 된다. id가 아니라 구조적 비교를 택한 이유는, 나중에 누군가 `cards.ts`의 다른 카드 수치를 편집하다가 실수로 시작 카드와 같은 숫자를 다시 만들어도 이 필터가 여전히 걸러내도록 하기 위해서다(방어적 설계 — Phase 12의 "카드 데이터는 나중에 실제 카드 리스트로 교체될 수 있다"는 전제와도 맞물린다). 회귀 테스트 1건을 `Century.test.ts`에 추가해 5개 시드로 `startGame(5, seed)`를 돌리고 마켓+덱 전체에 두 시작 효과가 하나도 없는지 확인했다(272→273개).

이번 수정으로 **덱 카드 수가 32장에서 30장으로 줄었다는 점은 밸런스에 미세한 영향을 준다** — 새 카드로 대체하지 않고 그냥 제외하는 쪽을 택했는데, 이는 사용자가 "완전히 제외"라고 명시했고 이 카드셋 자체가 Phase 12에서 이미 "공식 카드를 재현한 것이 아닌 자체 설계 데이터셋"이라고 문서화돼 있어(§4.1 참고), 대체 카드를 새로 설계하는 건 이번 요청 범위를 넘는 판단이라고 봤기 때문이다.

**수레 10칸 인벤토리 슬롯 UI**: `CenturyBoard.tsx`에 `CartInventory` 컴포넌트를 신설했다. 기존엔 보유 자원을 `BundleRow`(색상별 배지 + 숫자)로만 나열해 "10개 중 몇 개 찼는지"를 매번 암산해야 했다. 새 컴포넌트는 `HAND_LIMIT`(10)개의 고정 슬롯을 항상 렌더링하고, `RESOURCE_ORDER`(자원 가치 오름차순) 순서로 큐브를 채워 넣은 뒤 남는 슬롯은 점선 테두리의 흐릿한 빈 칸으로 표시한다. 10개 한도를 순간적으로 초과한 상태(강제 버리기 모달이 뜨기 전, `mustDiscard` 게이트가 걸리는 그 찰나)에도 자원이 화면에서 사라지지 않도록, 11번째 이상은 장미색 테두리+글로우의 "초과 슬롯"으로 10칸 그리드 뒤에 이어서 그린다. 같은 컴포넌트를 슬롯/아이콘 크기만 줄여(`slotClass`/`iconClass` prop) "내 수레" 패널과 상대방 요약 행(`PlayerSummaryRow`) 양쪽에 적용해, 모든 플레이어의 수레가 같은 슬롯 형태로 일관되게 보이도록 했다.

이번 세션도 **UI는 코드 리뷰 + `tsc`/`lint`/`vitest`/`build`만으로 검증했고 실제 브라우저 육안 확인은 하지 않았다** — 특히 상대방 요약 행에 욱여넣은 축소판 10칸 슬롯이 다른 배지들과 줄바꿈 없이 자연스럽게 배치되는지, 덱이 30장으로 줄어든 것이 5인 게임처럼 카드를 많이 소진하는 판에서 체감될 정도로 영향을 주는지는 다음 세션 §3 1번 항목으로 이월한다.

## Phase 16 — Century.md 카드 데이터 최신화와 카드 플레이 취소 기능 (2026-08-08, 같은 날 여덟 번째 세션)

**커밋**: `feat(century): update card deck from Century.md and add card play cancel action`

사용자가 `boardGameRule/Century.md`에 **상인 카드 42장(기본 10장+일반 32장)과 점수 카드 36장의 전체 목록**을 새 부록(§1/§2)으로 직접 추가한 뒤, (1) 그 공식 데이터를 엔진에 정확히 반영하고 (2) 카드 플레이/자원 선택 중 취소 수단을 넣어 달라고 요청했다. Phase 12에서 "공식 카드 원문을 기계가 읽을 수 있는 형태로 구하지 못해 자체 설계 데이터셋을 썼다"고 남겨둔 전제가 이번에 해소됐다.

### 1. 카드 덱 데이터 전면 교체 — 그리고 Phase 15 판단의 정정

`cards.ts`의 `createMerchantDeck()`(32장)과 `createPointDeck()`(36장)을 Century.md 부록의 A/B/C, ①/②/③ 분류 순서 그대로 옮겨 적었다(수치 하나하나를 rulebook과 대조해 확인). 두 함수 모두 이제 자체 설계가 아니라 **룰북의 직접 전사**다.

이 작업 도중 **Phase 15에서 내린 판단 하나가 틀렸다는 게 드러났다.** Phase 15는 "일반 상인 카드 32장 중 `{upgrade, upgrades:2}` 카드 2장이 각 플레이어의 기본 시작 카드(역시 upgrades:2)와 완전히 같은 효과라서 마켓에 중복으로 뜨는 버그"라고 보고, 효과가 시작 카드와 일치하면 걸러내는 `isStarterMerchantEffect()` 필터를 추가해 실제 덱을 32장에서 30장으로 줄였었다. 그런데 이번에 확보한 Century.md 부록은 업그레이드 카드 항목에 이렇게 명시한다: *"향신료 2회 업그레이드 (**기본 카드와 별개로 더미에 1장 추가 포함**)"* — 즉 그 중복은 우연한 데이터 설계 실수가 아니라 **룰북이 의도적으로 넣어둔 카드**였다. 그래서 이번 세션에 `isStarterMerchantEffect`와 그 필터 호출을 완전히 삭제했고, `Century.test.ts`의 관련 회귀 테스트도 "시작 카드와 절대 겹치면 안 된다"에서 "덱 크기(32/36장)와 카드 id 중복 없음, 그리고 `{upgrade, upgrades:2}` 카드가 정확히 1장 존재하는지"를 확인하는 테스트로 바꿔치기했다.

이 반전은 이 프로젝트가 세션 시작 때부터 지켜온 "작업 지시와 룰북이 다르면 룰북 원문을 채택하고 그 판단을 문서에 남긴다"는 원칙([architecture.md §5](./architecture.md#5-디렉토리-구조-및-계층-규칙), Phase 12에서 두 번 실제로 있었던 상황)의 연장이지만, 이번엔 성격이 조금 다르다 — 이전엔 "이미 있는 두 문서가 서로 다른 말을 해서 룰북 쪽을 택한" 것이었다면, 이번은 **"룰북 자체가 이후 세션에서 더 상세해지면서, 그 전에 불완전한 정보로 내린 판단이 사후적으로 틀린 것으로 드러난"** 사례다. 룰북이 살아있는 문서(사용자가 계속 갱신 중)일 때는 "지금 아는 것으로 최선의 판단을 내렸다"는 게 "나중에도 옳다"를 보장하지 않는다는 걸 확인한 셈 — 이후 세션에서도 룰북 갱신이 있으면 과거에 "버그"라고 확정했던 것들을 의심해볼 필요가 있다는 교훈을 남긴다.

### 2. 카드 플레이/자원 선택 취소 기능

기존에 업그레이드/교환/유상(2번째 칸 이후) 상인 카드 획득은 이미 모달(취소/되돌리기/확정 버튼)을 거쳐 진행됐지만, **생산 카드 사용, 무료(1번째 칸) 상인 카드 획득, 점수 카드 완성 이 세 가지는 클릭 한 번에 즉시 `onAction`이 나가 취소할 방법이 없었다** — 사용자가 신고한 "잘못 클릭했을 때 취소할 수단이 없다"는 문제의 실체가 이 세 경로였다. 신규 공용 컴포넌트 `ConfirmActionModal`(제목/설명/자원 미리보기 + 취소/확정 버튼)을 만들어 이 세 경로 모두 "먼저 선택 → 검토 → 취소 또는 확정"으로 통일했다. `startAcquire()`의 "index === 0이면 즉시 dispatch" 분기도 제거해 무료 카드도 항상 `AcquireModal`을 거치도록 했고(`index === 0`일 때는 자원 배치 UI 없이 "무료로 가져옵니다" 안내만 보여주는 축약 뷰로 분기), 강제 버리기(Discard) 모달에는 선택한 자원을 한 번에 되돌리는 "선택 해제" 버튼도 추가했다.

확정 전까지는 로컬 React 상태(`confirmingProduction`/`confirmingClaim`/`acquiring` 등)만 바뀌고 `onAction`이 전혀 호출되지 않으므로 — 즉 네트워크로 브로드캐스트되는 것도 전혀 없으므로 — "취소하면 이전 손패 상태로 되돌아간다"는 요구사항은 "실행을 되돌리는 기능"이 아니라 "확정 전엔 애초에 아무것도 실행되지 않는 구조"로 자연스럽게 충족된다. 이미 이런 스테이지-그리고-확정 패턴을 쓰던 업그레이드/교환/유상 획득 모달과 정확히 같은 모양이라, 엔진(`engine.ts`)에는 새 액션이나 되돌리기 로직을 전혀 추가하지 않았다.

이번 세션도 **UI는 코드 리뷰 + `tsc`/`lint`/`vitest`/`build`만으로 검증했고 실제 브라우저 육안 확인은 하지 않았다** — 특히 이제 두 단계(선택→확정)가 된 생산 카드/무료 획득/점수 카드 흐름이 실제 플레이에서 번거롭게 느껴지지 않는지, 새 공식 카드 데이터로 몇 판 진행했을 때 밸런스가 체감상 자연스러운지는 다음 세션 §3 1번 항목으로 이월한다.

## Phase 17 — 페루도 보라색 베팅 주사위 보드-트랙 UI 개편 (2026-08-08, 같은 날 아홉 번째 세션)

**커밋**: `style(perudo): add purple betting dice on board track and face selector UI`

사용자가 페루도의 베팅 UX를 바꿔 달라고 요청했다: 기존에는 눈금(1~6)을 먼저 고르고 `BidTrack`의 개수 칸을 클릭하면 그 즉시 `raise` 액션이 나가는 "원클릭 즉시 선언" 방식이었는데, 이를 "보드판 트랙 위에 보라색 주사위를 얹어두고, 그 주사위를 옮기고 눈금을 돌려 베팅을 준비한 뒤 확정 버튼을 눌러야 실제로 선언되는" 보드게임 말(piece) 모델로 바꿔 달라는 요청이었다.

### 1. 보라색 베팅 주사위 — 실제 굴리는 다이스와 분리된 전용 컴포넌트

`PerudoBoard.tsx`에 `BettingDie` 컴포넌트를 신설했다. 기존 `DieFace`(상아색/적색, 실제 굴린 값)와 시각적으로 뚜렷이 구분되도록 보라-자홍 그라디언트 + 보라색 글로우로 스타일링했고, 상호작용 가능할 때는 손 이모지(✋) 배지와 호버/클릭 스케일 애니메이션을 얹었다. 이 다이스는 `BidTrack`의 트랙 셀과 **같은 CSS 그리드 셀**(`gridColumn`/`gridRow`를 그 칸의 좌표와 동일하게 지정)에 겹쳐 그려지므로, 절대좌표 계산 없이도 정확히 원하는 칸 위에 "얹힌" 것처럼 보인다.

### 2. "옮기고 → 눈금 돌리고 → 확정" 2단계 흐름

기존엔 눈금 선택(`FacePicker`)과 개수 선택(트랙 클릭)이 곧바로 `raise` 액션 하나로 합쳐졌지만, 이번엔 그 사이에 로컬 전용 "베팅 초안" 상태(`pendingFace`/`pendingQuantity`)를 끼워 넣었다:
- **눈금 변경**: 보라색 주사위를 직접 클릭하면 palafico로 막히지 않은 다음 눈금으로 순환(cycle)한다(`cycleFace()`). 또는 주사위 바로 아래 `FacePicker`(1~6 버튼)로 원하는 눈금을 바로 지정할 수도 있다 — "주사위 클릭 또는 근처 컨트롤러" 요구사항을 동시에 충족.
- **위치 이동**: 트랙 칸을 클릭하면 초안의 개수가 그 칸으로 이동한다(`onCellClick` → `setPendingQuantity`). 더 이상 클릭이 곧바로 액션을 내보내지 않는다.
- **확정**: 새로 추가한 "✅ {눈금} × {개수}개로 베팅 확정" 버튼을 눌러야만 실제로 `onAction({ type: "raise", ... })`이 나간다. 그 전까지는 로컬 상태만 바뀔 뿐 네트워크로 브로드캐스트되는 것이 전혀 없다 — Century의 `ConfirmActionModal`(Phase 16)이 쓰는 "확정 전엔 아무것도 보내지 않는" 패턴과 동일한 안전장치다.

초안 상태는 새 라운드가 시작되거나 다른 누군가 베팅을 올릴 때마다(=`state.currentBid`가 실제로 바뀔 때마다) 다시 초기화해야 하는데, 이를 위해 `revealedRound`(파일에 이미 있던 "prop이 바뀌면 렌더 중에 상태를 조정" 패턴)와 똑같은 기법을 재사용했다: `bidKey`(라운드 번호+현재 베팅 좌석/개수/눈금을 합친 문자열)가 이전에 동기화한 값과 다르면, 렌더 도중 `setPendingFace`/`setPendingQuantity`를 그 시점의 최소 합법 값으로 재설정한다. `useEffect`를 쓰지 않은 이유도 기존 패턴과 같다 — 그러면 첫 렌더에 옛 초안이 한 프레임 노출된다.

내 차례가 아닐 때는 `pendingFace`/`pendingQuantity`를 아예 쓰지 않고, 보라색 주사위가 `state.currentBid.face`/`.quantity`를 그대로 보여주는 읽기 전용 마커로 렌더링된다(`dieInteractive = isMyTurn && iAmAlive`) — 그래서 모든 플레이어가 항상 "지금 실제 베팅이 트랙 어디에 있는지"를 보되, 내 로컬 조작 중인 초안은 남에게 전혀 새어나가지 않는다(어차피 로컬 React 상태라 네트워크에 실리지도 않는다).

### 3. 베팅 위치·눈금 제한 로직 — 새 규칙 없이 기존 엔진 헬퍼 재사용

"이전 베팅보다 낮은 칸으로 이동 불가"와 "일반(2~6)↔페루도(1) 전환 시 최소 개수 공식(룰북 §3: 2배+1 / 절반 올림)"은 전부 `engine.ts`의 기존 `minValidQuantityForFace(prev, face, palafico)` 하나로 이미 구현돼 있었다(Phase 이전 세션에서 트랙 스테퍼 clamp용으로 만들어둔 함수). 이번 세션은 새 판정 로직을 추가하지 않고, 그 함수를 두 곳에서 다시 불렀을 뿐이다: (1) 트랙 셀의 `enabled` 판정(`cell.quantity >= minQty`, `minQty`는 초안 눈금 기준으로 매 렌더 재계산), (2) 눈금을 바꿀 때(`pickFace`) 초안 개수가 새 눈금의 최소치보다 낮으면 끌어올리는 클램프. 팔라피코 라운드에서는 기존 `disabledFaces` 로직(시작 플레이어가 연 눈금 외 전부 비활성화)이 그대로 `FacePicker`와 주사위 순환(`cycleFace`) 양쪽에 적용된다. 극단적인 엔드게임 상황(파코 베팅이 이미 커서 "2배+1" 다음 최소치가 트랙 길이 40칸을 넘는 경우)에는 보라색 주사위를 트랙의 마지막 칸에 시각적으로 고정하고, 확정 버튼에는 실제 개수를 그대로 표시하도록 방어 처리했다(`Math.min(dieQuantity, TRACK_LENGTH)`로 위치만 클램프, 실제 값은 그대로 유지).

`engine.ts`는 이번 세션에 전혀 수정하지 않았다 — 전부 `PerudoBoard.tsx`의 순수 UI 상태와 기존 엔진 헬퍼 재사용. 회귀 없음(273개 테스트 그대로 유지, 애초에 페루도 보드 UI는 다른 6게임과 동일하게 jsdom 미설치로 자동 테스트 대상 밖).

### 4. 육안 확인 — Phase 14 방식 재사용

`PerudoGame.tsx`가 Supabase 로비를 거쳐야만 `PerudoBoard`에 도달해 오프라인 육안 확인이 막히는 문제는 Phase 14와 동일해서, 그때와 같은 방법을 그대로 재사용했다: `src/app/dev-perudo-preview/`에 `PerudoBoard`를 고정 state(4인, 이미 한 번 선언·재선언이 오간 상태)로 직접 렌더링하는 임시 라우트를 만들고, `npm run dev` + Playwright(`chromium.launch()` 스크립트, `npx playwright`가 아니라 npx 캐시에 내려받힌 patchwright 패키지를 `NODE_PATH`로 직접 참조)로 스크린샷과 클릭 시뮬레이션을 돌렸다. 확인한 것: (1) 보라색 다이스가 정확히 `currentBid` 칸 위에 얹히는지, (2) 내 차례가 되면 초안으로 바뀌어 `FacePicker`/확정 버튼이 뜨는지, (3) 주사위를 클릭하면 눈금이 순환하는지(페루도 해골 아이콘 포함), (4) 트랙 칸을 클릭하면 다이스가 그 칸으로 옮겨가고 확정 버튼 문구가 즉시 갱신되는지, (5) 최소 개수보다 낮은 칸(비활성화된 칸)을 강제로 클릭해도 상태가 전혀 바뀌지 않는지, (6) 확정 버튼을 누르면 실제로 `currentBid`가 갱신되고 다음 플레이어에게 턴이 넘어가며 다이스가 읽기 전용으로 바뀌는지 — 전부 스크린샷으로 확인 완료. 확인 후 임시 라우트와 스크립트는 삭제했다(커밋에는 포함되지 않음).

**다만 이 확인도 범위가 좁다** — 8인 확장 레이아웃에서 트랙이 안 잘리는지, 컵 쉐이킹 애니메이션의 실제 타이밍, reveal/gameOver 화면, 팔라피코 배너, 그리고 무엇보다 **실제 Supabase 온라인 로비를 거친 멀티 디바이스 동기화**(특히 내 로컬 베팅 초안이 락스텝 브로드캐스트를 타고 상대방 화면에 새어나가지 않는지 — 설계상 안 나가야 맞지만 실제 네트워크 경로로는 미검증)는 여전히 검증 대상 밖이다.

## Phase 18 — 센추리 UI 전면 개편: 실물 스파이스 로드 보드판 리스킨 (2026-08-08, 같은 날 열 번째 세션)

**커밋**: `style(century): overhaul UI to realistic spice road game board design`

사용자가 센추리 보드 UI를 실물 "센추리: 향신료의 길(Century: Spice Road)" 게임판을 그대로 옮겨놓은 듯한 대규모 레이아웃으로 전면 개편해 달라고 요청했다 — 목재/카펫 질감의 게임 매트, 4색 향신료 그릇, 3D 자원 큐브, 실물 수레(caravan) 보드판, 카드 덱 더미 스택까지 포함하는 폭넓은 요청. 엔진(`engine.ts`)과 카드 데이터(`cards.ts`)는 전혀 건드리지 않고, 순수 UI 컴포넌트(`CenturyBoard.tsx`, `ResourceIcon.tsx`) 레이어에서만 전면 재작성했다 — 기존 핸들러/모달 흐름(취소 가능한 스테이지-확정 패턴, Phase 16)은 그대로 재사용.

### 1. 3D 자원 큐브 — `ResourceCube` 신설
`ResourceIcon.tsx`에 기존 다이아몬드형 젬 아이콘(`ResourceIcon`, 텍스트 옆 배지용으로 계속 사용)과 별개로, 실물 위에 "얹혀 있는" 자원처럼 보여야 하는 자리(수레 슬롯, 향신료 그릇, 상인 카드에 얹힌 자원)에 쓸 `ResourceCube`를 추가했다. 이미지 자산 없이 순수 CSS 그라디언트+box-shadow만으로 광택(왼쪽 위 하이라이트)과 둥근 모서리(`rounded-[6px]`)를 표현 — 이 파일의 기존 관례(외부 이미지 자산 없이 인라인 SVG/CSS만 사용)를 그대로 따랐다.

### 2. 매트/펠트/캐러밴 3단 비주얼 레이어
`CenturyBoard.tsx`에 세 겹의 CSS 텍스처를 신설했다: 최외곽 `MAT`(목재 탁자 느낌, 어두운 갈색 그라디언트+그레인 반복 패턴), 중앙 마켓을 감싸는 `FELT`(어두운 적갈색 펠트/카펫 느낌, 방사형 얼룩 패턴), 내 수레 전용 `CARAVAN_STYLE`(더 밝은 목재 톤). 전부 이미지 자산 없이 `linear-gradient`/`radial-gradient`/`repeating-linear-gradient` 레이어와 다중 `box-shadow`(inset 링 + 외곽 그림자)로만 구현 — 기존 `CARD_FRAME_STYLE`/`CoinStack`이 이미 쓰던 "레이어드 CSS로 실물 질감 흉내"라는 이 파일의 관례를 그대로 확장한 것.

### 3. 향신료 그릇(`SpiceBowl`) — 의도적으로 장식 전용
4색 자원 각각에 대해 목재/아크릴 그릇 모양(`rounded-b-[999px]` 타원 바닥 + 갈색 그라디언트)에 `ResourceCube` 5개를 담아놓은 `SpiceBowl`을 신설해 마켓 펠트 상단에 4개를 나란히 배치했다. **의도적으로 실시간 수량을 반영하지 않는다** — `engine.ts`의 기존 설계 원칙(모듈 doc 참고)이 이미 "공용 향신료 그릇(105개 큐브)은 유한한 은행으로 모델링하지 않는다, 생산/교환은 그릇 잔량에 막히지 않는다"고 명시하고 있으므로, 그릇에 표시할 "실제 잔량"이라는 개념 자체가 엔진에 없다. 그릇은 순수히 "실물 보드처럼 보이게" 하는 장식이고, 이 사실을 컴포넌트 doc 주석에 명시해 다음 세션이 "왜 그릇 숫자가 안 바뀌지?"를 버그로 오인하지 않도록 했다.

### 4. 카드 덱 더미 스택(`DeckStack`)
점수 카드 덱(`state.pointDeck.length`)과 상인 카드 덱(`state.merchantDeck.length`)을 각각 남은 장수와 함께 카드 뒷면이 겹쳐 쌓인 더미로 시각화하는 `DeckStack`을 신설해 각 마켓 행 오른쪽에 배치했다. `CARD_FRAME_STYLE`과 같은 양피지 그라디언트를 재사용해 마켓에 펼쳐진 카드들과 같은 "실물 카드" 재질로 통일했고, 덱이 0장이 되면 스택 대신 점선 테두리의 "소진" 플레이스홀더로 전환된다.

### 5. 수레(Caravan) 보드판 재설계
기존 `CartInventory`(10칸 사각 슬롯)를 실물 수레 보드판처럼 보이도록 재작업했다: 정사각형 대신 오목하게 파인 원형 "우물(well)" 슬롯(방사형 그라디언트+`inset` 그림자로 파인 느낌)에 `ResourceCube`가 얹혀 있는 형태로, 메인 수레는 `grid-cols-5`(5×2, 실물 캐러밴 보드 배치) 고정 그리드, 상대방 요약 행은 좁은 공간에 맞춰 `flex-wrap` 축소판으로 갈리도록 `compact` prop 하나로 두 모드를 갈랐다(이전엔 `slotClass`/`iconClass`만 다르고 레이아웃 자체는 같은 `flex-wrap`이었다).

손패는 카드가 부채꼴로 펼쳐지도록 각 카드에 인라인 `transform: rotate()/translateY()`를 인덱스 기반으로 계산해 적용했고(중앙에서 멀수록 회전각·아래쪽 처짐이 커짐), 겹치는 정도는 음수 `marginLeft`로 냈다. 사용한 카드(버린 카드 더미)는 같은 기법으로 더 크게 겹치고 회색조(`grayscale`)를 유지해 "아직 못 쓰는 카드"라는 상태를 계속 구분되게 하면서, 부채꼴이 아니라 "쌓아 올린 더미"처럼 보이도록 회전각을 더 작고 불규칙하게 줬다.

### 6. 실제 렌더링 스크린샷 검증 — 그리고 발견된 버그 1건
HANDOFF.md가 반복해서 강조해온 "레이아웃 버그는 코드 리뷰만으로 고쳤다고 단정하지 말 것" 원칙에 따라, 이번엔 실제로 Phase 14/17과 같은 방식(임시 `dev-century-preview` 라우트 + 고정 state + `npx playwright screenshot`)으로 육안 검증까지 마쳤다. 이 과정에서 실제 버그 1건을 발견해 고쳤다 — 금화/은화 공급량이 완전히 같은데도 금화 코인 스택만 짧아 보이는 문제(`z-index` 경합, 근본 원인·해결법은 [troubleshooting.md #10](./troubleshooting.md#10-센추리-금화은화-공급량이-똑같은데도-금화-코인-스택만-짧게-보임) 참고). 그 외에 확인한 것: 점수/상인 마켓 5장·6장이 좁은(420px) 화면과 넓은(900px) 화면 모두에서 잘리지 않고 반응형으로 배치됨, 업그레이드/교환/획득/생산·점수카드 확정 모달 4종이 전부 새 목재/양피지 톤으로 자연스럽게 재스킨됨(클릭 시뮬레이션으로 실제로 열어서 확인), 손패 부채꼴/버린 카드 더미가 겹침 없이 읽힘, 상대방 요약 행의 축소 수레 슬롯이 다른 배지와 줄바꿈 없이 배치됨. 검증에 쓴 임시 라우트·스크립트는 확인 후 전부 삭제했고(커밋에 포함되지 않음), 화면 검증용으로만 잠시 설치했던 `playwright` 패키지도 `--no-save`로 설치해 `package.json`에는 흔적을 남기지 않았다.

**여전히 검증 범위 밖인 것**: 실제 Supabase 온라인 로비를 거친 멀티 디바이스 락스텝 동기화(다른 좌석이 카드를 획득/사용할 때 내 화면에도 새 마켓/수레 비주얼이 정확히 반영되는지), 5인 게임처럼 자원 개수가 많아 손패 부채꼴이 화면 폭을 넘기는 극단적 케이스, 실제 태블릿/저해상도 기기에서의 터치 조작감.

## Phase 19 — 그리드 포커 방 설정에 커스텀 제한시간(초) 옵션 추가 (2026-08-08, 같은 날 열한 번째 세션)

**커밋**: `feat(grid-poker): add customizable timer duration options for room settings`

사용자가 그리드 포커의 배치/제출 단계 카운트다운 제한시간을 방장이 방 생성 시 직접 고를 수 있게 해 달라고 요청했다. 조사해 보니 그리드 포커에는 애초에 "시간 제한 모드/없음 모드" 선택지 자체가 없었다 — `GridPokerBoard.tsx`에 `PLACING_SECONDS = 20`, `SUBMITTING_SECONDS = 15`로 하드코딩된 카운트다운이 모든 방에서 항상 강제로 돌고 있었다(끌 수 없음). 그래서 이번 세션은 순수 리스킨이 아니라 실제 새 기능 신설이었다.

### 1. 타이머 설정을 `GridPokerState` 자체에 편입 — 새 동기화 채널을 만들지 않기 위해
`useCountdown.ts`의 기존 설계 원칙(카운트다운 자체는 클라이언트 로컬 UX일 뿐, 만료 시 오직 "내 좌석" 액션만 낸다 — 합의 대상이 아님)은 그대로 두되, **몇 초짜리 카운트다운인지**는 모든 클라이언트가 반드시 똑같은 값을 봐야 한다. 이를 위해 별도의 룸-설정 브로드캐스트 채널을 새로 만드는 대신, `engine.ts`에 `TimerSettings`(`mode: "limited" | "unlimited"`, `placingSeconds`, `submittingSeconds`) 타입을 추가하고 `GridPokerState.timerSettings` 필드로 편입시켰다. `startGame(playerCount, timerSettings)`가 이 값을 상태에 박아 넣으면, 리듀서의 모든 브랜치가 이미 `{...state, ...}` 스프레드로 상태를 통째로 들고 다니므로 별도 전파 로직 없이 게임 끝까지 그대로 유지된다 — Century의 카드 데이터가 `state`에 편입되어 있는 것과 같은 패턴.

### 2. 방장 → `game-start` 브로드캐스트 페이로드로 전파
기존에 `playerCountRef`가 하던 것과 똑같은 방식으로 `timerSettingsRef`를 신설했다: 방장이 "방 만들기" 폼에서 고른 값을 `enterRoom()` 시점에 ref에 스냅샷하고, `sendGameStart()`가 `game-start` 브로드캐스트 payload에 `timerSettings`를 실어 보낸다. 수신 측(방장 자신을 포함 — 채널이 `broadcast: { self: true }`라 방장도 자기 브로드캐스트를 받는다)은 `startGame(playerCount, timerSettings)`을 그 값으로 호출하므로, 모든 참가자가 정확히 같은 `GridPokerState.timerSettings`를 갖고 게임을 시작한다. 재시작(`다시하기`)도 같은 ref를 재사용해 같은 설정을 유지한다.

### 3. 방 생성 폼 UI — 프리셋 버튼 + 수기 입력
"방 만들기" 폼(`intent === "create"`, 기존 인원 수 스테퍼 바로 아래)에 새 설정 블록을 추가했다:
- **모드 토글**: "⏱️ 시간 제한 모드" / "⏳ 시간 제한 없음" 두 버튼 중 하나 선택. 없음 모드를 고르면 아래 초 설정 UI 자체가 사라진다(카운트다운이 아예 존재하지 않는다는 걸 명확히 전달).
- **카드 배치 제한시간**(그리드 포커의 "placing" 단계 — 공용 카드 한 장을 매 라운드 자기 보드에 배치하는 단계): 20/30/40/60초 프리셋 + "직접 입력"(숫자 입력, 5~300초로 clamp), 기본값 40초.
- **라인 제출(마지막 배팅) 제한시간**(그리드 포커의 "submitting" 단계 — 12개 라인 중 하나를 블라인드로 고르는 단계): 10/15/20/30초 프리셋 + "직접 입력", 기본값 30초.

두 필드 다 재사용 가능한 `TimerSecondsField` 컴포넌트 하나로 구현(선택된 프리셋/직접입력 상태를 pill 버튼 스타일로 표시). 사용자 요청 원문은 "1차 덱빌딩 시간"/"마지막 배팅 시간"이라는 라벨을 썼는데, 그리드 포커에는 덱빌딩/배팅 개념 자체가 없다(다른 게임 스펙에서 재사용된 표현으로 보임) — 실제 UI 라벨은 그리드 포커의 진짜 두 단계 이름(카드 배치/라인 제출)에 맞춰 붙이고, 요청이 명시한 옵션 목록·기본값(20/30/40/60·40초, 10/15/20/30·30초)은 그대로 따랐다.

### 4. `GridPokerBoard.tsx` — 하드코딩 상수 제거, `state.timerSettings` 참조로 교체
`PLACING_SECONDS`/`SUBMITTING_SECONDS` 모듈 상수를 삭제하고 `state.timerSettings.placingSeconds`/`.submittingSeconds`를 직접 읽도록 바꿨다. `mode === "unlimited"`일 때는 `useCountdown`의 `active`를 항상 `false`로 고정해 틱/자동 액션을 완전히 끄고, `CountdownBar`도 렌더링하지 않는다(긴급 상태 사운드 트리거 `isUrgent` 계산도 같은 조건으로 게이팅해, 없음 모드에서 초기 `timeLeft`가 우연히 낮은 값이어도 절대 울리지 않게 했다).

### 5. 테스트 + 육안 검증
`GridPoker.test.ts`에 `startGame`이 기본값(40/30/limited)을 채우는지, 커스텀 설정(없음 모드 포함)이 액션을 여러 번 거쳐도 리듀서 전체에서 그대로 보존되는지 2개 추가(273→275개, 전부 통과). 방 생성 폼 자체는 다른 게임의 `<Game>Board.tsx`처럼 jsdom 미설치로 자동 테스트 대상 밖이라, Phase 14/17/18과 같은 방식(임시 `dev-gridpoker-preview` 라우트 + `npx playwright screenshot`, 확인 후 라우트·스크린샷·`playwright` 패키지 전부 삭제해 커밋에 흔적 없음)으로 육안 검증했다: 기본값(40초/30초)이 정확히 반영된 초기 렌더, "시간 제한 없음" 선택 시 초 설정 UI가 깔끔히 사라지는지, "직접 입력" 클릭 시 이전 프리셋 값을 그대로 이어받은 숫자 입력창이 뜨는지 — 셋 다 레이아웃 깨짐 없이 확인됨. **온라인 방을 실제로 열어 방장이 고른 초 값이 다른 기기 카운트다운 시작값에도 그대로 반영되는지는 이번 세션에도 미검증**(Supabase 로비를 거쳐야 하는 다른 항목들과 같은 사각지대).

## Phase 20 — 틀린 그림 찾기(Spot the Difference) 신규 게임 (2026-08-08)

**커밋**: `c854454` — `feat(spot-difference): add spot the difference game engine, photo upload mode, team total scoring, and ui`

사용자가 `boardGameRule/spotTheDifference.md` 룰북을 기반으로 신규 게임 하나를 통째로 추가해 달라고 요청했다(엔진→UI→온라인 동기화→단위 테스트→커밋/푸시/배포까지 요청 자체에 명시). 룰북의 핵심은 "번갈아 맞히기"가 아니라 "팀 전체가 동시에 찾고 총합으로 승부"(§3-C 실시간 총합 경쟁)라는 점 — 이 프로젝트에 팀 개념이 있는 게임이 없었기 때문에 좌석-팀 배정을 새로 설계해야 했다.

### 1. 팀 합산 정산을 어떻게 결정론적으로 만들 것인가
다른 7게임은 전부 "내 턴에만 액션을 낸다"는 전제가 있어 액션 순서가 곧 게임 진행이지만, 이 게임은 팀원 누구나 아무 때나 클릭할 수 있다. 그래서 좌석(seat)마다 팀을 고정 배정(`defaultTeamAssignment` — 짝수 좌석 A/홀수 좌석 B)하고, 클릭 액션의 `seat`으로 어느 팀에 점수를 더할지 결정하는 구조로 풀었다. 점수는 좌석별이 아니라 `stages[i].foundBy: Record<spotId, TeamId>`에 팀 단위로만 쌓이므로 "누가 찾았는가"가 아니라 "어느 팀이 찾았는가"만 상태에 남는다 — 개인별 기여도를 추적하지 않는 것은 룰북이 애초에 요구하지 않는 정보이기도 하고, 이 프로젝트의 파생 상태 금지 원칙(불필요한 상태를 만들지 않기)과도 맞는다.

### 2. 오답 페널티 락을 리듀서 안에서 결정론적으로 처리하기
"틀린 곳 클릭 시 2초 잠금"은 명백히 시간 기반 로직인데, 이 프로젝트의 모든 엔진은 `Date.now()`를 리듀서 안에서 직접 읽지 않는다(모든 클라이언트가 액션을 재생해 동일한 상태에 도달해야 하므로, 리듀서가 실행되는 "지금 이 순간의 벽시계"에 의존하면 클라이언트마다 다른 결과가 나올 수 있다). 다른 게임들이 RNG 시드를 액션이 아니라 `startGame` 인자로 한 번만 공유하는 것과 비슷하게, 여기서는 클릭 액션 자체에 클릭한 클라이언트가 캡처한 타임스탬프(`atMs`)를 실어 보낸다. 오답이면 `penalties[seat] = atMs + 2000`을 기록하고, 이후 들어오는 클릭의 `atMs`가 그보다 작으면 무시한다 — 어느 클라이언트가 재생하든 같은 `atMs` 값들을 같은 순서로 처리하므로 결과가 항상 같다.

### 3. 기본 스테이지: 외부 이미지 없이 "그림 자체를 데이터로"
이 프로젝트는 처음부터 외부 이미지 자산을 쓰지 않는 관례가 있다(PerudoFaceIcon.tsx, Century의 ResourceIcon.tsx 등 전부 순수 인라인 SVG). 틀린 그림 찾기의 "그림"도 같은 방식을 택했다: `scenes.ts`에 도형 목록(원/사각형/삼각형/별 등, 0~100 좌표계)으로 씬을 정의하고, 정확히 5개의 "diff"(색상/위치/크기/회전 변경 또는 삭제)를 함께 선언한다. 여기서 중요한 설계 판단은 **diff가 참조하는 도형의 원래 좌표를 그대로 정답 좌표(`Spot`)로 재사용**한 것(`computeSpotsForScene`) — 그림 좌표와 정답 좌표를 별도 리스트로 관리했다면 둘이 어긋나는 버그가 날 수 있었는데, 애초에 하나의 소스에서만 나오게 만들어 그 가능성 자체를 없앴다.

### 4. 사진 업로드 모드: "정답을 전송하지 않고 시드에서 파생"
룰북 §3-D("사진 업로드 → 자동 변형 생성")를 실제 이미지 인식/객체 탐지 없이 구현해야 했다. 결정: 어디를(좌표) 어떻게(색조 회전/반전/모자이크/블러/좌우반전/틴트/흑백 중 하나, 강도) 바꿀지는 실제 사진 픽셀과 무관하게 공유 시드만으로 결정론적으로 생성한다(`generatePhotoDiffSpots(seed, count)` — 최소 간격을 두고 겹치지 않는 원형 영역을 뽑는 순수 함수, vitest로 결정론/좌표 범위/최소 간격 전부 검증). 실제 사진 데이터(`imageDataUrl`)만 `game-start` 브로드캐스트로 전송하면, 모든 클라이언트가 "이미지 + 같은 시드"에서 똑같은 좌표와 똑같은 효과를 계산하므로 좌표 리스트 자체를 따로 보낼 필요가 없다 — 이 프로젝트의 "필요한 건 시드뿐, 결과는 각자 계산" 원칙을 이미지에도 그대로 적용한 것. 실제 픽셀 변형은 순수 함수가 아니라 `PhotoStageCanvas.tsx`가 Canvas 2D API(`clip` + `filter` + 오프스크린 캔버스를 이용한 모자이크)로 매 렌더링 시점에 적용한다.

사진은 브로드캐스트 페이로드 크기 제한을 고려해 클라이언트에서 먼저 리사이즈(최대 900px)+JPEG 압축(최대 약 170KB, 품질을 0.8에서부터 0.25까지 내려가며 재시도)한 뒤에만 전송한다. 그래도 아주 복잡한 사진은 한도를 넘을 수 있음 — 실기기 검증 전까지는 알려진 한계로 남겨둠(§3 참고).

### 5. UI/연출
`SpotDifferenceBoard.tsx`가 팀 A/B 합산 스코어보드, 남은 차이 개수, 남은 시간(로컬 카운트다운 — 다른 게임의 `useCountdown.ts`와 같은 관례로 만료 시 `timeUp` 액션 1회만 발신, 리듀서 쪽에서 이미 게임오버면 무시하므로 여러 클라이언트가 동시에 쏴도 안전), 오답 잠금 표시, 팀별 힌트(2회, 사용한 팀에게만 파동 애니메이션)를 전부 담당한다. 정답 마킹 팝/힌트 파동 애니메이션은 다른 게임들의 관례대로 `globals.css`에 전역 키프레임(`spot-diff-pop`, `spot-diff-wiggle`)으로 등록하고 Tailwind의 `animate-[keyframe_duration_ease]` 화살괄호 문법으로 참조했다(styled-jsx는 이 저장소에서 쓰지 않는 관례라 처음엔 그렇게 짰다가 기존 관례를 발견하고 globals.css로 옮김). SFX는 `soundEngine.ts`에 `playCorrectDing`/`playWrongBuzz` 두 개를 추가(기존 Web Audio API 합성 방식 그대로, 외부 오디오 파일 없음).

### 6. 온라인 방 + 테스트 + 검증
`SpotDifferenceGame.tsx`는 다른 7게임과 동일한 락스텝 로비 패턴(시드 하나 브로드캐스트, `state-request`/`state-sync` 재접속, deviceId 사전순 좌석 충돌 자가치유)을 그대로 이식했고, 방 생성 폼에 인원(2~8명)·모드(기본/사진)·스테이지 수 또는 차이 개수·제한시간 선택지를 추가했다. 엔진 테스트 26개를 신설(275→301개, 전부 통과): 클릭 좌표 판정(중앙/허용반경 경계/반경 밖/이미 발견한 곳), 팀 합산과 세 가지 승리조건(시간종료 승/전원발견 즉시종료/동점 공동승리), 게임종료 후 액션 무시, 오답 페널티 락(걸림/유지/해제 후 재시도/다른 좌석엔 영향 없음), 힌트, 사진 diff 생성기의 결정론성·좌표 범위·최소 간격. UI는 Phase 14/17/18/19와 같은 방식(임시 `dev-spot-preview` 라우트 + `npx playwright screenshot`, 확인 후 라우트·스크린샷·`playwright` 패키지 전부 삭제)으로 육안 검증했다: 기본 진행 화면(듀얼 씬 렌더링), 정답 마킹 팝 애니메이션, 힌트 파동, 게임종료 스코어 화면, 그리고 실제 `/games/spot-difference` 방 생성 폼(기본/사진 모드 전환, 실제 이미지 파일 업로드 → 압축 → 미리보기까지) — 콘솔 에러 없음, 레이아웃 깨짐 없음. **실제 Supabase 온라인 로비를 거친 멀티 디바이스 동기화, 특히 사진 업로드 모드의 실기기 페이로드 한도는 이번 세션에도 미검증**으로 남아 있음(다른 게임들과 같은 사각지대, §3 참고).

### 0. 이 세션 자체의 특이사항 — 작업 트리가 두 번 되돌아간 뒤 재작업
이 세션 도중 작업 트리에 적용한 편집이 다음 턴에서 원본으로 조용히 되돌아가 있는 현상을 두 차례 겪었다(§2의 "세션 시작 시 git status를 항상 먼저 확인할 것" 항목 및 이 문서 이전 기록 참고). 원인은 끝내 특정하지 못했지만, `git log`에 실제로 이 저장소 밖의 다른 세션이 만든 새 커밋(틀린 그림 찾기 Phase 20)이 존재한 것으로 보아 **같은 워킹 디렉터리를 공유하는 여러 세션이 동시에 떠 있었을 가능성**이 유력하다. 사용자에게 상황을 있는 그대로 보고한 뒤, 사용자 확인 하에 처음부터 다시 작업해 이번에는 매 파일 편집 직후 `git diff --stat`으로 즉시 디스크 반영 여부를 확인하며 진행했고, 최종적으로 아래 내용이 전부 커밋·검증까지 완료됐다.

### 1. 차등 페널티 수식 — 룰북 §4 그대로
- **"페루도!" (dudo)**: 실제 개수 < 선언 개수(의심 성공)면 직전 선언자가 `선언 개수 − 실제 개수`개를 잃는다. 실제 개수 ≥ 선언 개수(의심 실패)면 의심한 사람이 `실제 개수 − 선언 개수 + 1`개를 잃는다(정확히 맞는 선언을 의심해도 최소 1개는 잃는다는 뜻).
- **"맞아!" (calza)**: 정확히 일치하면 기존과 동일하게 주사위 1개를 회복(최대 5개 cap). 틀리면 `|실제 개수 − 선언 개수|`개(절댓값 오차)를 한 번에 잃는다.
- `engine.ts`의 `RoundResolution.diceDelta` 타입을 `1 | -1`에서 `number`로 넓혀 손실 폭을 그대로 실어 날랐다. `applyResolution`의 탈락 판정(`justEliminated`)도 `delta === -1` 대신 `delta < 0`으로 일반화했다 — 여러 개를 한 번에 잃어도 0개로 클램프되면 탈락으로 정확히 잡힌다.
- `boardGameRule/Perudo.md` §4 본문 + 가이드 표, `RulebookModal.tsx`도 룰북 원문의 공식과 예시(5개 선언·실제 2개→3개 상실, 4개 선언·실제 6개→3개 상실, 4개라 외쳤으나 실제 7개→3개 상실)를 그대로 반영해 갱신했다.
- `Perudo.test.ts`: 기존 dudo 테스트 2개가 "차이 1"인 우연한 픽스처라 결과값만 갱신하면 통과했지만, 차등 폭이 1보다 큰 경우를 검증하는 게 이 변경의 핵심이라 룰북 예시를 그대로 옮긴 신규 테스트 3개(dudo 1개, calza 2개)와 손실 폭이 보유 주사위 수를 넘을 때 0개로 클램프되는 경계 테스트 1개를 추가했다(42개 전부 통과).

### 2. 3D 입체 주사위 — `DiceCube` 공유 프리미티브
플랫 그라디언트+inset-shadow로 입체감을 흉내 내던 기존 방식 대신, `transform-style: preserve-3d`로 실제 앞면 + 윗면 베벨 + 옆면 베벨 3면을 세운 `DiceCube` 컴포넌트 하나를 새로 만들고 `DieFace`(내 주사위/공개된 주사위), `DieBack`(컵 속 상대방 주사위), `BettingDie`(보드 트랙 위 보라색 베팅 주사위)가 전부 이 컴포넌트를 색상(`CubeColorway`)만 바꿔 공유하도록 다시 짰다.
- 깊이(`depth`)는 정육면체 전체 깊이가 아니라 얼굴 크기의 약 28%로 얕게 잡았다 — 실제 정육면체 깊이를 그대로 쓰면 회전 후 화면 차지 면적이 크게 부풀어 이 프로젝트가 빽빽하게 배치하는 주사위 행(플레이어당 최대 5개 손패, 8인 로스터 스트립)이 깨질 위험이 있었기 때문(§3에 남은 미검증 항목 참고).
- 페루도(1) 해골/마스크 마크(`PerudoFaceIcon`)는 이제 이 입체 큐브의 앞면 위에 얹혀 "각인된" 느낌이 나도록 배치했다.
- 리빌 화면의 결과 문구도 하드코딩된 "1개"에서 `Math.abs(res.diceDelta)`로 실제 손실 폭을 보여주도록 고쳤다.

## Phase 22 — 페루도 실제 WebGL 3D 주사위(Three.js/R3F/Rapier) + 게임 카드 실사 이미지 (2026-08-08, 같은 날 열네 번째 세션)

두 개의 별개 요청이 한 세션에 이어졌다. 먼저 사용자가 페루도의 CSS 입체 주사위(Phase 21)를 실제 Three.js/React Three Fiber/물리 엔진 기반 3D로 완전히 대체해 달라고 요청했고, 진행 도중(3D 주사위가 아직 미완성일 때) 로컬 `image/` 폴더의 실사 이미지로 게임 카드 에셋을 교체해 달라는 요청이 끼어들었다 — 사용자에게 순서를 물어 3D 주사위를 먼저 마무리한 뒤 이미지 작업을 진행하기로 확인받았다.

### 1. 왜 Cannon 대신 Rapier인가
사용자는 "Cannon.js"를 예시로 들었지만, `@react-three/cannon`은 `@react-three/fiber@8`까지만 지원한다(`npm view` peerDependencies로 사전 확인) — 이 프로젝트는 React 19 + `@react-three/fiber@9`라 호환 불가. `@react-three/rapier`는 `react ^19`/`fiber ^9.0.4`를 정식 지원해 대신 채택했다. `three-stdlib`도 새 직접 의존성으로 추가했다(아래 3번 참고).

### 2. 물리는 연출일 뿐, 결과는 항상 엔진 값에 강제 정렬
이 프로젝트의 온라인 대전은 락스텝(시드+액션 재생)이라 물리 시뮬레이션 결과가 클라이언트마다 미세하게 달라질 수 있다. 그래서 `DiceCup3D`는 굴림을 시작하기 전에 이미 `engine.ts`가 정한 최종 눈을 알고 있고, 물리는 정해진 시간(≈0.95초) 동안 순전히 시각적 혼돈만 연출한 뒤, 남은 ≈0.32초 동안 매 프레임 `rigidBody.setTranslation/setRotation`으로 스냅 지점(`faceMath.ts`의 `quaternionForFaceUp`)까지 수동으로 보간해 강제로 착지시키고 그대로 잠근다(`lockTranslations/lockRotations`). 결과값 계산에는 물리 시뮬레이션이 전혀 관여하지 않는다 — 시각적 굴림과 실제 결과 계산이 완전히 분리된 구조.

### 3. 진짜 6면 독립 텍스처가 필요해서 drei의 `RoundedBox`를 버림
`@react-three/drei`의 `<RoundedBox>`는 2D 라운드 사각형을 압출(extrude)해 만들어 머티리얼 슬롯이 앞+뒤 캡 1개, 옆면 전체 1개 — 총 2개뿐이다(주사위처럼 굴러서 어느 면이든 위로 올 수 있는 오브젝트에는 근본적으로 안 맞음). 대신 `three-stdlib`의 `RoundedBoxGeometry`(진짜 `BoxGeometry`를 상속해 모서리만 둥글리는 방식이라 6면 독립 머티리얼 그룹을 그대로 유지)를 직접 사용했다. `three-stdlib`를 `package.json`에 새 직접 의존성으로 추가.

### 4. 8인 테이블 성능 — 공유 캔버스 하나로 수십 개 주사위
WebGL 컨텍스트는 브라우저당 보통 8~16개로 제한되는데, 8인 로스터(최대 5개씩)+내 손패+베팅 다이 등 실시간으로 수십 개의 주사위가 동시에 화면에 있을 수 있다. `DiceStage.tsx`가 drei의 `<View>`를 이용해 캔버스 하나(`DiceStageRoot`, `position:fixed` 풀스크린 오버레이, `pointer-events:none`)만 마운트하고, 개별 주사위(`DiceView`)는 그 캔버스로 자기 화면 사각형만 터널링하는 작은 트래킹 `<div>`가 된다 — 기존 DOM 플렉스랩 레이아웃(손패 줄바꿈, 로스터 그리드)은 그대로 유지되면서 실제로는 GL 컨텍스트 1개만 쓴다. 물리 굴림 연출(`DiceCup3D`)만 예외적으로 자기 전용 캔버스를 하나 더 쓴다(동시에 화면에 하나뿐이라 문제 없음).

### 5. CSS 폴백을 지우지 않고 그대로 보존
기존 CSS `DiceCube`/`DieFace`/`DieBack`/`BettingDie`/`ShakingCup`을 삭제하지 않고 `*Css` 접미사로 남긴 뒤, `DieFace`/`DieBack`/`BettingDie`가 `active3D` 플래그로 3D/CSS를 디스패치하도록 만들었다. `active3D`는 `useWebglSupport()`(SSR 중엔 `false`, 하이드레이션 직후 실제 WebGL 지원 여부로 갱신)와 사용자가 직접 누르는 "3D 끄기" 토글의 AND — SSR, WebGL 미지원 브라우저, 저사양 기기 셋 다에서 안전하게 기존 검증된 CSS 렌더러로 떨어진다. `useWebglSupport`는 `useEffect`+`setState` 대신 `useSyncExternalStore`로 구현했는데, 이 프로젝트의 엄격한 react-hooks lint 규칙(effect 안 동기 setState 금지)에 걸리지 않으면서 SSR 스냅샷을 자연스럽게 처리할 수 있어서다.

### 6. 실제로 스크린샷으로 잡아낸 버그 두 개
- **"닫힌" 컵인데 속이 다 보임**: 처음에 컵을 열린 실린더(`openEnded: true`)로 만들었더니, 카메라가 위에서 내려다보는 각도라 닫혀 있어야 할 컵 안의 주사위가 그대로 보였다. 임시 프리뷰 라우트 스크린샷으로 발견해 닫힌(양 끝 캡 있는) 실린더로 고쳤다 — "컵을 들어올려야 보인다"는 토글 기능 자체가 무의미해질 뻔한 버그.
- **다른 눈의 주사위 옆면에 페루도 해골이 걸쳐 보임**: 3/4 각도 카메라에서는 실제 정육면체처럼 두 면이 동시에 보이는데, 물리적으로 모든 주사위가 항상 6면을 다 갖고 있어(1의 해골 면 포함) 어떤 값이든 카메라 각도에 따라 우연히 해골 면이 옆에 살짝 걸릴 수 있었다. 순간적으로 조커 개수를 착각하게 만들 수 있는 문제라, 정적 타일(`DiceView`)의 카메라를 거의 수직으로 낮춰 위쪽 한 면만 뚜렷하게 읽히도록 고쳤다(물리 굴림 연출용 `DiceCup3D` 카메라는 원래도 좌우 대칭이라 이 문제가 없어 그대로 둠).

### 7. 검증

## Phase 23 — 게임 카드 이미지 잘림 수정(object-contain) + 대시보드 그리드 레이아웃 개편 (2026-08-08, 같은 날 열다섯 번째 세션)

**커밋**: `style(hub): fix board game image cropping with object-fit contain and improve grid layout`

Phase 22 §9에 남겨둔 "박스 표지 사진이 가로로 넓은 썸네일 슬롯에서 `object-cover`로 위아래가 잘린다"는 후속 항목을 사용자가 직접 지적하며 수정을 요청했다. 실측해 보니 5장 전부 세로형(대략 3:4, 예: 스플렌더 415×600, 페루도 300×411)인데 카드 썸네일 슬롯은 `h-28/h-32`(가로로 넓은 랜드스케이프) 고정 높이였어서, `object-cover`가 폭에 맞춰 확대한 뒤 위아래를 크게 잘라내고 있었다.

### 1. `object-cover` → `object-contain`이 기본값
`GameThumbnail.tsx`의 기본 `imageClassName`을 `object-cover`에서 `object-contain`으로 바꿨다 — 어떤 종횡비의 사진이 추가되더라도 잘리지 않는 게 우선이라는 판단(Phase 22 §9가 이미 "다른 종횡비 사진이 추가되면 재확인 필요"라고 예견한 대로, 근본 해결은 크롭 방향이 아니라 전체 노출 방향이 맞다고 결론). 개별 호출부에서 `imageClassName="object-contain p-4"`처럼 패딩을 얹어 이미지가 카드 가장자리에 바로 붙지 않고, 뒤에 깔린 그라디언트 배경이 자연스러운 레터박스 여백으로 보이게 했다.
- **주의**: `next/image`의 `fill`은 부모의 **패딩 박스**가 아니라 콘텐츠+패딩을 포함한 영역 전체에 `position:absolute; inset:0`으로 앉는다 — 컨테이너 `<div>`에 `p-2`를 줘도 이미지 자체는 줄어들지 않는다. 그래서 여백은 항상 컨테이너가 아니라 `imageClassName`에 실은 `p-*`로 준다(이미지 자체의 패딩).
2곳(게임 준비중 페이지 썸네일, 상세 페이지 헤더 아이콘)도 같은 패턴으로 `imageClassName="object-contain p-1~p-2"` + 컨테이너 `bg-white/5`를 추가해 레터박스가 화면 배경에 그냥 묻히지 않고 옅은 사각 배경 위에 놓이도록 통일했다.

### 2. `GameCard` 썸네일 슬롯을 세로형 `aspect-[4/5]`로
기존 고정 높이(`h-28 sm:h-32`, 폭 전체) 대신 `aspect-[4/5]`(가로4:세로5, 박스 표지 종횡비에 더 가까움)로 바꿔 실사 이미지가 레터박스를 최소화하며 크게 보이게 했다. 이모지+그라디언트 카드(21종 중 16종)도 같은 비율 박스를 쓰는데, 큰 정사각형에 가까운 색면에 이모지가 중앙에 뜨는 모양이라 오히려 더 카드 게임 박스처럼 보이는 부수 효과가 있었다(스크린샷으로 확인). 텍스트 영역 패딩/간격(`p-4→p-4 sm:p-5`, `gap-2→gap-2.5`, 배지 `px-2 py-0.5→px-2.5 py-1`)도 같이 넉넉하게 키워 제목/인원수/시간이 더 잘 읽히게 했다.

### 3. 그리드를 6열까지 늘어나던 것에서 최대 4열로 캡
기존 `grid-cols-2 sm:3 md:4 lg:5 xl:6`은 화면이 넓어질수록 카드가 계속 작아지는 구조라, 세로형으로 커진 썸네일과 맞물리면 아주 넓은 화면에서 6열 x (세로로 긴 카드)가 과도하게 촘촘해 보였다. `grid-cols-2 sm:gap-5 lg:grid-cols-3 xl:grid-cols-4`로 바꿔 데스크톱(`xl`, 1280px+)에서도 최대 4열로 고정 — 모바일/태블릿은 2열 그대로, 데스크톱만 3~4열로 확장되는 모양이 사용자가 예시로 든 배치(데스크톱 3~4열·태블릿 2열·모바일 1~2열)에 부합한다고 판단했다. (참고: `xs:` 같은 커스텀 브레이크포인트는 이 프로젝트 Tailwind 설정에 정의돼 있지 않아 실제로는 아무 효과가 없다는 걸 먼저 확인하고, 실재하는 기본 브레이크포인트(`sm/md/lg/xl`)만 썼다.)

### 4. 검증

- **가짜 버그 하나 만남**: 처음 찍은 데스크톱 **풀페이지** 스크린샷에서 두 번째 줄부터 카드 제목/설명 텍스트가 통째로 사라지고 빈 흰 여백만 남는 것처럼 보여서 실제 레이아웃 버그로 의심했다. `page.evaluate`로 그리드 자식 요소의 실제 `getBoundingClientRect()`/`textContent`를 직접 찍어보니 모든 카드의 높이(481.25px)와 텍스트가 정상이었고, 뷰포트 크기 그대로(비-full-page) 스크롤해 캡처한 스크린샷에서도 전부 정상 렌더링됨을 확인 — Playwright CLI의 `--full-page` 스크린샷이 `position:fixed` 플로팅 버튼(우측 하단 🎲 버튼)과 얽혀 만들어낸 캡처 자체의 스티칭 아티팩트였다(실제 DOM/CSS 문제 아님). **교훈**: 이 프로젝트가 이미 troubleshooting.md에 남긴 "시각적 버그는 코드 리뷰만으로 판단하지 말 것" 원칙의 반대 방향 함정도 있다는 것 — 스크린샷 한 장도 무조건 진실은 아니며, 의심스러우면 `getBoundingClientRect`/`textContent` 같은 실제 DOM 값으로 교차 확인해야 한다.

## Phase 24 — 대시보드 기본 정렬: 플레이 가능한 게임 우선 노출 (2026-08-09)

**커밋**: `feat(hub): sort coming-soon board games to the end of default list`

대시보드가 `GAME_REGISTRY` 등록 순서를 그대로 노출하던 탓에 플레이 가능 8종과 "준비중" 13종이 뒤섞여 있었다. 사용자가 플레이 가능한 게임이 먼저 보이고 "준비중" 게임은 뒤로 밀리도록 기본 정렬을 요청했다.

### 1. `sortByPlayability` 공용 helper 신설
`registry.ts`에 `GameMeta.playable`만 보고 정렬하는 `sortByPlayability<T extends Pick<GameMeta, "playable">>(games: T[]): T[]`를 추가했다. `Array.prototype.sort`가 ES2019부터 표준 사양상 안정 정렬(stable sort)임을 이용해 `Number(b.playable) - Number(a.playable)` 비교자 하나로 "플레이 가능 그룹 먼저, 준비중 그룹 나중" 순서만 강제하고, 각 그룹 **내부** 순서는 입력 배열(카탈로그 순서, 혹은 그 앞에 적용된 검색/카테고리 필터 결과 순서)을 그대로 보존한다. 원본 배열을 변경하지 않도록 `[...games].sort(...)`로 복사본에 적용.

### 2. 대시보드 필터링 파이프라인에 적용
`src/app/page.tsx`의 `filtered` `useMemo`가 검색어(`query`)/인원수 필터(`filterIdx`)로 걸러낸 뒤 `sortByPlayability`를 마지막 단계로 통과시키도록 수정 — 검색어를 입력하거나 인원수 필터를 바꿔도 필터링된 결과 안에서 항상 "준비중" 항목이 뒤로 가는 게 유지된다(정렬이 필터 *이후* 단계라 필터가 걸러낸 하위집합에 대해 매번 다시 적용됨).

### 3. 검증
`registry.test.ts` 신설(4개 케이스: 플레이 가능 우선 배치, 그룹 내 안정 정렬 유지, 원본 배열 비변경, 전부 같은 상태일 때 순서 무변화). `npx tsc --noEmit`/`npm run lint`(경고 0)/`npx vitest run`(**312개 전부 통과**, 신규 4개 포함)/`npm run build` 전부 그린. UI 컴포넌트(`GameGrid`/`GameCard`) 자체는 변경하지 않고 상위에서 넘기는 배열 순서만 바꿨으므로 화면 레이아웃 회귀 위험은 낮다고 판단해 별도 스크린샷 검증은 생략했다.

## Phase 25 — 스플렌더(Splendor) 신규 게임 (2026-08-09)

**커밋**: (이번 세션 — `feat(splendor): add splendor board game engine, card market ui, noble system, and tests`)

사용자가 카탈로그에 `playable: false`("준비중")로만 등록돼 있던 스플렌더를 실제로 플레이 가능한 9번째 게임으로 구현해달라고 요청. `boardGameRule/스플랜더.md`(이번 세션에 새로 추가된 룰북 원문)를 근거로 엔진→UI→온라인 방→카탈로그 등록까지 기존 8게임과 동일한 5파일 패턴(`engine.ts`/`<Game>Board.tsx`/`<Game>Game.tsx`/`RulebookModal.tsx`/`meta.ts`/`<Game>.test.ts`)으로 구현했다. 참고 템플릿은 구조가 가장 가까운 센추리(엔진 빌딩 + 시장 + 온라인 락스텝)를 그대로 따랐다.

### 1. 카드/귀족 데이터는 룰북 수량만 지키는 자체 설계 데이터셋 (`cards.ts`)
`boardGameRule/스플랜더.md`는 Century.md와 달리 카드 목록 부록이 없고 단계별 수량(1단계 40장/2단계 30장/3단계 20장/귀족 10개)과 대략적인 비용·점수 곡선만 서술한다. 실제 카드 목록을 "출처 없이 정확히 아는 척 전사"하는 대신, century/cards.ts의 전신이 썼던 것과 같은 판단(문서 자체 헤더에 근거 명시)을 따라 **비용 템플릿을 5개 보석 색상에 순환 적용하는 생성기**를 만들었다 — 1단계 8개 템플릿×5색=40장, 2단계 6개×5=30장, 3단계 4개×5=20장, 귀족 2개×5=10개. 공식 수량은 구조적으로 보장되고, 색상별 분포도 균등하다.

### 2. 엔진 설계 — 자동 결제 계산 + 이산 단계별 페이즈 게이트 (`engine.ts`)
- **황금 토큰을 포함한 결제는 엔진이 자동 계산**한다(`computeAutoPayment`) — 보유한 해당 색 토큰을 먼저 쓰고 부족분만 황금으로 채우는 방식이 항상 최적(황금은 모든 색의 상위호환이라 다른 색을 아끼고 황금을 먼저 쓸 이유가 없음)이라는 판단으로, UI가 결제 조합을 수동으로 고르게 하지 않았다(센추리의 `simulateUpgrade`/`maxTradeRepeats`처럼 "엔진과 UI가 같은 함수를 공유"하는 패턴의 연장, 다만 "사용자가 더 나쁜 선택지를 고를 수 있게 열어둘 필요가 없다"는 점에서 한 단계 더 단순화).
- **턴 종료 처리를 2단계 게이트로 분리**: `finishTurn`이 먼저 10토큰 초과 여부(`phase: "discarding"`)를 확인하고, 해소되면 `afterTokensSettled`가 귀족 방문 조건을 확인한다 — 조건을 만족하는 귀족이 2명 이상이면 `phase: "choosingNoble"`로 게이트해 플레이어가 직접 골라야 다음 사람 턴으로 넘어간다(룰북 "한 차례에 귀족 1명만"). 귀족 조건은 **보유 토큰이 아니라 구매한 카드의 보너스 색상 수만** 계산한다(룰북 명시).
- **동점자 처리**: 점수와 구매 카드 수까지 완전히 같으면 "공동 승리"라는 룰북 문구를 그대로 반영해 `computeRankings`가 표준 경쟁 순위(1,1,3 — 1,1,2가 아님)를 매기도록 했다(센추리는 "더 늦게 턴을 진행한 쪽이 승리"로 완전한 순서를 강제했던 것과 의도적으로 다른 처리).

### 3. 예약 카드는 다른 8게임과 다른 새로운 "부분 은닉" 사례 (`SplendorBoard.tsx`)
이 프로젝트의 온라인 신뢰 모델(모든 클라이언트가 전체 상태를 들고 있음, docs/architecture.md §2)상 예약 카드의 정체도 사실 모든 클라이언트 메모리에 존재하지만, 실물 룰상 예약 카드는 상대에게 비공개다. 아발론이 역할을, 뱅!이 역할을 감추는 것과 같은 "UI 계층에서만 은닉" 기법을 재사용해, `SplendorBoard`가 **내 예약 카드만 카드 앞면으로, 다른 좌석의 예약 카드는 개수만 보이는 뒷면 아이콘**으로 렌더링한다 — 이 프로젝트 최초로 "카드"라는 시각 자산에 이 은닉 기법을 적용한 사례(기존 사례는 역할 카드/칩 색상 등 더 단순한 자료형이었음).

### 4. UI 비주얼 — "아크릴 포커 칩" 토큰 + 단계별 카드 프레임 (`GemToken.tsx`)
사용자가 명시적으로 요청한 "입체감 있는 둥근 아크릴 포커 칩" 형태를 위해 `GemChip`을 새로 만들었다 — 방사형 그라디언트 + 반투명 점선 테두리(카지노 칩 각인 흉내) + 좌상단 글로시 하이라이트, 전부 CSS만으로 구성(이미지 자산 없음, 이 프로젝트의 `ResourceIcon.tsx`/`PerudoFaceIcon.tsx`와 같은 관례). 개발 카드는 1/2/3단계별로 초록/황색/청색 톤 테두리+배경을 입혀 실물 카드 뒷면 색과 대응시켰고, 구매 가능한 카드는 보라색 글로우로 강조했다(룰북이 요청한 "즉시 구매 가능 카드 하이라이트" 요구사항).

### 5. 검증
`npx tsc --noEmit`/`npm run lint`(경고 0)/`npx vitest run`(**344개 전부 통과**, 신규 32개 — 인원수별 시작 토큰 수량, 3색/2색 토큰 획득 제한, 보너스 할인+황금 결제 계산, 10토큰 초과 반납, 예약 3장 제한, 귀족 방문 조건, 15점 달성 후 라운드 종료까지 요청받은 5개 영역 전부 커버)/`npm run build` 전부 그린. `npm run dev` + `npx playwright screenshot`(CLI)로 고정 state를 주입한 임시 라우트(`/dev-splendor-preview`, 검증 후 삭제)를 렌더링해 카드 시장/토큰 뱅크/귀족 타일/내 보석상/다른 플레이어 요약 행이 깨지지 않고 표시되는 것을 확인했다 — 다만 이 프로젝트의 반복된 사각지대(§2)와 동일하게, 결제/예약/귀족선택/토큰반납 모달의 실제 클릭 흐름과 실제 Supabase 온라인 방 2대 이상 기기 동기화는 이번 세션에서도 검증하지 못했다.
