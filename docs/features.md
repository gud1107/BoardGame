## 대시보드 & 게임 카탈로그

`src/app/page.tsx` — `GAME_REGISTRY`(§[architecture.md §4](./architecture.md#4-게임-카탈로그-데이터-중심-확장-설계))를 이름/영문명 검색과 인원수 필터(전체·2인·3~4인·5인+)로 필터링해 `GameGrid`로 렌더링한다. 필터는 `players.min`/`players.max` 범위가 필터 구간과 **겹치는지**(`min <= 필터상한 && max >= 필터하한`)로 판단한다 — 게임의 인원 범위가 필터 구간을 포함하거나 걸치기만 해도 노출되므로, "5인+" 필터에서 4~7인 게임(뱅!)도 정상적으로 나온다.

`playable: false`인 게임 카드는 클릭해도 `/games/[gameId]`에서 "아직 준비 중인 게임입니다" 화면만 뜬다(§[architecture.md §4](./architecture.md#4-게임-카탈로그-데이터-중심-확장-설계) 참고 — 버그 아니라 카탈로그가 구현보다 먼저 커지는 걸 보여주는 의도된 상태).

## 게임 플레이 진입 흐름 (`/games/[gameId]`)

`src/app/games/[gameId]/page.tsx`가 `select → playing → record → done`이라는 스테이지 머신을 로컬 `useState`로 관리한다.

- **`onlineMultiplayer` 게임(4종 전부)**: `select` 스테이지를 아예 건너뛰고 바로 `playing`으로 시작한다 — 참가자 식별을 게임 자신의 방 로비(닉네임 입력 + 초대 코드)가 대신 처리하기 때문이다. 게임 완료 후에도 `done` 스테이지로 넘어가지 않고 **게임 컴포넌트가 계속 마운트된 채로 자체 rematch/leave 화면**을 보여준다 — 이 페이지의 stage를 바꿔 컴포넌트를 언마운트해버리면 Realtime 채널이 전환 도중에 끊겨버리기 때문에, 온라인 게임은 의도적으로 이 페이지의 상태 머신 밖에 남는다.
- **내기(로스터) 모드**: 활성 내기 세션이 있으면 세션 참가자 중 이번 판에 낼 사람을 버튼으로 골라 선택한다(자동으로 세션의 앞 N명이 기본 선택됨, 자유롭게 조정 가능). `min === max`(예: 하나미코지) 게임은 항상 정확히 그 인원만, 가변 인원 게임은 `min~max` 범위에서 고를 수 있다.
- **자유 플레이(내기 없음) 모드**: 참가자 이름을 직접 입력한다. `Player 1`, `Player 2`처럼 기본 이름이 **초기 state 값 자체에** 미리 채워져 있어 아무것도 입력하지 않고 바로 "게임 시작"을 눌러도 동작한다([troubleshooting.md #2](./troubleshooting.md#2-고정-인원-게임에서-게임-시작-버튼이-사실상-진행-불가)에서 고쳐진 부분).
- 게임이 끝나면(`onComplete`) 결과를 **내기 세션 유무와 무관하게 항상** `gameResults`(IndexedDB)에 기록한다 — 자유 플레이 기록도 남긴다는 의미. 내기 세션이 있으면 추가로 `record` 스테이지(`RoundResultEntry`)로 넘어가 정산에 반영한다.

## 내기(정산) 시스템

### 활성화/설정

화면 우측 하단 플로팅 버튼(`🎲`)으로 여닫는 `BettingSidebar`(`src/components/betting/`)에서 전부 처리한다. 시작 전에 참가자 닉네임(최대 10명, `RosterEditor`)과 등수별 상금/벌금표(`PayoutTableEditor`)를 입력한다.

- **제로섬 검증**(`validatePayoutTable`): 합계가 정확히 0이 아니면 시작 자체가 막힌다. 기본값(`generateDefaultPayoutTable`)은 인원수에 맞춰 스펙 예시(8명 기준 4000~-4000 대칭)와 동일한 로직으로 자동 생성되어, 손대지 않고 시작해도 항상 유효하다.
- 내기를 켜지 않으면 게임은 순위 기록 없이(정확히는 `gameResults`에만 기록되고 정산에는 반영 안 된 채로) 자유롭게 플레이된다.

### 진행 중 편집 가능 범위

- **닉네임과 상금/벌금표는 진행 중에도 수정 가능.** 닉네임을 바꾸면 같은 Zustand 스토어를 구독하는 진행 중인 게임 화면에도 즉시 반영된다. 상금표를 바꾸면 제로섬 검증을 다시 통과해야 저장되고, 통과 전까지는 마지막으로 저장된 값이 유지된다(중간에 깨진 상태로 저장되지 않음).
- **참가자 추가/삭제는 세션 중 지원하지 않는다.** 이미 기록된 라운드들의 `rankedPlayerIds`/`deltas`가 특정 참가자 집합을 전제로 계산돼 있어, 중간에 인원이 바뀌면 그 라운드들과 길이/구성이 어긋나 제로섬이 깨질 수 있다. 인원을 바꾸려면 "내기끝"으로 세션을 종료하고 새로 시작해야 한다.

### 라운드 정산과 동점 처리

`useBettingStore.recordRound()`가 매 판마다 `computeRoundDeltas`(§[architecture.md §3.4](./architecture.md#34-데이터-조합-규칙-제로섬은-스키마가-아니라-매-라운드가-테이블-전체를-소비하는-방식으로-보장))로 델타를 계산하고 `totals`에 누적한다. 동점(공동 순위)이 나오면 해당 구간의 상금/벌금을 **평균 배분**하므로, 순위 입력 방식과 무관하게 라운드 합계는 항상 0을 유지한다. 실제로 플레이한 인원(예: 2인 전용 게임에 참가자가 5명 있는 세션)만 자동 순위가 매겨지고, 나머지는 공동 최하위로 자동 배정되되 필요하면 `RoundResultEntry`에서 직접 조정할 수 있다.

### 세션 종료

"내기끝"을 누르면 `endSession()`이 `computeFinalStandings`로 최종 순위를 계산해 `DailyRecord`로 저장하고(오늘 날짜 `YYYY-MM-DD` 기준), **진행 중 세션 레코드 자체는 삭제**한다(§[architecture.md §3.3](./architecture.md#33-과거-데이터-불변성-지금-이름과-그때-이름을-의도적으로-분리) — 불변 스냅샷 확정). Supabase가 설정돼 있으면 `backupDailyRecord`로 클라우드 백업도 best-effort 시도한다. 결과는 `/history` 페이지(`src/app/history/page.tsx`)에서 날짜별로 열람할 수 있다 — 이 페이지는 **이 브라우저(기기)에 저장된 기록만** 보여준다(IndexedDB가 브라우저 스코프이므로).

### 온라인 대전과 내기 시스템의 (현재) 분리

내기 세션은 IndexedDB에 저장되는 **기기 로컬** 상태다. 온라인 대전은 서로 다른 기기에서 진행되므로, 한 기기의 내기 세션이 상대 기기와 공유될 방법이 애초에 없다 — 그래서 온라인 게임의 결과는 이 기기의 `gameResults`에만 기록되고, 내기 정산에는 반영되지 않는다. 온라인 대전 결과를 내기에 반영하려면 내기 세션 자체를 Supabase로 옮기는 별도의 더 큰 작업이 필요하다(미착수, 우선순위 논의된 바 없음).

## 플레이어 식별 (일자별 닉네임 매핑)

`src/lib/identity/resolve.ts`의 `resolvePlayerIdentity(nickname)`이 3가지 신호를 순서대로 조합한다:

1. **정확히 같은 (현재) 닉네임**이 이미 있으면 자동으로 같은 사람으로 처리(`kind: "known-device"`) — 모호함이 없는 경우만 자동 병합.
2. 정확 일치가 없으면 약한 신호들을 모은다 — 과거 별칭(`aliases`) 일치, 이 기기(`deviceId`)의 최근 사용 이력, (Supabase 설정 시) 같은 IP의 다른 기기 이력(최근 14일, `RECENT_WINDOW_DAYS`). 신호가 하나라도 있으면 `kind: "needs-confirmation"`으로 후보 목록을 반환한다.
3. 아무 신호도 없으면 `kind: "new"` — 완전히 새 플레이어.

**왜 기기ID만으로 자동 확정하지 않는가**: 이 앱의 실제 사용 패턴은 "한 사람이 한 기기로 로그인"이 아니라, **한 명(주최자)이 한 기기로 여러 사람의 이름을 순서대로 입력**하는 패스 앤 플레이/사설 스코어보드 방식이다. 그래서 "이 기기 = 이 사람"이라는 가정 자체가 성립하지 않는다 — deviceId는 항상 사용자 확인을 거쳐야 하는 **약한 힌트**일 뿐, 그것만으로 새 닉네임을 기존 플레이어에게 조용히 합치지 않는다. 최종 판단은 항상 UI에서 사람이 "네, 같은 사람이에요" / "아니요, 새 사람이에요"를 확정해야 한다(`confirmMerge` / `createFresh`).

IP 기반 매칭은 Supabase가 설정된 경우에만 동작한다(`/api/ip`가 Vercel의 `x-forwarded-for`/`x-real-ip` 헤더에서 읽어온 값을 `device_sightings` 테이블과 대조) — IndexedDB만으로는 브라우저 하나에 국한되므로 기기를 넘나드는 매칭 자체가 불가능하다.

## 4개 온라인 대전 게임 — 규칙 구현 노트

공통 아키텍처(엔진/보드/네트워크 어댑터 3계층, 락스텝 동기화)는 [architecture.md](./architecture.md)와 [cloud-sync.md](./cloud-sync.md) 참고. 여기서는 **각 게임의 룰 해석 판단**만 기록한다 — 원문은 `boardGameRule/`에 있다.

### 하나미코지 (2인 전용)

21장 아이템 카드(호감도 2×3, 3×2, 4×1, 5×1 = 7명의 게이샤), 매 라운드 1장 비공개 제외 후 6장씩 배분. 4가지 액션(비밀/거래/선물/경쟁)을 라운드당 정확히 한 번씩만 사용. 게이샤 소유권은 **라운드를 넘어 유지**되며(다수 카드를 낸 쪽이 그 라운드에 가져감, 동률이면 기존 소유자 유지), 누적 게이샤 4개 이상 또는 호감도 합 11점 이상을 먼저 달성하면 즉시 매치 승리.

### 뱅! (4~7인)

표준 베이스 게임판(80장 덱, 4역할)을 구현하되 **개별 캐릭터 고유 능력(윌리 더 키드 등 16종)은 의도적으로 범위 제외**했다 — 그 외(무기 사거리, 쌍안경/무스탕 거리 보정, 다이너마이트/감옥, 무법자 처치 보상, 보안관의 부관 오사 페널티, 응급 맥주)는 전부 구현. 자리는 원탁 고정, 죽은 자리는 계산에서 제외되어 원이 좁혀진다(`circleDistance`). 승리 조건 우선순위: 배신자 단독 생존이 다른 조건보다 항상 우선.

### 그리드 포커 (2~6인)

넷플릭스 데스게임(오징어 게임 2화)의 룰을 표준 트럼프 카드로 재구성한 변형 규칙 — 원작의 10면체 주사위 대신 52장+조커 2장(54장) 덱을 쓴다. 공통 카드는 **복원 추출**(뽑을 때마다 즉시 되돌아감)이라 매 순간 확률이 항상 1/54로 동일하다. 5×5 보드에 25라운드 동안 배치, 가로 5+세로 5+대각선 2 = 12개 라인을 만들어 제출·비교한다. **2인전은 12개 중 10개 라인만 써서 6승 선취 즉시 종료**(2개는 전략적으로 버릴 수 있음), 3인 이상은 12개 라인 전부 사용(7승 선취 즉시 종료, 아니면 12라운드 종료 후 최고 승점). 동일 족보 타이브레이크는 주 숫자 → 키커 → 문양(♠>◆>♥>♣) 순.

### 아발론 (5~10인)

레지스탕스: 아발론의 표준 5~10인 룰. 인원별 선/악 구성은 공식 룰표를 그대로 따르되, **7인 구성의 "오베론 또는 모드레드" 표기 애매함은 항상 모드레드를 우선하는 것으로 명시적으로 확정**했다(스펙 해석 판단, 원문이 배타적 선택지를 애매하게 표기한 부분을 하나로 정함). 메를린은 모드레드를 제외한 모든 악(오베론 포함)을 보고, 퍼시벌은 메를린·모르가나 두 좌석은 알지만 어느 쪽이 진짜인지는 구분하지 못한다(`getKnowledge`가 이 비대칭 지식을 계산). 원정 부결이 한 라운드에서 연속 5회 누적되면 즉시 악 승리, 실패 3회도 즉시 악 승리, 성공 3회는 곧장 끝나지 않고 암살 단계로 넘어간다(암살자가 메를린을 정확히 지목하면 역전승). 7인 이상의 4라운드는 "실패 카드 2장 이상"이어야 실패로 처리되는 예외를 반영.
